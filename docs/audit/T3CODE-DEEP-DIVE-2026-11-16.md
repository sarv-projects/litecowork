## Findings and LiteCowork disposition

These are comparative observations, not decisions that override LiteCowork owner contracts.

### BYOA and provider behavior

T3 is a BYOA coding-agent product, not a model-neutral presentation router. Its own FAQ describes it as the app around existing harnesses. The reviewed implementation and guides show provider-specific adapters and provider-owned auth/model/session semantics rather than uniform behavior. Generic ACP capability declarations are conservative; separate providers have deeper bespoke adapters. The reviewed ACP surface does not provide a universal dashboard/component tree or a universal subagent feed. ACP Registry contracts describe auth methods, browser URL elicitation, disposable-session probes, model/config catalogs, and explicit session-management capabilities; a `ready` result requires a disposable session rather than passive detection (`packages/contracts/src/acpRegistry.ts:112–141, 267–309`). T3's composer context is a bounded message-context envelope with fixed typed cards and an opaque bounded future-kind payload, not a generic model-authored component tree (`packages/contracts/src/composerContext.ts:19–45, 98–177, 256–332`). `provider-core` models optional session operations such as resume, history injection, steering, interruption, runtime-request responses, snapshots, rollback, and fork; these are T3 adapter capabilities, not properties every ACP agent supplies (`packages/provider-core/src/server/ProviderAdapter.ts:83, 698`). T3's application-owned continuation queue is a separate mechanism and its default implementation drops requests; the shared live queue must be wired to the worker (`packages/provider-core/src/server/ProviderContinuationRequests.ts:15–58`). OpenCode v2 has its own event/session API and maps its live permission/form requests and background continuation behavior itself. Targeted Codex App Server source review confirms two separate question paths: experimental live `item/tool/requestUserInput` requests and `item/completed` async-question notifications that T3 turns into message-capability requests and later user-message continuation. This is provider-specific CODE/replay evidence; it does not show that ACP supplies either behavior or that a live Codex build emits the events.

The completed Cursor adapter pass provides a concrete counterexample to assuming approval/user-input parity across agents: its declared capabilities support steering, but set approval kinds and structured questions unsupported, expose no native request IDs or child-thread IDs, and state that session requests do not survive restart (`packages/provider-cursor/src/server/adapter.ts:85–89, 99–151`). It differentiates replay of an interrupted, uncheckpointed prompt from native resume after checkpoint, and interrupt waits 10 seconds before finalizing interrupted (`adapter.ts:1,058–1,066, 2,457–2,464, 2,713–2,750, 2,785–2,797, 3,125–3,149`). Child app-thread identities are synthesized from run/task IDs (`adapter.ts:1,740–1,830`); tests use injected SDK fakes or a synthetic local HTTP/protobuf backend (`adapter.test.ts:907–1,124, 1,789–1,970, 3,136–3,202; CursorSdk.test.ts:18–20`). This is provider-specific source/test evidence, not a real Cursor account or LiteCowork qualification.

The completed Pi adapter is a contrasting provider-specific path. It declares approvals, structured input and live-only request responses, steering, interruption, native thread IDs and subagent lifecycle; it does not declare durable pending requests, a native turn ID or relayable child-thread IDs (`packages/provider-pi/src/server/adapter.ts:105–197`). Confirm/select/input/editor requests use Pi's `extension_ui_request` RPC and respond through the live process; closure/expiry cancels the pending request (`adapter.ts:1,634–1,691, 1,748–1,905, 3,559–3,628`). Unexpected `agent_start` can be adopted only through Pi-specific continuation ownership callbacks; without an owner it is treated as an error and the process is terminated (`adapter.ts:2,167–2,228`). Pi subagent events deliberately retain `childThreadId: null`, with tests asserting no invented child conversation (`adapter.ts:1,445–1,641; adapter.test.ts:3,492–3,581`). Structured tool output is bounded at 64 KiB, depth 32 and 4,096 nodes, but this is not a shared UI component protocol (`adapter.ts:210–312`). Its permission hook covers Pi calls passing through that hook, not arbitrary OS/process effects (`mcpExtensionSource.ts:341–380`). Tests use fake process spawning and scripted RPC records; no T3 tests were run and these facts do not generalize to ACP or qualify LiteCowork.

**LiteCowork disposition:** retain one truthful descriptor/capability surface per native module. Keep provider reasoning, authentication, model catalogs, private transcripts, and native tools with the harness. Do not flatten unsupported provider differences, infer a tree/subagent feed from ACP, or turn provider requests into LiteCowork Task/Trust/Effect records. Any durable continuation must be separately defined by the owning LiteCowork contract and supported by exact provider evidence.

### Authentication and credentials

Reviewed T3 ACP registry/auth UI selects a provider-advertised auth method and shows the actual browser/terminal/credential interaction. Its setup contract restricts sign-in URLs to HTTP(S), models browser/device-code/terminal/credential interaction with typed bounded responses and a flow ID, and names explicit verifying/succeeded/failed/cancelled states (`packages/contracts/src/providerSetup.ts:17–113, 115–150, 183–196`). The remote T3 Connect onboarding flow also validates endpoint/environment identity before consuming a pairing code or exchanging its bootstrap credential; this is relay-specific, not native harness sign-in (`packages/client-runtime/src/connection/onboarding.ts:101–169`). Its provider-core auth controller binds a flow to owner, flow ID and expiry; serializes starts/responses; checks the selected method was advertised; and closes provider sessions around credential changes/auth (`packages/provider-core/src/server/providerAuthFlow.ts:109, 253, 382`). Its auth lifecycle verifies browser/terminal login by opening a fresh native session; discovery or a successful browser callback alone is not confirmation. Confirmation data is a binding hash/boolean, not the credential. Cancellation/logout interrupt active auth work, and subscriptions redact active interaction details from other owners (`providerAuthFlow.ts:451, 512`). The reviewed tests use fakes and do not prove live provider sign-in. These are contract and service patterns, not evidence every T3 provider implements every path. Some T3 provider guides also support instance-specific environment variables or native config directories; those are provider-specific choices and can share or isolate credentials differently.

**LiteCowork disposition:** adapt the lifecycle principle only. Authentication remains fail-closed until LiteCowork has descriptor-backed choices, a secure OS SecretStore path, safe durable receipts/reconciliation, and a verified bind/send journey. Never copy T3’s environment-variable secret entry or claim per-instance isolation unless LiteCowork’s native provider can prove it.

### Live preview versus whole-computer control

T3's live Browser preview is scoped to its daemon-owned browser tab. The server adapter asks Chromium for bounded JPEG frames, lowers the requested scale during detected motion, restores full scale after motion settles, and paces frame acknowledgements (`apps/server/src/preview/ServerBrowser.ts:3191–3203, 3287–3329`). Its authenticated stream binds the view to a `threadId` and `tabId`; outbound frame back-pressure retains one in-flight plus the newest pending frame, dropping obsolete frames (`apps/server/src/preview/ServerBrowserStream.ts:29–33, 68–90, 137–151`). The client ACKs a binary frame when it receives it, before the caller paints it (`packages/client-runtime/src/preview/serverBrowserStream.ts:246–252`). Its separate painter permits one `createImageBitmap` decode and retains only the newest waiting frame for slow viewers (`packages/client-runtime/src/preview/serverBrowserStream.ts:408–452`), but a targeted search of `src/preview` and `src/device` found no call/test of that painter and no direct checks for malformed/oversized JPEG decode or its buffer dimensions. These are source-level implementation patterns, not a measured low-overhead guarantee or proof a frame was displayed. Local/server Browser mode and Electron webview relay are separate paths (`apps/server/src/preview/ServerBrowser.ts:1040–1125`; `apps/server/src/preview/DesktopBrowserChannel.ts:15, 122+`). The web surface labels the action Take control/Release control (`apps/web/src/browser/ServerBrowserSurface.tsx:757–770`). `SessionControl` serializes operations, changes tab owner/epoch, rejects stale agent actions, and queues the new owner's actions behind tracked in-flight work and navigation before handing control over (`apps/server/src/preview/SessionControl.ts:25–38, 53–74, 84–108, 180–203`). A server regression explicitly holds a running operation, begins takeover, rejects a racing agent operation, drains the first operation, and invalidates an old snapshot reference (`apps/server/src/preview/ServerBrowser.test.ts:1628–1675`). The takeover affects Browser-tab actions; it does not request cancellation of the overall agent run. Do not equate this with LiteCowork's whole-desktop Computer channel or treat Browser JPEG behavior as evidence for Computer transport performance. T3's Device panel streams and accepts input for iOS simulators/Android emulators running on configured hosts; this is a mobile-device surface, not the host laptop desktop. Its IPC contracts separate discrete Desktop Snapshot lifecycle events from Browser preview streaming/control events (`packages/contracts/src/ipc.ts:118–245, 606–667, 1272–1349`). The Desktop Snapshot captures and delivers a selected window image; it is not continuous screen streaming. These capabilities must not be conflated.

**LiteCowork disposition:** preserve the separate, still-unavailable whole-desktop Computer target under Feature 008. The semantic split is useful: **Take over** should fence only mediated computer input, leaving reasoning and unrelated allowed work active; **Stop run** should separately close that input fence and request cancellation from the Conversation or Task owner. Sending a message is neither action. Browser preview/takeover, a simulator stream, and a one-shot screenshot do not qualify native laptop capture or takeover. Keep local observation consent, agent disclosure, input fencing, dispatched-action reconciliation, and platform qualification distinct. A UI Take over control must have an out-of-app route if the app is behind the target window; without a qualified host fence, the control must remain unavailable.

### Agent-generated interface output

T3 has two different UI-output mechanisms: a T3-owned `html_render` tool publishes agent-generated HTML as a thread attachment for a sandboxed HTML frame; MCP Apps are provider-adapted `ui://` HTML resources hosted in a separate sandboxed frame with mediated MCP calls. The MCP Apps contract binds operations to the originating `threadId` and `itemId` and defines tool/resource/context operations, not a universal declarative component tree (`packages/contracts/src/mcpApps.ts:5–58`). The reviewed client runtime's presentation state is a projection of environment/connection/configuration status, not generated app composition (`packages/client-runtime/src/state/presentation.ts:67–109, 128–182, 193–329`). Its MCP Apps host proxies typed tool/resource/link/message/context/display-mode/download requests, caps inbound JSON at 256 KiB and concurrent host requests at 16, and bounds teardown; these constraints belong to the sandboxed MCP Apps host, not ACP (`packages/client-runtime/src/mcpApps/host.ts:8–10, 210–259, 265–375, 383–408, 417–429, 469–494`). The HTML renderer is not evidence that arbitrary HTML/JavaScript belongs in LiteCowork chat.

**LiteCowork disposition:** keep Feature 016’s canonical, versioned RichPresentation contract as the only proposed portable structured answer format. Accept only registered component kinds and validated bindings/actions through that owner contract. Do not add a competing schema, execute model-supplied HTML/JavaScript in the chat WebView, or imply that an ACP agent can emit dashboards without an explicit supported capability and source evidence. Persisting/reopening a stateful answer remains a separate Library lifecycle requirement.

### Runtime, receipts, and recovery

The reviewed T3 server has typed command handling and an EventSink that atomically records its events/projections/receipts/outbox before running external effects. A post-commit worker owns side effects. Recovery recreates runtime handles from persisted references and reconciles incomplete runs; it does not claim the native provider process survived a server restart. Replay/integration fixtures exercise simulated provider event transcripts against SQLite and orchestration code, but they are not live-provider or packaged-user qualification.

The bounded stop-control review confirms that T3 re-reads the exact thread/session/provider-thread/provider-turn binding before steering or interrupting. Stop still asks the provider adapter to interrupt even when the client projection looks settled, because only the adapter can observe residual background work; terminal ingestion is awaited for at most two seconds and timeout becomes an explicit unresponsive result (`ProviderTurnControlService.ts:125–181, 216–239, 274–416`). Steering includes canonical message/context identity and re-reads current turn state after a dispatch race (`:417–518`). The 2,243-line `ThreadStop.test.ts` exercises delegation/outbox barriers, held queued messages, cancellation races, restart continuation and unresponsive stop with in-memory SQLite, production orchestration layers and a replay provider (`ThreadStop.test.ts:168–2,243`). This is richer deterministic server/replay evidence than a pure UI projection test, but it is not a real native process, OS kill, packaged desktop run or provider qualification; `ProviderTurnControlService.test.ts` uses a fake provider runtime (`:126–362`).

The continuation review distinguishes the live handoff queue from restart recovery. `ProviderContinuationRequests` is an in-memory Effect Queue whose default implementation drops requests; it is not a durable outbox (`packages/provider-core/src/server/ProviderContinuationRequests.ts:1–58`). `ProviderContinuationService` serializes by thread, revalidates thread and completion identity before dispatch, retries delegated delivery only in memory with bounded backoff, and clears adapter state after a failed ordinary dispatch (`apps/server/src/services/ProviderContinuationService.ts:29–50, 62–84, 134–171, 163–238, 246–348`). Separately, `RestartContinuation` records `provider-runtime.continue` through durable effect/outbox recovery, requires strong provider/session/native-ref identity, excludes stopped/archived/snoozed/secret-wait states and newer user work, and bounds continuation chains to three in five minutes (`apps/server/src/services/RestartContinuation.ts:38–90, 92–234, 236–378`). Its tests use fake projections and dispatch captures; this does not prove hard process-kill recovery or packaged provider restart. Do not merge the live queue and restart outbox into one product capability claim.

The latest lifecycle tranche added full reads of `RunFinalizationService.ts` (168 lines) and its 432-line test, plus `RestartBackgroundNote.ts` (448) and its 256-line test. Finalization awaits checkpoint capture, then runs repository/workspace refresh asynchronously; keyed fibers replace stale PR/identity work and prevent display refresh from blocking the next turn (`apps/server/src/orchestration-v2/RunFinalizationService.ts:62–165`). Restart notes bound labels and entry counts, track whether background work was awaited, deduplicate delivery against completed provider turns, and constrain continuation retries (`RestartBackgroundNote.ts:20–179, 195–309, 321–448`). Source tests cover those state transitions using mocked services except a temporary-directory real-git identity case; they were read but not run. The selected runtime/source audit now totals 75 files / 73,626 lines fully read, in addition to the separately counted 12,679-line `runtimeLayer.test.ts`; this is still a bounded source review, not complete server coverage.

**LiteCowork disposition:** these patterns are useful comparison points, not a schema or implementation mandate. LiteCowork’s own aggregate, transaction, Event, receipt, idempotency, RuntimeIncarnation, Environment, and recovery contracts remain authoritative. Use replay tests for deterministic mapping/race coverage, while keeping packaged desktop/provider E2E and owner/platform evidence as separate gates.
