# E13-S03 — Real workflow and platform release suite (review packet)

Story / child story IDs: `E13-S03` (epic `E13`, gate `G3`).

Commit and base: working tree on `main` at base `0b98c21`.

Outcome and touched modules:

- `scripts/v1_platform_matrix.py` (**new**) — the **generator** of the release
  qualification matrix. It probes the environment (operating system, kernel,
  architecture, toolchain versions, the agent roster, the browser roster, the
  OS credential store, the backup/restore suite, the packaging checks and the
  secret scan) and writes the matrix from what it actually observed.
- `implementation/QUALIFICATION-MATRIX.md` (**new**, generated) — the matrix
  itself, with one row per capability per operating system and one row per
  agent/browser with its observed version.

The matrix is **generated by a probe**, never hand-written. A cell is reported
as `PASSED` only when the probe ran on this host and observed success; every
other cell is `NOT RUN` or `BLOCKED` with the reason and the command.

Contract / API / event / schema references:

- Contract authority: `implementation/SCOPE.md` (the G0–G3 gate sequence, the
  "no OS receives a supported label without a real run on that OS" rule and
  the native-agent completeness list), `implementation/RELEASE.md` (the G3
  checklist), `implementation/V1-CONTRACT-RECONCILIATION-2026-10-13.md` (the
  exact mandatory OS/provider cells), `implementation/epics/E13.md` (the
  mandatory OS/provider release matrix gates of 2026-10-13).
- **No schema change, no event change, no API change.**

Fixture digests and expected vs observed outputs: the generator writes the

versions, the agent/browser observations and the per-probe state, command and
observation. The owner can replay the generator and compare.

Failure / race / authorization checks: the generator never emits a `PASSED`
cell without an observed success. The `BLOCKED` reason for the daemon-backed
capabilities is the OS credential store probe:

```
$ dbus-send --session --dest=org.freedesktop.DBus --type=method_call \
    --print-reply /org/freedesktop/DBus org.freedesktop.DBus.ListNames | grep -c secret
0
```

There is no `org.freedesktop.secrets` service on the session bus, so the daemon
cannot register its OS principal and cannot reach a state where the native
send, the planner isolation, the Workspace root revalidation, the Coworker
learner, the browser takeover, the PTY, the Effect reconciliation or the
independent verification can be exercised.

Known limitations, cost and measured performance:

1. The matrix covers **one** operating system (the probing host). The Windows
   and macOS columns are `BLOCKED` because no run happened on them. This is
   the truthful state, not a supported claim.
2. The agent roster is reported as *observed*, never as *supported*. Support
   needs the E03-S11 CODE + SYSTEM + USER conformance on the exact agent,
   version and operating system.
3. The generator does not yet drive the daemon end to end; the daemon-backed
   capability cells are `BLOCKED` by the credential store rather than executed.
   When a host with a Secret Service (or Windows/macOS) runs the generator,
   those cells still need the exact qualification commands from the owning
   epics; the generator reports the command that has to be run.
4. The matrix does not carry the per-cell **USER** result; the owner records it
   in the review packet.

Upgrade / rollback / demo instructions: re-run the generator command above.
It only reads the repository and the local build output and writes the matrix
and the evidence sidecar.

Assigned flows / benchmarks and evidence locations:

- Evidence: `/tmp/litecowork-release-evidence/platform-matrix-evidence.json`.
- Per story packets: `implementation/reviews/E13-S01.md` … `E13-S04.md`.

Blockers (owner-only or environment gates):

1. **A host with an OS credential store** (Linux Secret Service, Windows
   Credential Manager, macOS Keychain) is required to exercise the
   daemon-backed cells. That is an environment gate, not a code gate.
2. **Windows and macOS hosts** are required for their columns. No run happened
   on them, so they stay `BLOCKED`.
3. **Signing hardware/accounts** (Apple notarization, a Windows signing
   certificate) block the GA claim for those platforms. This is an owner-only
   resource.
4. **Real provider accounts** and installed native agent harnesses are needed
   for the agent cells.
