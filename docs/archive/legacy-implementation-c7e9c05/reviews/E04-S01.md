# E04-S01 — Trust evaluation and credential boundary review packet

Status: **PARTIAL.** Source includes an authenticated local-owner route for read-only TaskPlanning grant
issuance, grant revocation, exact Task/Attempt-bound Approval request
production, policy evaluation, and SecretLease metadata lifecycle. Focused SQLite and
daemon Trust CODE suites pass. This does not implement a production PolicyEngine context loader,
authenticated approval-request route, grant-specific ApprovalUse, Attempt grant
issuance, CapabilityBroker admission, or provider credential-egress boundary.

## Implemented behavior

- The typed Trust store records TaskPlanning grants only for the authenticated Workspace
  owner. This path currently allows only `workspace.resource.read`, has no SecretRefs,
  requires APPROVE_SAFE assurance, validates the exact typed CapabilityRef identity, and
  validates bounded ResourceScope shape and same-Workspace ResourceRefs, and expires
  within 24 hours. Conversation grants
  remain denied because the current persisted scope type does not pin an exact live
  ConversationTurn as required by `docs/TRUST.md`.
- Grant admission and exact replay are protected by a principal-scoped request digest
  that binds the requested authority. Generated aggregate/event IDs may change after a
  lost response; changed authority under the same request ID conflicts.
- TaskPlanning grant admission resolves every scoped ResourceRef in the selected
  Workspace. Optional revision pins must belong to that exact Resource, and Resources
  carrying a non-ACTIVE ContextDocument are ineligible for new grants. Missing Resources,
  foreign-Workspace Resources, mismatched revisions, and inactive ContextDocuments all
  return the same nondisclosing `NotFound`. Fresh admission checks this before aggregate
  state blob creation and repeats it inside the grant transaction; exact receipt replay
  remains ahead of mutable Resource checks.
- Grant row, event, aggregate snapshot, redacted audit record, and idempotency receipt
  commit in one transaction. Owner and exact-replay preflight happens before blob write;
  the write transaction repeats the owner, scope, and replay checks. Failure while writing
  audit rolls back all database rows.
- Standalone Attempt grants are denied because Attempt admission must pin the grant IDs
  atomically. Supplied Approval IDs are denied until grant-specific ApprovalUse is
  transactionally implemented. Unknown or mutating operations fail closed.
- The Effect live-fence check now binds an Attempt grant to the exact CapabilityRef on its
  CapabilityInvocation as well as the allowed operation. Missing Effect identity and a
  grant for a different capability fail closed; this guard does not make dispatch
  available because atomic Invocation/Approval admission is still missing.
- Grant revocation is Workspace-owner authorized, expected-version checked, and
  replay-safe. It records the new version, event, redacted audit, snapshot, and receipt
  atomically. SecretRef provider locators are excluded from events/audit/snapshots.
- The internal policy producer persists a pending Approval only when evaluation returns
  `REQUIRE_APPROVAL`, binds the exact Task/Attempt, operation, capability identity, target
  digest and scope digest, and sets a 15-minute expiry. It does not grant authority or
  dispatch an Effect and currently has no production caller.
- SecretLease issue requires an active Attempt grant containing the exact SecretRef,
  CapabilityRef and allowed usage, a current Runtime incarnation and lease, and sensitive
  owner assurance. Revocation can only change status/version; it rejects changes to the
  lease's authority scope. The SecretStore API is write-only and has no credential read
  method.

## Receipt replay ordering regression — 2026-10-19

The CapabilityGrant issue receipt now binds the caller's original Resource-scope intent
before any mutable Resource-head resolution. An exact receipt is looked up after owner
authorization and before resolving Resource heads or checking Resource existence. First
execution still resolves and pins the current Resource revisions, then rechecks those
pins and the active Task inside the grant transaction before committing the Grant, event,
snapshot, audit record and receipt together.

Two production-store regressions cover retries after (1) the Resource current revision
advances and (2) the scoped Resource and its revisions are deleted. Both assert replay of
the original committed Grant/Event; the first also confirms the Grant retains its original
revision pin. Test-first evidence:

```text
cargo test --locked --offline -p storage-sqlite --lib trust::tests::exact_grant_replay_survives -- --nocapture --test-threads=1
```

The initial run failed both regressions as expected: head advancement returned
`IdempotencyConflict`, and deletion returned `NotFound`. After the fix, the same command
passed **2/2** (434 filtered) on Linux with Rust 1.98.1 in offline mode. `rustfmt
--edition 2024 crates/storage-sqlite/src/trust.rs` and scoped `git diff --check` also
passed. The first test's original Resource revision is still required to belong to that
Resource at initial issuance; exact replay bypasses subsequent mutable-head/existence
checks only after the principal is re-authorized.

Daemon Trust policy command:

```text
cargo test --locked --offline -p litecoworkd --bin litecoworkd trust::tests:: -- --nocapture --test-threads=1
```

Result: **PASS, 27 passed, 0 failed** (304 filtered; local Linux, offline). The Cargo
build emitted unused/dead-code warnings from unrelated `domain-task`, `storage-sqlite`
WorkspaceRoot membership, and daemon archive/filesystem modules.

An earlier focused run exposed that SecretLease revocation accepted a caller-mutated
`next` record with altered `allowed_usage`. The transaction now compares the full expected
record before persistence. The same run exposed incorrect parsing of HLC metadata as an
RFC3339 timestamp; Trust event validation now checks that HLC fields are present and
control-character-free rather than treating them as wall-clock timestamps.
