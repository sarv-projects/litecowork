# E05-S04 partial source review packet — Verification escalation and lead failover

**Status:** Partial CODE, IN_PROGRESS. E05-S04 has bounded policy evaluators, a durable
policy-failover admission transaction and a production failover service caller, but
automatic trigger production, replacement Attempts, a persisted LeadHandoffPacket, a fresh
lead AgentSession, qualified fallback admission and provider recovery are not implemented.
Dispatch remains fail-closed.

## Implemented source

`domain-task` now exports a typed lead-failover policy evaluator and a bounded worker
escalation evaluator. The failover evaluator validates the pinned
policy shape and bounded ordered fallback list, requires an explicitly confirmed enabled
trigger, binds the observation to the currently selected lead, checks observation
freshness/expiry and Runtime-incarnation identity where required, enforces the policy
change budget and safe-boundary gate, and considers fallbacks only in their pinned order.
Candidate readiness must refer to the exact Task aggregate version and TaskSpec revision.
The result is either disabled, an owner-choice request, a version-fenced recommendation,
or a typed blocker. The caller remains responsible for revalidating the recommendation in
the TaskService transaction; it is not authorization to switch the lead.

The escalation evaluator counts the initial child Attempt toward the profile and Task
ceilings, respects the global 1..8 cap and effective child concurrency, and only proposes
the next policy-ordered profile after a recoverable verification failure, settled Effects,
and a recoverable Step. Passed, permanent, ambiguous, budget-exhausted, stale TaskSpec,
unreconciled, over-limit, or unqualified states cannot produce another Attempt. Every
recommendation is pinned to the observed Task version and TaskSpec revision.

The Coworker settings editor now renders the exact selected fallback order and provides
keyboard-operable Move up/Move down controls. Unknown saved bindings stay visible and can
be removed. The selected list is still checked against current lead eligibility at
execution time; editing its order grants no authority.

An owner-only Operator command is also wired to a `TaskStore::commit_task_lead_handoff`
port. It requires Workspace ownership, an active local Runtime binding, `If-Match`, an
idempotency key and an 8 KiB bounded body. The transaction is constrained to a Task in
`READY`, before an accepted Plan or active planning session, Attempt, or unresolved Effect;
it rechecks the target binding and writes the Task assignment, canonical event and replay
receipt atomically. It retains the TaskSpec revision and does not transfer authority,
Attempt, lease or native session state. The implementation does not yet build or persist
the portable LeadHandoffPacket or open a new AgentSession. This path is an owner-requested
safe-boundary assignment only; it is not automatic failover and cannot change a running
Task's lead.

The canonical `task.lead_agent.changed.v1` event uses the committed old/new binding IDs,
`OWNER_REQUEST`, authenticated Principal actor, pinned TaskSpec revision and aggregate
version. Request idempotency and event correlation IDs are independently derived and are
not required to be equal. Exact Task/event/receipt behavior is covered by focused SQLite
transaction tests; Operator route invocation and the domain correlation test are added,
with their verification result to be recorded below after the shared Rust target is free.

The internal POLICY_FAILOVER handoff command now rejects observations without an expiry,
observations whose expiry is not after the server-generated event time, future-dated
observations, and malformed/non-finite timestamp text. The policy evaluator and handoff
command are still not wired to an automatic producer, and the SQLite lead-handoff
transaction deliberately accepts only `OWNER_REQUEST`; future automatic failover must
revalidate the authenticated observation, TaskSpec policy, candidate readiness, and safe
boundary in its owning transaction.

The `ASK` mode now has a durable Needs You surface. `domain-task` returns the ordered
eligible fallback choices instead of discarding them, and
`crates/storage-sqlite/src/lead_failover_choice_request.rs` commits that choice request as
a planning-scope `UserRequest` of kind `DECISION` with the ordered fallback bindings as
its only answers, together with the `user.request.created.v1` event and an exact replay
receipt. The request is scoped to the Task's planning AgentSession, one observation can
open at most one request, and the transaction re-derives the pinned policy, the current
lead, the observation freshness, the binding eligibility and the Task fences before it
writes anything.

## Durable observation and policy-failover admission (2026-10-20)

The canonical `task.lead_agent.changed.v1` event is now the durable trigger-observation
record. No separate observation table or event family was invented because the current
machine contracts define neither; the event schema already carries the exact bounded
observation shape. A `POLICY_FAILOVER` commit therefore records the observation, the
cause, the service actor, the pinned TaskSpec revision and the aggregate version in one
immutable row, and the same transaction refuses to reuse that
`(source_service_id, source_observation_ref)` pair for a second lead change.

`crates/storage-sqlite/src/delegation_failover.rs` revalidates, inside the immediate
handoff transaction: observation shape and required expiry; `observed_at <= event time <
expires_at`; the affected binding equals the transactionally read current lead; the pinned
`lead_failover_policy_json` is structurally valid and `ALLOW_LISTED`; the trigger is
allowed; the count of prior `POLICY_FAILOVER` events is below `max_lead_changes`; the
observation reference has not already been consumed; and the target is the next ordered,
enabled/lead-eligible fallback. The existing Task-version CAS, TaskSpec revision check,
READY/no-plan/no-live-planner/no-active-Attempt/no-unresolved-Effect boundary, canonical
event, aggregate-state blob and exact idempotency receipt remain unchanged. A failed
observation, fallback, change budget or race writes no Task mutation, event or receipt.

`domain-task::LeadFailoverService` is the production caller of the previously unwired
`decide_lead_failover`. It loads the owner-scoped Task and current TaskSpec, parses the
pinned policy, rechecks each ordered fallback's static Workspace/enabled/lead-eligible/
Runtime-pin eligibility, consumes caller-supplied placement proofs for the first
statically eligible fallback, evaluates the fresh observation, and only then builds and
executes a `POLICY_FAILOVER` command with the authenticated service actor. A placement
failure on the first fallback blocks rather than silently promoting a later fallback that
the storage transaction cannot independently qualify. `ASK` returns an owner-choice
decision and `DISABLED` returns disabled; neither commits a lead change.

## Durable `ASK` owner-choice request (2026-10-20)

`TASK-RUNTIME.md` requires `ASK` to "add a Needs You choice from its ordered fallback
list", and `DELEGATION.md` states that `ASK` presents choices in Needs You. The durable
artifact is now implemented: `crates/storage-sqlite/src/lead_failover_choice_request.rs`
commits a planning-scope `UserRequest` of kind `DECISION` and interaction mode `FORM`,
its `user.request.created.v1` event, and the exact replay receipt in one transaction.

The request is scoped to the Task's planning `AgentSession`, so the schema's
`user_request_admission_matches_scope` trigger admits it only for the Task that raised
it, and the answer returns to that Task. The choices are the pinned fallback list in
pinned order, filtered to the bindings that are enabled and lead-eligible in the same
Workspace at commit time; the current lead is never offered as its own replacement. Each
choice carries `value = {"agent_binding_id": ...}`, and the stored response schema
accepts only that object, so a free-form answer cannot select an unbound replacement.
The choice label is host-authored from the catalog display name plus the binding ID; no
provider text, native handle, transcript or secret is stored, and the request summary
names only the confirmed trigger.

The transaction re-derives everything instead of trusting the caller: Workspace status,
Task version and TaskSpec revision fences, a Task state that can still hold an answerable
request, the current lead against the observation, the pinned `ASK` policy and its
allowed trigger, a non-empty bounded fallback list, durable binding eligibility, the
planning session scope, and the observation freshness and authenticated source. The
durable request ID is derived from the observation identity, so one observation can open
at most one owner choice request in a Workspace — the same rule the automatic failover
transaction applies to a lead change; a replayed observation is rejected with
`LEAD_FAILOVER_OBSERVATION_ALREADY_ASKED` instead of opening a second inbox item or a
second choice request for another Task of the same Workspace. A rejected commit writes no
request, no event and no receipt.

The owner answer path already existed: `POST /v1/user-requests/{id}/respond` with a
`choice_id` resolves the stored choice value, and the new test proves the recorded
response is exactly the chosen fallback binding.

`crates/storage-sqlite/src/delegation_failover.rs` now exposes the pinned-policy loader,
the policy shape validator and the observation accessors used by both the automatic
handoff and this choice request, so the two paths cannot drift on policy or observation
semantics.

## Remaining acceptance

- **CODE pending:** a real adapter/Runtime producer that supplies confirmed
  `AGENT_UNAVAILABLE`/`QUOTA_EXHAUSTED`/`RUNTIME_UNAVAILABLE` observations through an
  authenticated service boundary; endpoint/auth/Trust/budget/deadline revalidation for the
  selected fallback beyond the static binding and placement proof checked here; a persisted
  bounded `LeadHandoffPacket` (no machine schema exists yet); a fresh lead `TASK_PLANNING`
  AgentSession created from that packet; and atomic new-Attempt escalation admission.
  Owner-requested READY-only assignment and the policy-failover transaction do not satisfy
  those gates.
- **CODE pending (contract gap):** the durable `ASK` request is implemented and proven in
  the storage layer, but no `storage-core` port exposes it, so `domain-task`'s
  `LeadFailoverService` cannot persist the owner choice request itself, and no producer
  supplies the confirmed observation that would trigger it. `crates/storage-core/src/lib.rs`
  needs a `LeadFailoverChoiceRequestStore` port (or an equivalent `TaskStore` method) that
  `domain-task` can call for its `AskOwner` outcome.
- **CODE pending:** the owner's answer is recorded durably, but applying it to a Task's
  lead still goes through `POST /v1/tasks/{id}/lead-agent`, which `docs/API.md` documents
  as a `READY`-only, settled-Task assignment. Applying an `ASK` answer to a running Task
  needs either that documented boundary to change or a dedicated owner-decision handoff;
  `docs/API.md` is the document that must change, and it is outside this story's write
  surface.
- **SYSTEM pending:** exact native adapter/provider, Runtime, Environment and OS recovery
  qualification, including quota and stale-TaskSpec races.
- **OWNER USER pending:** failed low-cost/verifier run followed by bounded fallback or a
  Needs You choice, reviewed against the output and permission oracle.

No provider dispatch or lead failover was performed against a live provider. The execution
admission store remains fail-closed until the Trust, Invocation, ApprovalUse, Environment,
lease/fencing and Effect transaction is implemented and qualified. The `ASK` owner choice is
now durable and answerable, but nothing yet produces it in a live run: the observation
producer and the `storage-core` port do not exist, so the request is only created when a
caller commits it directly. The request carries no expiry because no contract defines a
choice-request lifetime; a Task cancellation still cancels pending Task-scoped
`UserRequest`s, and the owner can dismiss the request.
