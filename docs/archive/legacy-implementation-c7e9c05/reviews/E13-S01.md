Fixture digests and expected vs observed outputs:

- The CODE tests use the repository's own schema (the store is opened through
  `SqliteWorkspaceStore::open`, so the migration chain and the immutability
  triggers are the real ones).
- Expected: a backup container is written, re-read, and every digest
  recomputed. Observed: the round trip restores the Workspace row and the
  aggregate blob, and the restored blob decrypts to the original bytes
  (`{"value":42}`).
- The container digest, the manifest integrity digest and the archive size are
  printed by `litecoworkd backup create`; the exact values of a run are the
  owner-facing evidence.

Failure / race / authorization checks:

| Negative case | Where it is proven | Result |
|---|---|---|
| corrupt archive | `verification_rejects_a_corrupt_archive` | refused with `StoreError::Integrity` |
| wrong passphrase | `verification_rejects_the_wrong_passphrase` | refused with `StoreError::Integrity` |
| interrupted/partial restore | `a_failed_restore_leaves_the_destination_untouched` | the destination is never created |
| restore with a live daemon | `a_restore_refuses_a_live_runtime_lock` | refused with `StoreError::Busy` |
| restore into a populated directory | `a_restore_refuses_a_non_empty_destination` | refused, the owner's file survives |
| foreign/incompatible schema | `a_restore_refuses_a_manifest_that_declares_a_foreign_schema` and `the_upgrade_check_refuses_an_unknown_schema_version` | refused |
| disk full during the backup | `a_failed_backup_leaves_no_usable_archive` (unwritable backup directory) | refused, no archive and no staging area left |
| secret in the artifact | `the_passphrase_never_appears_in_the_archive_or_its_name` | the passphrase and the workspace key material are absent from the archive bytes and from the archive name |
| Runtime-local tables | `the_filtered_snapshot_drops_runtime_local_tables_and_keeps_workspace_rows` | the excluded rows are dropped and the schema guards are preserved |

Known limitations, cost and measured performance:

1. The blob scope of a backup is **one Workspace**; the database snapshot still
   carries the rows of every Workspace in the installation, because row-level
   Workspace filtering of the snapshot is not implemented. A multi-Workspace
   installation must be treated as one backup unit.
2. The restore is refused when the destination holds its single-instance lock;
   there is no forced restore.
3. The restore does not restore the OS credential store. A different OS user or
   a different machine has no workspace blob key and the restore refuses with
   `the encryption key for ... is unavailable`.
4. The backup is a local file. There is no schedule, no cloud copy and no key
   escrow.
5. The backup create/restore requests are **not** wired into the Operator
   request-dedup ledger or the `audit_records` audit trail that
   `docs/STORAGE.md` requires for "Create/restore request deduplication and the
   corresponding AuditRecord". The CLI writes the verified
   `workspace_backup_manifests` row, but the dedup receipt and the audit record
   are not produced. This is a contract gap that needs the Operator request
   path.
6. The in-progress upload chunk metadata is not restored as non-resumable audit
   state; the purge plans and purge receipts **are** carried because those
   tables are not excluded.

Blockers (owner-only or environment gates):

1. **SYSTEM evidence is BLOCKED on this host.** The daemon registers its OS
   principal in the OS credential store before it opens the durable store, and
   this host has no Secret Service:

   ```
   $ dbus-send --session --dest=org.freedesktop.DBus --type=method_call \
       --print-reply /org/freedesktop/DBus org.freedesktop.DBus.ListNames | grep -c secret
   0
   ```

   There is no `org.freedesktop.secrets` service on the session bus, so
   `litecoworkd run` fails with `RUNTIME_OS_PRINCIPAL_UNAVAILABLE` and no real
   installation can be created here. The backup/restore behaviour with the
   **real** OS credential store is therefore **NOT RUN** and must be qualified
   on a host with a Secret Service (or on Windows/macOS).
2. **USER evidence is PENDING.** The owner has to run the restore on a clean
   installation and resume an eligible Task.
3. **Signing / installer** is out of scope for this story and is covered by
   E13-S04.
