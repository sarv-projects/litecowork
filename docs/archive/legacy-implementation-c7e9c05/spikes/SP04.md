# SP04 — Native coding-agent handover and safe-switch PoC

## Question

Given a coding task that Codex has started but not finished, can OpenCode continue from a
bounded, durable handoff and the shared project state, complete the acceptance criteria, and
return changes that the owner can review—without relying on Codex's private session or full
transcript, losing work, duplicating changes, or allowing Codex to keep writing after handoff?

This is a feasibility spike, not production code or proof that the full Agent Fabric,
Task Runtime, Trust, or desktop experience is complete. The architecture authorities are
[`AGENT-FABRIC.md`](../../docs/AGENT-FABRIC.md),
[`TASK-RUNTIME.md`](../../docs/TASK-RUNTIME.md),
[`FLOWS.md`](../../docs/FLOWS.md) (F25, F30, F37, F38, F53),
[`TRUST.md`](../../docs/TRUST.md), and
[`BENCHMARKS.md`](../../docs/BENCHMARKS.md) (B10, B15, B22, B33, B34, B43, B44, B46,
B60, B67).

## Selected pair

| Role | Harness | Model/configuration |
|---|---|---|
| Lead | Codex CLI | GPT-6 Luna, reasoning effort medium |
| Worker | OpenCode CLI/server | `opencode/mimo-v2.6-flash-free` |

## Probe protocol

1. Use disposable repositories and deterministic coding tasks with explicit acceptance tests.
   Never expose the LiteCowork source tree or unrelated user files to a worker.
2. Have Codex make a bounded partial implementation, then stop it at a declared checkpoint.
   Capture the base repository commit/branch and dirty-state summary, workspace snapshot/diff,
   per-file checkpoint manifest and digest, tests already run, completed and unresolved
   requirements, relevant decisions, and acceptance criteria in a bounded packet.
3. Start OpenCode with only that packet, the permitted project state/artifacts, and normal
   repository instructions. Do not provide Codex's full transcript, private session, or
   hidden reasoning. Ask OpenCode to identify completed versus remaining work before editing.
4. Let OpenCode continue and finish the same task. Run the complete acceptance suite against
   the combined result, inspect the diff relative to both the original repository and the
   sender checkpoint, and have the owner review it for correctness and necessary rework.
5. Repeat across distinct small coding tasks and checkpoint shapes. Include partial code with
   failing tests, a completed subtask with unresolved acceptance criteria, and a checkpoint
   taken after the sender is stopped mid-task. Record each case as PASS, FAIL, or BLOCKED.
6. Exercise safety gates independently: sender still active, missing/malformed packet,
   checkpoint digest mismatch, stale Task version, worker crash, cancellation uncertainty,
   and restart between settlement and replacement. A safe block is correct behavior for
   unsafe/ambiguous states, but does not count as a successful handover case.
7. The owner reviews the produced diff and test evidence for every real coding-task run.

## Handover acceptance criteria

Each case passes only when all applicable checks pass:

| Criterion | Evidence required |
|---|---|
| Task continuity | Receiver correctly states the objective, completed work, remaining work, constraints, and acceptance criteria using the packet and project state alone. |
| Checkpoint integrity | The captured checkpoint is identified by a digest; a mismatch blocks receiver admission. |
| Work preservation | Sender changes remain present unless the receiver makes a justified, reviewable change. No sender work is silently lost or reverted. |
| Receiver completion | Receiver completes the task and the full acceptance suite passes against the final combined tree. |
| No duplicate work | Diff and tests show no duplicate implementation or repeated consequential operation caused by handover. |
| Stale-writer exclusion | The receiver is not admitted until the sender is confirmed quiescent and old write authority is fenced; no old-worker write occurs after handover. |
| Reviewability | Final changed paths, test evidence, unresolved limitations, and provenance are available for owner review. |
| Context sufficiency | Any receiver question is recorded; a case fails if it depends on unprovided sender-private context that should have been in the packet. |

Passing the prototype ledger tests is not sufficient by itself: at least the real-provider
handover, end-to-end acceptance tests, and owner review must pass. A few successful cases
establish feasibility only; they do not establish general reliability across tasks/providers.

## Handover evidence record

For each case record:

```text
case ID and task specification/acceptance-test digest
host OS and repository fixture identity
sender harness/model and receiver harness/model versions
base repository commit/branch and dirty-state summary
sender checkpoint state and checkpoint digest
handoff packet schema/version and digest; per-file manifest or immutable snapshot reference
what context/artifacts were provided to the receiver
receiver's stated completed and remaining work
initial, checkpoint, and final changed-file lists/digests
full acceptance-test command and result
stale-writer, duplication, lost-edit and restart checks
receiver clarification requests and whether required context was absent
owner review result and required rework
provider usage/cost when available, otherwise UNKNOWN
failures, limitations, and evidence references
```

Provider usage and cost are contextual; correctness and successful handover are the PoC
question.

**Technical result: PASS for this sequential handover case; owner review pending.** This does
not test a LiteCowork Task record, active Codex cancellation, or broad reliability. The model

## Handover case SP04-HO-05 — retry policy checkpoint — 2026-10-07

The disposable Git fixture is `/tmp/litecowork-sp04-ho05-retry-after`, base commit
`584f6b2b5032e329ccd23cfc7842bec65c12172b`, branch `master`. Codex CLI 0.160.1 using
`gpt-6-luna` at medium reasoning implemented only `exponential_delays`; its three focused
tests passed and its one-shot process exited before receiver admission. The bounded packet
included the original objective and acceptance criteria, branch/base, changed paths, completed
and remaining work, checkpoint test state, and a SHA-256 manifest over `README.md`,
`retry_policy.py`, and `test_retry_policy.py` (`2e24383541da12cd599ad7e9ca77f666e037b425eb8426e686ce3fb3d3db0431`). It did not include a transcript or private Codex session.

OpenCode CLI 2.0.24 was requested with `opencode/mimo-v2.6-flash-free`; the model was listed
and the request ran on it. Before editing, OpenCode restated the objective, the Codex-completed
function, remaining `parse_retry_after` behavior, constraints, and expected checkpoint failures
from the packet. It verified the manifest hashes, implemented the remaining function, added
coverage, preserved Codex's implementation, and reported 15 tests passing. Independent review
then found a standards mismatch that the initial acceptance tests did not cover: signed values
such as `-1` were clamped to zero, even though HTTP `delay-seconds` is `1*DIGIT` (non-negative
decimal digits). The implementation and tests were tightened to reject signed values and
malformed date forms, while adding coverage for the two obsolete HTTP-date formats recipients
must accept. A follow-up source review found that 5,000-digit values could raise Python's
integer conversion limit and that positive fractional-millisecond delays were rounded down.
The fixture now parses bounded digit strings in small groups, rejects inputs over its documented
8,192-character resource limit, and rounds date delays up. The final disposable suite passes
20 tests. The applicable grammar is in [RFC
9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3).

Final changed paths are `retry_policy.py`, `test_retry_policy.py`, and the fixture's README
contract; the handoff packet is retained for review. No dependencies were added. The full task
was completed only after the review correction, so the case records **handover pass with one
independent-review correction**, rather than treating the receiver's first green run as final
acceptance. It is sequential handover evidence: Codex had exited, so this case does not test
active cancellation or stale-writer fencing. The fixture remains temporary; its generated
`__pycache__` is an untracked test artifact and is not part of the implementation diff. The
handoff packet and final diff are available under the path above.

## Prototype safety gates — 2026-10-07

The spike suite now has 42 tests. The ledger rejects missing/malformed packets, stale Task
versions, unquiesced senders, mismatched manifest digests, and a Task packet changed after the
sender Attempt settled. It persists the settled checkpoint and lease epoch across database
reopen between settlement and replacement. A sender that exits with a crash status can be
replaced only after quiescence, Effect reconciliation, lease release, and a matching checkpoint
digest are recorded. `SafeSwitchCoordinator` now joins file verification to both ledger
transitions: before settlement it copies the manifest-listed files into a digest-addressed,
read-only checkpoint snapshot and verifies the copied bytes; before receiver admission it
verifies that persisted snapshot again. Changes to the sender's original workspace after
settlement do not affect the receiver's pinned snapshot. Tampering with the stored snapshot or
its identifier blocks admission and leaves the settled sender Attempt intact. An unchanged
snapshot can be admitted after ledger restart with the next lease epoch.

Replacement lifecycle state now distinguishes admission from a running process. The ledger
records a replacement as `ADMITTED` while its lease epoch is reserved; the coordinator marks
it `RUNNING` only after process creation succeeds. If checkpoint revalidation or process
startup fails, it records `START_FAILED`, clears the Task's active Attempt, and keeps the
consumed lease epoch fenced. A subsequent admission may retry the same selected lead from the
same pinned checkpoint at a higher epoch. The tested TOCTOU failure between admission and
process launch therefore cannot leave a nonexistent worker recorded as running or strand the
Task behind an active Attempt.

A Linux restart test crashes the Runtime after it launches a contained heartbeat writer but
before it records the replacement as `RUNNING`. Bubblewrap's `--die-with-parent` stops further
writes. The admission persists the launch owner's Linux identity (PID, `/proc` start-time
ticks, and boot ID); recovery refuses to clear it while that identity is live, then records
`START_FAILED` only after a restarted Runtime verifies the owner is gone. A retry uses the same
pinned checkpoint at lease epoch 3. Separate checks reject PID reuse and an identity from a
different boot; unreadable boot identity also fails closed. An `ADMITTED` row with missing
identity remains blocked. These are
SP04 Linux behaviors; product RuntimeLifecycle/TaskService integration, Effect reconciliation,
and supported desktop OS qualification remain open. B76/F80 describe the startup recovery gate.

Recovery is also exercised after the replacement has durably reached `RUNNING`. The ledger
stores the Runtime launcher's PID/start-time/boot identity and the contained bubblewrap worker's
PID/start-time/boot identity in the same transition that records `RUNNING`. After the Runtime
crashes, recovery refuses to release the Task while either identity is live or cannot be
verified. Once both are gone and the heartbeat has remained unchanged for the test's quiet
window, the Attempt becomes `ABANDONED`, records the test-supplied Effect/lease reconciliation
gates, and releases Task ownership. A retry preserves the pinned checkpoint and starts at lease
epoch 3. A live-process check confirms recovery leaves the Attempt `RUNNING` while the Runtime
is still alive. If worker identity sampling fails immediately after process creation, the
coordinator still commits `RUNNING` and retains the active Task slot; recovery blocks because
the identity is missing. This is Linux fixture evidence; Effect and lease gates remain mocked,
and product recovery is still required. Missing worker identity and unresolved Effect gates
both leave the Attempt `RUNNING` and its Task slot occupied. F81/B77 record the product
contract.

As a repeatability check, the two Runtime-crash recovery tests (crash after launch but before
`RUNNING`, and crash after `RUNNING`) were each run five additional times. All 10 repeat runs
passed. This supports repeatability of those fixture transitions only; it does not expand OS,
provider, or product-runtime coverage.

The Linux process supervisor can bind the admitted snapshot read-only at a fixed path inside
the receiver's bubblewrap mount namespace while keeping the receiver's project directory
writable. Before launch, the supervisor copies each manifest-listed file into a Linux sealed
`memfd`, verifies the file digest while copying, seals it against writes/growth/shrinking, and
passes it to bubblewrap as read-only bind data. A sandboxed receiver read nested pinned files,
failed to overwrite them, and wrote an output file to its writable project directory. A host
mutation after sandbox launch did not change what the receiver read. A snapshot changed between
ledger admission and worker launch was rejected before launching. This proves those byte and
mount boundaries for the tested Linux/WSL2 setup; it does not qualify other desktop operating
systems.

An end-to-end fixture now starts a sender under the Linux process supervisor, stops it and
collects quiescence evidence, creates and verifies the checkpoint snapshot, settles the sender
Attempt, admits the next lease epoch, then starts a receiver with that snapshot mounted
read-only. The receiver observed the sender's checkpoint contents from sealed mount data,
could not overwrite the mounted checkpoint, updated the corresponding file in the writable
project workspace, and wrote an output file there while the pinned snapshot remained unchanged.
Effect reconciliation and lease release in this fixture are still supplied as test booleans,
not product services.

`handoff_integrity.py` builds a canonical SHA-256 manifest over relative files and verifies the
manifest against the actual checkpoint tree. Tests reject changed/missing files, edited
manifest fields, parent traversal, symlink paths, and NUL-byte paths. The helper independently
verified the SP04-HO-04 manifest digest. `SafeSwitchCoordinator` copies the manifest-listed
files to a digest-addressed snapshot, verifies the snapshot, marks it read-only, then pins the
manifest through settlement. Receiver admission re-verifies that snapshot after ledger restart. At
worker start, the Linux supervisor hashes each file again while copying its bytes to sealed
`memfd`s; a mismatch blocks launch. Bubblewrap mounts those sealed bytes read-only in the
receiver namespace. Thus later changes to the source files cannot change the worker's view.
Receiver packaging is bounded to 4,096 files and 512 MiB total; larger checkpoints fail before
worker launch. The Python PoC does not qualify other desktop OSes, native harness shutdown
semantics outside the tested path, or product integration with Environment and Task services.

The process supervisor tests continue to prove live-worker/descendant containment for the
tested Linux PID namespace. These tests do not establish macOS/Windows behavior, every native
agent's host shutdown semantics, or real Effect/lease service integration. Owner review of
the implementation and evidence remains required.

Platform qualification for this run is limited to WSL2: Linux kernel
`6.18.40.1-microsoft-standard-WSL2`, bubblewrap `0.9.0`, x86_64. A guard test verifies that
the PoC refuses to spawn workers when its platform identifier is Darwin or Windows. Native
Linux, macOS, and Windows containment were not run; the guard test proves refusal only, not
containment on those systems. See the consolidated
[`SP04 handover review`](../reviews/SP04-HANDOVER-REVIEW.md).

A follow-up attempt tried to launch Codex inside the same read-only-root bubblewrap fixture
used for fake workers. Codex exited before starting Task work because the read-only home
prevented PATH-alias and in-process App Server initialization. No task files changed. This
shows that the fixture sandbox cannot simply wrap the whole native Codex CLI. Native harness
state and the worker's writable Environment need separate boundaries; the next live-cancel
test should use the native adapter's supported sandbox/App Server path instead of weakening
the fixture's read-only filesystem.

The prototype integration is deliberately narrower: it materializes and revalidates a
manifest-scoped snapshot at settlement/admission and mounts it read-only for a tested Linux
receiver. It does not solve the native adapter's environment-boundary problem or qualify
host-side snapshot protection against another same-user process.

## Handover safety fixture — 2026-10-06

The spike ledger is a disposable SQLite prototype with WAL/FULL durability. It keeps a
running Attempt pinned to its original AgentBinding when the Task lead changes. Replacement
admission requires matching process-exit evidence, mocked Effect reconciliation, mocked
ExecutionLease release, a checkpoint digest and a strictly increasing lease epoch. The
Task/handoff survive database reopen. These are prototype gates; the Effect and lease
services are not connected to LiteCowork's product implementations.

Fixture process cancellation was tested against a live worker, a SIGTERM-resistant child, and a
descendant that calls `setsid()`. A plain POSIX process group failed the detached-child case:
it reported quiescence while the detached child later wrote a marker. The PoC therefore now
requires Linux bubblewrap with a PID namespace and `--die-with-parent`. In a regression test,
the same detached-child behavior was contained and no write occurred after quiescence. The
worker root is read-only except the disposable project directory; `/tmp` is private to the
sandbox. This proves behavior only for the tested Linux environment. macOS/Windows process
containment, capability side effects, and provider-specific cancellation remain unqualified.

The fixture tests process quiescence and replacement admission only. Case SP04-HO-04 adds a
real Codex App Server interruption followed by sender-host shutdown and a real OpenCode
continuation, but the Effects and lease gates remain mocked. Turn interruption alone left the
writer active; only host shutdown followed by an observed quiet interval allowed replacement.

## Current result

**IN_PROGRESS — five disposable Codex-to-OpenCode handovers reached task acceptance, with
independent review corrections in the fifth case: three sequential cases, one interrupted
partial-implementation case, and one digest-pinned retry-policy case.** In the live case,
`turn/completed(interrupted)` did not stop the sandbox writer; the sender App Server host
had to be shut down and its heartbeat observed stable before OpenCode admission. This proves
that the selected agents can continue a bounded checkpoint after that explicit quiescence
gate. It does not establish product Task/Attempt coordination, actual lease fencing, Effect
reconciliation, native cancellation guarantees beyond this observed path, cross-platform
containment, or broad handover reliability. Owner review remains pending.

HO-01 through HO-04 scratch source trees were absent during the 2026-10-07 review; their
recorded results are retained, but exact diffs could not be independently reviewed. HO-05's
source review caught the HTTP grammar issue and follow-up integer-length/rounding edge cases;
the disposable fixture now passes 20 tests. Product code was not changed by those corrections.

The prototype stays under this spike. Do not promote its SQLite ledger or process supervisor
into product crates without implementing the owning Task/Attempt, lease, Effect, Environment
and Runtime contracts.
