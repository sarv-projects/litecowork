# SP05 — Local model provider and native-harness qualification

Status: **NOT RUN**. This spike is a release gate for E06-S04, not a claim that local
inference is implemented. It does not authorize Task planning/execution, a local-model
AgentBinding, or direct access from the WebView or an Environment to an inference server.

## Question

Can one supported native coding-agent harness use a selected local inference engine on
declared desktop hardware while preserving the harness's tools, bounded context,
cancellation, session lifecycle, and LiteCowork's local-provider security boundary?

A model HTTP endpoint by itself is not an AgentAdapter. The desired outcome is a qualified
combination of:

```text
native harness + exact harness version/configuration
                  ↓
             local engine
                  ↓
       selected model + hardware
```

## Candidates and sources

Compare candidates only through their official APIs and current documentation:

- Ollama API: <https://docs.ollama.com/api>
- LM Studio developer API: <https://lmstudio.ai/docs/developer>
- llama.cpp project/server: <https://github.com/ggml-org/llama.cpp>
- Existing native harness contracts: [Agent Fabric](../../docs/AGENT-FABRIC.md) and
  [Stack](../STACK.md).

These links are research references, not selected protocols. Record the exact product,
version, API mode, endpoint ownership, request/response fields, and model identifier used
for every run. Do not assume that two OpenAI-compatible endpoints have identical behavior.

## Preconditions and safety boundary

1. Select one provider protocol/version and one native harness/version. If no harness has
   a supported local-provider configuration path, record **BLOCKED**; do not wrap raw
   completion HTTP as a fake agent.
2. The owner explicitly registers the local provider endpoint in trusted Runtime state.
   The desktop UI and WebView do not make network requests to it. Agent input, Resource
   content, model output, and provider redirects cannot register or change the endpoint.
3. The Runtime broker accepts only the registered local service identity and the exact
   approved scheme, host/address, port, and operations. Apply the local-provider and
   loopback rules in [Network Security](../../docs/NETWORK-SECURITY.md); reject arbitrary
   loopback, private/intranet, link-local, metadata, DNS-rebinding, and redirect targets.
   Do not weaken worker-egress policy to make the provider reachable.
4. No credential is placed in the URL, UI response, prompt, event, or log. If the selected
   provider requires authentication, keep it in an OS-backed secret flow and prove that
   the broker can authenticate without returning the secret bytes to the WebView or Agent.
   Otherwise record that the provider is unauthenticated only on the owner-controlled
   local endpoint and document the residual local-machine threat.
5. Before any readiness/model-catalog implementation, choose explicit connect/read
   timeouts, response-header/body limits, model-count/name limits, JSON nesting limits,
   cancellation behavior, and sanitized error mapping. A hanging, oversized, malformed,
   or hostile response fails closed. Catalog results are display metadata only and do not
   prove inference entitlement or successful inference.
6. Run against synthetic code/document fixtures only. Do not send Workspace data until
   the normal Resource authorization, placement, and egress checks are integrated.

## Experiment matrix

Run the selected harness/provider combination on two recorded hardware profiles (one
CPU-only baseline and one supported accelerated profile if available). Record OS/build,
CPU, RAM, GPU/VRAM/driver, model digest/quantization/context settings, provider/harness
versions, and network state. Include a no-network run after model assets are present.

For each model/profile, exercise:

- bounded provider readiness and sanitized model-catalog discovery;
- first-token latency, total latency, throughput, peak RSS/VRAM, cold load and warm reuse;
- a small code explanation and a bounded repository edit using the native harness;
- tool use, file/worktree isolation, structured result parsing, and source citation where
  the selected harness supports them;
- cancellation during load, generation, and tool execution; verify actual process/provider
  stop behavior and no later writes;
- context near the configured limit, overflow rejection/truncation semantics, and a
  provider/model change requiring a fresh session;
- OOM, no GPU, insufficient memory, unavailable model, stalled stream, malformed response,
  oversized body/catalog, endpoint restart, and broker shutdown;
- explicit no-network behavior: no DNS/external fallback and no cloud substitution;
- quality against a prepared owner-reviewed oracle for coding and grounded document tasks.

## Required output

Create a sanitized report containing:

```text
selected or rejected provider/protocol/version
selected or rejected native harness/version
supported hardware/model matrix and known limitations
exact owner-registration and broker policy needed
readiness/catalog semantics and all configured resource limits
tool/context/cancel/resume behavior and evidence
quality, latency, RSS/VRAM and cold/warm measurements
secret/log/output inspection results
failure behavior and explicit no-fallback evidence
go/no-go recommendation for E06-S04
follow-up API/schema/events/UI/Environment contracts, if any
```

Do not claim parity with popular local-model applications without a user-defined task
corpus and measured results. Do not claim that catalog discovery is inference readiness.

## Exit criteria

**GO** only when a native harness successfully completes the declared local workflows on
both recorded hardware profiles, cancellation/containment is evidenced, provider access
passes the exact registration/broker policy, and the no-network case proves no external
fallback. A provider that passes catalog discovery but fails native tools/cancellation is
not a GO.

**BLOCKED** if the exact harness/provider protocol, authenticated endpoint binding,
process/resource controls, or supported hardware cannot be established. In that case,
keep the UI explicit that local inference is unavailable and continue with non-inference
features; do not create a generic model router or an unqualified HTTP adapter.
