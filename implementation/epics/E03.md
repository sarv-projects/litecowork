### OpenCode profile-probe qualification note — 2026-10-09

The profile projection now has focused tests for malformed/failed provider reads, bounded
provider/model lists, omission of native option objects, and strict rejection of obvious
credential/account-like IDs and display names. A failed attempted route is reported as
`UNKNOWN`; `NOT_PROBED` is reserved for a route that was not attempted. A reported
`/provider.connected` list remains explicitly separate from authentication, entitlement,
inference, session-model selection, and profile admission.

Local read-only check against `opencode v2.0.26` used a fresh temporary HOME/XDG tree,
started `opencode serve`, and made no session or inference request. The v2 `/api/provider`
and `/api/model` routes returned HTTP 200 JSON envelopes, while the probe's legacy
`/provider` and `/config/providers` paths returned the desktop HTML fallback (HTTP 200,
`text/html`). This observation motivated the version-aware adapter slice below.

### OpenCode V2 adapter correction — 2026-10-09

The profile probe now performs a bounded `--version` check and accepts only `2.0.26`, the
exact installed version whose route behavior was observed. It reads `/api/provider` and
`/api/model`; unsupported or mismatched versions stop before server startup and do not
fall back to legacy routes. V2 `data` envelopes are projected into bounded catalog IDs
and safe display names. Provider IDs remain catalog observations, separate from connected
providers, authentication, entitlement, and inference. Location paths, native provider/
model objects, options, headers, and raw responses are discarded. The probe remains
read-only and the Runtime offer remains incompatible.

The adapter transport now has V2-specific session creation, prompt, event-stream, and
interrupt routes. No Task or Conversation caller invokes them. Strict native output
projection, Trust authorization, a qualifying Environment, process-tree containment,
durable AgentSession binding, Effect reconciliation, and lease fencing remain production
blockers. No session or inference request was made for this change. Focused verification
passed: `cargo test --locked -p litecoworkd --bin litecoworkd opencode_ -- --nocapture`
(13 tests) covers version parsing/mismatch, V2 projection and sanitization, HTML/malformed
responses, timeout configuration, and response bounds. `cargo check --locked -p litecoworkd
--bin litecoworkd` also passed. The architecture and implementation-plan validators passed
with 141 typed events and 60 stories/5,317 coverage rows respectively. These checks do not
qualify a real provider/session or complete E03.

Planning-readiness cases cover required/current `If-Match`, stale Task races, Workspace/owner scoping, strict sanitized blocker parsing, rejection of extra/duplicate/unknown fields or any true execution flag, late-response suppression, and proof that no Task/event/session/plan/Attempt/lease/Environment/provider state is created.

**E03-S03-SYSTEM:** Execute the implementation using its actual process/transport/provider. Inject the listed failures at before-admission, after-persist and before-response boundaries where meaningful; assert durable/UI/authority truth after restart. Record OS/build/provider versions.

Current source has standalone Task creation, planner reservation/activation code paths,
and an initial-plan acceptance service/storage transaction. The concrete SQLite adapter
now rejects both planner reservation and activation with
`TASK_PLANNING_ISOLATION_UNAVAILABLE` before writing session/event/receipt state; this
closes direct internal admission until Runtime-owned isolation proof and the remaining
execution gates are integrated. The plan path validates
non-empty bounded steps, unique logical keys, dependency references/cycles, and acceptance
criterion shape; SQLite rechecks owner, Task version/spec/status, active lead planning
session, attached host and current ready Runtime incarnation, live endpoint binding, active
Workspace EXECUTOR binding, and enabled lead eligibility. It writes the immutable
PlanRevision/Steps, advances the Task pointer, appends the Task/Step snapshots/events, and
commits the idempotency receipt atomically. The RequestId digest binds the normalized typed
plan and producer session; live endpoint expiry is checked against storage admission time.
Read APIs for plan history and Steps are connected to the Operator API. SQLite v5 adds
PlanRevision immutability, Step identity protection, and Step deletion rejection.
Task input validation now deserializes each JSON value through the closed
`storage_core::PinnedResourceRef` shape before same-Workspace/revision/ContextDocument
checks; an unknown `path` property was observed accepted before the regression fix and is
now rejected. This guards Task creation and TaskSpec revision admission, but does not
resolve or stage Resource bytes.

This remains an unbuilt/untested source slice. It accepts only an initial plan from an
active `TASK_PLANNING` session; execution-produced replans are rejected until Attempt/lease
admission exists. The documented POST plan route is not yet wired to a producer-scoped
authentication context, and no agent tool invokes `submit_initial_plan`; do not let an
owner request body select a producer session or treat this as integrated planning. The
desktop composer now exposes a save-only standalone Task path through Tauri. It keeps the
Task in `READY`; when no current Plan exists, detail says “No accepted plan is currently
saved for this Task” without inferring that it has never been planned or executed. The Task
list uses the neutral “Ready” label because recovery may also return a Task to that state.
The owner may attach exact Resource revision references from the Library; these do not read
content or grant agent access. The composer does not expose planner or execution controls.
Task detail now loads the persisted current PlanRevision and materialized Step statuses
from the existing read routes, checks them against the Task's current-plan pointer and
logical keys, and labels a plan based on an older TaskSpec revision as stale. This is
presentation of existing state only; it does not start planning or create an Attempt.
Task detail keeps its objective/status summary visible and places timestamps, pinned
inputs, and validated persisted Plan/Step rows in a collapsed-by-default `Work details`
disclosure. Resource wording remains generic; expansion does not imply execution,
verification, or progress. This UI source slice remains unbuilt and untested.
Task detail now also exposes a narrowly scoped objective editor for a `READY` Task with no
accepted Plan. The Tauri command sends the current Task version and parent TaskSpec
revision with a stable idempotency key; the authenticated Operator route appends an
immutable revision through TaskService/SQLite and then the UI reloads current Task/Plan
state. Omitted spec fields remain inherited. This path rejects stale/planned Tasks and
starts no AgentSession, Plan, Step, Attempt, lease, Environment, or Invocation. F103
defines the commit/retry/race behavior and the deferred verification cases. PlanningCoordinator,
native adapter dispatch, scoped producer authentication, and the complete execution path
remain absent, so the story's acceptance criteria remain open.

Task detail now also offers an explicit read-only **Check readiness** diagnostic when no
PlanRevision is saved. It calls the authenticated `GET /v1/tasks/{id}/planning-readiness`
route with the loaded Task version and shows only translated typed blockers/time. The Tauri
bridge rejects stale/mismatched responses, unknown or duplicate blockers, extra fields,
and any response that claims dispatch/session/Plan creation. The UI states even a clear
preflight cannot start planning in this build. This diagnostic creates no durable records,
events, processes, provider calls, or execution authority. The slice is source-only and
unverified; F106 defines deferred failure, race, non-mutation, and accessibility coverage.

Task detail now has a compact, read-only TaskSpec history disclosure backed by the already
mounted authenticated `GET /v1/tasks/{id}/spec-revisions` route. The desktop bridge checks
Workspace/Task ownership, ordered positive revisions, parent pins, author identity, and
timestamps; the UI shows the exact revision, objective, creation time, author, and parent
revisions. It compares the returned history head with the loaded Task detail: newer history
is labeled “Latest saved” with a Task reload action, while incomplete/older history is
disclosed and never labels an older revision “Current.” It offers no restore or edit action
(F112). This source slice is unbuilt and unverified.

The current interim standalone desktop Task composer can send the selected legacy primary Coworker ID and
expected aggregate version; this is transitional Task-origin behavior, not the final ordinary chat default. The server pins its exact current revision and uses its
default lead before the Workspace fallback in the atomic Task create transaction. Task
detail is being extended to display the name from that exact immutable Coworker revision.
Source review also found a construction mismatch where the Coworker lead was resolved but
its default lead-failover policy was omitted from the initial TaskSpec. The server now
passes the policy snapshot into TaskService while SQLite rechecks the pinned Coworker
revision/version before commit. These changes remain unbuilt/unverified; planning dispatch,
Attempt execution, and provider admission are still unavailable.

The Codex App Server transport now offers a typed `read-only` thread constructor and a
structured-plan turn constructor with `type: readOnly` and `networkAccess: false`. This
closes only a protocol-shaping gap: the current policy does not restrict reads to selected
Resource roots, so it must only run inside an externally isolated Task-specific Environment.
It does not prove Environment identity, disable native MCP/app tools, route a plan through
PlanningCoordinator, or establish descendant-process containment. Do not expose a Start
planning control or accept Tasks through this path until those remaining admission and
recovery boundaries are implemented and the installed Codex protocol version is qualified.
Deferred verification must cover the emitted sandbox payload, path rejection cases,
structured-output parsing, native capability denial, and durable session crash/restart
boundaries.

**Additional source slice (unverified):** Added reusable
