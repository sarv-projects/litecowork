### Native inventory candidate selection — 2026-10-20

The bounded local inventory now selects the same CLI candidate in both inventory paths
and keeps the output of a CLI that exits immediately.

The version probe polled the child's stdout nonblocking and then checked whether the
child had exited. A CLI that wrote its version and exited between those two steps left
its output unread in the pipe, so the probe projected an empty output and reported
`VersionUnavailable` for an installed, working agent. The failure is scheduling
dependent: it appears in a fully parallel daemon run and not in an isolated run. The
probe now drains the remaining pipe bytes after the child has exited and before the
version is projected; the bounded output limit and the timeout refusal are unchanged.

The npm-package fast path and the `--version` probe also disagreed about which PATH
candidate wins: the fast path skipped a PATH entry that exists but cannot be executed,
while the probe stopped at that entry and reported `VersionUnavailable` for an agent
that would actually run. Both now skip an existing-but-unusable PATH entry, matching the
shell's own lookup order, and the Cline npm fast path uses the same file and
execute-bit rule as the probe, so the inventory can no longer describe a different
binary than the one a launch would execute. An unrelated executable named `cline`
earlier on `PATH` is therefore reported with its own version instead of a version that
belongs to a different file.

The isolated inventory cases also use a per-process counter in their temporary directory
name. A clock-derived name alone can collide when two concurrent cases sample the same
instant, which let one case overwrite the other's fixture and produce nondeterministic
failures.

Focused verification: `cargo test --locked --offline --jobs 2 -p litecoworkd --bin
litecoworkd -- agents::` — **88 passed; 0 failed; 1 ignored** (407 filtered). The
inventory still observes installation only: it never establishes authentication,
entitlement, session readiness, or lead eligibility.

### Conversation AgentBinding selection resolution — 2026-10-20

The ordinary Conversation submit route now resolves the admitted AgentBinding selection
that the accepted contract already defines instead of depending on an unserved pin. The
resolution is the explicit Conversation override first, then the Workspace default, and
the first configured selection is authoritative: a missing or ineligible selection is
refused with `422 AGENT_UNAVAILABLE` and persists no message, turn, event, receipt, or
Conversation version bump. The resolution and the eligibility recheck happen inside the
authoritative SQLite turn transaction, so a race between the route read and the commit
cannot admit an ineligible binding. The `conversation.turn.created.v2` payload records the
binding the turn was admitted against, and the Conversation aggregate keeps its own
override so a later Workspace default change still reaches newly admitted turns.

With a Workspace default configured, the production path now reaches the proven durable
turn plus failure-settlement behavior: the USER message and OPEN turn commit, the
unavailable native admission settles the same turn `FAILED`, and the route answers
`503 DEPENDENCY_UNAVAILABLE` with `no-store` instead of pretending the message was sent.
The former HTTP 202 branch that marked a turn RUNNING from online Runtime/EXECUTOR
inventory alone was removed. A route regression seeds an ONLINE/READY Runtime and confirms
503 plus no AgentSession when no native supervisor exists. Provider-backed
AgentSession reservation/readiness, dispatch, streaming, cancel/retry, the documented
202 ConversationTurnReceipt, a served route that pins a Conversation-level override,
packaged/system acceptance, and owner USER acceptance remain open. The exact-replay path still requires a
configured selection to exist at replay time, because the route resolves the selection
before the storage receipt lookup; that limitation is recorded in the
[`E03-S02 review`](../reviews/E03-S02.md).

### Native Conversation admission remains fail-closed - 2026-10-25

The submit handler no longer treats a live Runtime endpoint as a running native session.
A READY Runtime incarnation, an EXECUTOR Workspace binding, and an unexpired endpoint
binding prove inventory availability only. The current Operator has no Conversation
session supervisor connected to the staged Codex/OpenCode transports, so it must save the
user message, settle the turn FAILED, and return 503 DEPENDENCY_UNAVAILABLE; it must not
create agent.session.starting.v1, set ConversationTurn.RUNNING, or return 202.

A source audit also found that turn creation and the former admission transaction reused
the public Idempotency-Key with different canonical payloads. SQLite rejected admission
on its request-digest check, masking the unsafe 202 branch on the ordinary route. A red
regression step using a distinct internal key made that branch reachable and observed
202; the production branch and its unused receipt/session helpers were then removed.
Any future admission implementation needs a distinct stable internal idempotency identity,
a real adapter readiness handshake, permission handling, and a separate activation step.

The new route regression independently verifies that storage can resolve an eligible
Runtime host while the served route still returns 503, leaves the turn FAILED, emits no
session-start event, and creates no AgentSession/Task/Attempt/lease/Environment. This does
not qualify a provider or complete E03-S02. The low-level storage admission transaction
still needs to be split or guarded by the future supervisor/readiness contract before any
production caller is added.

**Plan-submission route stays unserved by contract.** `docs/API.md` states that the
`POST /v1/tasks/{id}/plan-revisions` contract "is specified but the current Operator
router does not expose it yet" and that "until the trusted agent-session gateway supplies
that context, the route must not be wired to accept a body-supplied producer ID". Wiring
the route from an owner credential would let a caller name a producer it does not own, so
the route is deliberately not served. The remaining precondition is a producer-scoped
authentication context derived from the current lead's active `TASK_PLANNING` AgentSession
or a current lead execution Attempt's active AgentSession and valid lease, plus the
Runtime-owned isolation attestation described below.

**Planning isolation seam for E07.** The storage boundary still refuses planner
reservation and activation with `TASK_PLANNING_ISOLATION_UNAVAILABLE` before any
session, event, or receipt write. The exact seam is
`require_task_planning_isolation_admission()` in
[`crates/storage-sqlite/src/lib.rs`](../../crates/storage-sqlite/src/lib.rs), called as
the first statement of `AgentSessionStore::start_task_planning_session` and
`AgentSessionStore::activate_task_planning_session`. To open it, E07 must supply a
verifier that the two storage methods call with an `IsolationAdmissionRequest`
(`environment_id`, `workspace_id`, `task_id`, `runtime_id`, `runtime_incarnation_id`,
`normalized_policy_digest`, `pinned_input_set_digest`, `readable_root_set_digest`,
`writable_root_set_digest`, `now_ms`) and that resolves against the incarnation-scoped
`RuntimeLocalIsolationStore` attestation through
`evaluate_isolation_admission()`. The attestation is Runtime-local, private, and must never
become a domain event, aggregate snapshot, backup, projection, or Agent prompt, so it
cannot be persisted as a column; it has to be rechecked inside the same write
transaction. The gate must not be weakened to a warning, a flag, or an optional check.

**Safety prerequisite source slice:** Codex profile diagnostics now include a separate
Conversation-turn eligibility result, fail-closed over six explicit controls: restricted
