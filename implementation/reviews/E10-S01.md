## Acceptance facts proved by code

- **App cannot steal Operator credentials.** The frame's sandbox attribute is exactly
  `allow-scripts`; it never contains `allow-same-origin`, forms, popups, downloads, or
  top navigation. The bridge message guard refuses any payload whose key is a
  credential-shaped name (`authorization`, `access_token`, `api_key`, `client_secret`,
  `cookie`, `credential`, `credentials`, `password`, `refresh_token`, `secret`) at any
  depth, and refuses a payload above the 64 KiB bound. The frame never receives an
  Operator credential: the only secret it gets is its own per-frame nonce.
- **Exact-origin transport only.** The bridge guard compares the message origin to the
  host-assigned frame origin with string equality, and compares the nonce to the
  host-issued per-frame nonce. The origin is assigned by the host
  (`app_frame_origin`), never taken from the request body, so a client cannot claim
  another App's origin.
- **Install metadata is not authority.** A `DiscoverCatalogEntry` has
  `authoritative: false` and the storage validator rejects any entry that claims
  authority. The `grants_required` list carries names only. The catalog row's
  availability is derived from the *observed* install/auth/compatibility state, and an
  unknown state is an error, never "available".
- **Incompatible option disabled.** `derive_discover_availability` fails closed:
  an unqualified provider outranks every other state, an incompatible entry is
  `UNSUPPORTED`, and an unknown install or auth state is `ERROR`. The desktop
  projection disables every row whose availability is not `AVAILABLE`.

## Known limitations and pending gates

- **LiteSPM package path is blocked.** `docs/CAPABILITY-FABRIC.md` line 51 publishes
  only the service base URL and states that "the LiteSPM API, authentication,
  manifests, package taxonomy, plugin composition, MCP discovery, installation,
  update, and upstream process/health operations are intentionally deferred to
  LiteSPM's own authority". The Discover catalog therefore reports
  `package_service_qualified = false` with reason
  `LITESPM_PACKAGE_SERVICE_NOT_QUALIFIED`, `connect-or-install` returns
  `DEPENDENCY_UNAVAILABLE`, and `capabilities/{id}/test` returns health `UNKNOWN`
  without contacting any provider. No LiteSPM endpoint, method, authentication, or
  package schema was invented. **The document line that must be published** is the
  LiteSPM package API/authentication/manifest section of
  `docs/CAPABILITY-FABRIC.md` (currently the paragraph beginning "This architecture
  records the service selection and system boundary only.").
- **The MCP App frame is issued, not rendered.** `POST /v1/mcp-apps/frames` resolves
  the App's server identity, resource URI, and content digest from the MCP capability
  host this Runtime already observes. It fetches no App bytes and renders no iframe:
  a qualified browser App host is a separate slice. The route returns the sandbox
  contract and the host-issued nonce so that host can render the frame.
- **No qualified MCP provider is observed in this Runtime**, so the frame route
  reports `DEPENDENCY_UNAVAILABLE` with reason `MCP_PROVIDER_NOT_OBSERVED` until one
  is. That is the truthful state, not a failure.
- **USER acceptance is pending.** Rendering a real compatible MCP App and denying an
  out-of-scope tool action needs a qualified MCP App host and the owner. It was not
  claimed.

## Rollback

Every route is additive and the aggregates are stored in the shared projection, so
removing `apps/litecoworkd/src/skill_operator.rs`'s route registrations and
`apps/litecoworkd/src/discover_operator.rs` reverts the served surface without a
schema change. The OpenAPI additions revert with the same commit. No data migration
is involved, so no rollback migration is required.

## Telemetry

The new routes emit no telemetry of their own. The `MCP_APP_FRAME_ISSUED`,
`SKILL_REVISION_COMMITTED`, and `SKILL_PROPOSAL_REVIEWED` audit records carry only
IDs and reason codes, never content, digests of secret bytes, or credentials.
