# E13-S02 — Performance/soak and resilience (review packet)

Story / child story IDs: `E13-S02` (epic `E13`, gate `G3`).

Commit and base: working tree on `main` at base `0b98c21`.

Outcome and touched modules:

- `scripts/v1_soak_harness.py` (**new**) — a bounded, deterministic local soak
  harness. It builds a **real** LiteCowork store from the repository's own
  schema files (`docs/schemas/sqlite-v1.sql` … `sqlite-v26.sql`), drives a
  seeded workload, restarts the store on a fixed cadence, truncates the
  write-ahead log on a fixed cadence and asserts that the on-disk footprint
  stays inside a declared bound.
- `scripts/v1_resilience_matrix.py` (**new**) — the fault matrix. Every row is
  executed by the script; a row is `PASSED` only when the probe ran here and
  the expected durable truth was observed.
- `scripts/v1_store_probe.py` (**new**) — the shared store builder the two
  scripts use, so both measure the shipped schema.
- `crates/storage-sqlite/src/backup.rs` — the storage-level resilience
  behaviour (partial restore, live-daemon restore refusal, corrupt archive
  refusal) is proven by the `backup::` suite.

Contract / API / event / schema references:

- Contract authority: `docs/BENCHMARKS.md`, `docs/TESTING.md`,
  `docs/FAILURE-RECOVERY.md`, `docs/OBSERVABILITY.md`, `docs/STORAGE.md`.
- **No schema change, no event change, no API change.** The harness reads the
  repository schema; it does not write one.

- Expected: the footprint stays inside `--max-bytes-per-iteration` (64 KiB per

Known limitations, cost and measured performance:

1. The measured latencies are **SQLite write latencies on the shipped schema**,
   not the end-to-end Core latencies the release gate asks for. The Core and
   provider latency separation cannot be measured here because the daemon does
   not start on this host (no OS credential store — see E13-S01).
2. The soak harness runs the store **single writer**. It does not exercise the
   concurrent writer queue, the provider circuit, the retrieval path or the
   native agent, so "many installed idle providers" and "provider circuit
   storm" are **NOT RUN**.
3. The million-row Task case is **NOT RUN**: the harness writes eight domain
   events per iteration, which is a different shape from a single Task with a
   million rows.
4. The numbers above are a **first baseline**, not a frozen SLO. The SLOs in
   `docs/BENCHMARKS.md` still have to be frozen by the owner; the harness
   reports the measurement so the SLO can be derived from a real run.
5. The harness does not currently assert a *latency* regression gate; it
   asserts the footprint bound and the integrity of the store.

Upgrade / rollback / demo instructions: re-run the two commands above with the
same `--seed` to reproduce the measurement. The harness never writes outside
`--state-dir` (or a temporary directory it removes afterwards).
