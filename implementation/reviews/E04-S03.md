# E04-S03 — Invocation reconciliation CODE review packet

Status: **PARTIAL.** This packet records durable terminal reconciliation for already-existing
`AMBIGUOUS` CapabilityInvocations and owner-scoped read-only Operator projections. It does
not implement Invocation creation, dispatch admission, Effect admission, provider execution,
or a qualified provider adapter.

## Implemented behavior

- Generic Invocation transitions cannot leave `AMBIGUOUS`; only the typed reconciliation
  operation accepts a terminal provider observation.
- The internal SQLite port requires an authorized Runtime/incarnation, exact Workspace and
  Invocation, matching immutable request digest, and provider identity matching the host
  instance bound to the Invocation's Activation.
- The result is version-checked and commits normalized provider terminal status, observed
  time, aggregate state reference, status event, and exact idempotency receipt in one SQLite
  transaction. Identical retries replay; changed content under the request ID conflicts.
- Event payloads include only the observation source, provider identity digest, and observed
  time. Provider handles, raw responses, and credentials are not recorded.
- Authenticated, no-store Operator GET routes expose one Invocation or bounded descending
  Task history. The SQLite read port checks Workspace ownership and Task membership,
  returns a stable `(created_at, invocation_id)` keyset page, and hides foreign Workspace
  ownership as not-found. Opaque provider handles and raw output are omitted from the
  public projection. The continuation cursor is versioned and bound to its Workspace and
  Task. `FailureRecord.details` is also omitted because the schema permits arbitrary nested
  values there; only its typed summary fields are projected. These read routes do not expose
  reconciliation or provider dispatch.
- Storage verifies the Runtime actor and activation-to-host identity but does not
  independently authenticate the external provider response. Only a trusted adapter that
  authenticates and correlates provider state may call the internal reconciliation port.

## 2026-10-20 — combined Trust + ApprovalUse + Invocation + Effect admission

### Implemented behavior

One authoritative SQLite transaction now admits a consequential dispatch. It is the internal
`CapabilityDispatchStore::admit_capability_dispatch` port; no Operator route exposes it and
the Broker is its only intended caller.

Inside a single transaction the adapter:

1. authorizes the Runtime incarnation in the Workspace (`authorize_runtime`);
2. resolves the exact idempotency receipt (identical retry replays, changed content under the
   same request identity is `IdempotencyConflict`);
3. loads the Invocation and requires `CREATED`, the expected version, no linked Effect, and
   `ATTEMPT_EXECUTION` scope — an Effect is only admissible inside an admitted Attempt;
4. loads the Effect and requires `PROPOSED`, the expected version, and matching
   Invocation/Task/Attempt/request-digest/execution-method/operation provenance;
5. re-checks live owner/lease authority through the schema's
   `live_agent_session_invocation_authority` view (AgentSession, Attempt, Step, PlanRevision,
   Task and ACTIVE ExecutionLease must still own execution authority);
6. re-checks the CapabilityGrant (ACTIVE, same scope and capability identity, operation
   allowed, not expired) and the CapabilityActivation (ACTIVE, same scope and capability
   identity, same Runtime/incarnation);
7. re-checks the Core Trust decision: it must be `ALLOW` or `REQUIRE_APPROVAL`, and must name
   this request digest, grant, activation, Effect, scope digest and action digest. `DENY` and
   every mismatched binding are rejected before any write;
8. re-checks the exact Approval: `APPROVED`, same Task and Attempt, not expired, and the
   recomputed approved action binding (task, attempt, operation, capability identity, target
   digest, execution method, Effect and scope digest) must equal the persisted
   `action_digest`. The binding is recomputed from persisted rows, so a summary, request id or
   similar description can never satisfy it;
9. appends exactly one immutable `ApprovalUse` naming the Effect. A second use of the same
   Approval is rejected as `APPROVAL_ALREADY_CONSUMED`;
10. transitions the Invocation to `DISPATCHED` and links the Effect, transitions the Effect
    `PROPOSED -> STARTED` with the next dispatch ordinal, and commits the three domain events
    (`capability.invocation.status.changed.v1`, `effect.started.v1`,
    `approval.use.consumed.v1`), the Invocation/Effect/ApprovalUse aggregate-state blobs and
    snapshots, the redacted audit record and the idempotency receipt together.

A rejected admission writes nothing: no Effect start, no `ApprovalUse`, no event, no audit
record and no receipt. The audit record keeps only identifiers and digests; no target
plaintext, provider handle or secret bytes are recorded.

### Lead-owned DDL required to enable this boundary

`docs/schemas/sqlite-v15.sql` still closes Invocation creation and the first dispatch:

```sql
CREATE TRIGGER capability_invocation_creation_admission_closed
BEFORE INSERT ON capability_invocations
BEGIN
  SELECT RAISE(ABORT, 'INVOCATION_CREATION_ADMISSION_UNAVAILABLE');
END;
```

and `capability_invocation_status_transition_guard` rejects `NEW.status = 'DISPATCHED'`.
The schema already carries the real admission rules (`capability_invocation_admission_matches_scope`
and `capability_invocation_first_dispatch_revalidates_owner`), so the required migration only
has to replace those two guards. Exact DDL for the lead (a new `docs/schemas/sqlite-v26.sql`,
applied by the integration owner — this slice adds no migration):

```sql
DROP TRIGGER capability_invocation_creation_admission_closed;
DROP TRIGGER capability_invocation_status_transition_guard;

CREATE TRIGGER capability_invocation_status_transition_guard
BEFORE UPDATE OF status, version ON capability_invocations
WHEN NEW.version <> OLD.version + 1
  OR NOT (
    (OLD.status = 'CREATED' AND NEW.status IN ('DISPATCHED', 'CANCELLED'))
    OR (OLD.status = 'DISPATCHED' AND NEW.status IN ('SUCCEEDED', 'FAILED', 'WAITING', 'INPUT_REQUIRED', 'CANCEL_REQUESTED', 'AMBIGUOUS'))
    OR (OLD.status = 'WAITING' AND NEW.status IN ('INPUT_REQUIRED', 'CANCEL_REQUESTED', 'AMBIGUOUS'))
    OR (OLD.status = 'INPUT_REQUIRED' AND NEW.status IN ('WAITING', 'CANCEL_REQUESTED', 'AMBIGUOUS'))
    OR (OLD.status = 'CANCEL_REQUESTED' AND NEW.status IN ('CANCELLED', 'SUCCEEDED', 'FAILED', 'AMBIGUOUS'))
    OR (OLD.status = 'AMBIGUOUS' AND NEW.status IN ('WAITING', 'INPUT_REQUIRED', 'CANCEL_REQUESTED', 'SUCCEEDED', 'FAILED', 'CANCELLED'))
  )
BEGIN
  SELECT RAISE(ABORT, 'CAPABILITY_INVOCATION_TRANSITION_INVALID');
END;
```

Until the integration owner applies that migration the boundary stays unreachable in
production: the shipped schema rejects every Invocation row, and the CODE fixture applies the
proposed DDL to the fixture database only.

## Lead-applied `sqlite-v26.sql` migration — 2026-10-20

The lead applied the migration this story asked for, and strengthened it beyond the original
request so that removing the version fifteen creation block cannot open a bypass.

`docs/schemas/sqlite-v26.sql` now does three things:

1. **Drops `capability_invocation_creation_admission_closed`.** The blanket block that
   aborted every `capability_invocations` INSERT is gone, so the combined Trust, ApprovalUse,
   Invocation and Effect writer can create an Invocation.
2. **Re-creates `capability_invocation_status_transition_guard`** with the same version rule
   and the same transition table as version fifteen, plus exactly one addition:
   `CREATED` may now advance to `DISPATCHED`.
3. **Adds `capability_invocation_dispatch_requires_consumed_approval`**, which is new and was
   not in the originally requested DDL. A dispatch is refused unless the exact `Effect` being
   dispatched is already bound to an `approval_uses` row whose approval is `APPROVED` for the
   same Task.

Point three is the reason the migration is safe. Without it, dropping the blanket block
would have let the direct status-transition writer advance an Invocation to `DISPATCHED` on
its own, whenever the version one live-authority triggers happened to be satisfied — that is,
without the Trust decision and without the ApprovalUse. The new guard closes that path at the
database boundary. The combined writer records the `ApprovalUse` in the same transaction
*before* it advances the Invocation, so the guard observes it; the writer's statement order
in `crates/storage-sqlite/src/capability_dispatch.rs` was changed for exactly that reason.

Admission is not thereby opened. The version one boundary triggers remain in force and still
reject an unauthorized Invocation at the database:

- `capability_invocation_admission_matches_scope` — a live `ACTIVE` agent session in the
  `live_agent_session_invocation_authority` view, an `ACTIVE` and unexpired capability grant
  with a matching scope, capability identity and an allowed operation, and an `ACTIVE`
  capability activation bound to the same workspace, scope and runtime incarnation;
- `capability_invocation_identity_immutable` — the admitted identity columns stay immutable;
- `capability_invocation_first_dispatch_revalidates_owner` — a dispatch is revalidated against
  live session, grant and activation authority.

Schema version moved from 25 to 26, with the usual migration record, fingerprint verification
and `Failpoint::DuringV26Migration` interruption point.

Two existing storage tests were updated to the new boundary rather than weakened:

- `sqlite_trigger_rejects_invocation_creation_until_combined_admission_exists` is now
  `sqlite_trigger_rejects_invocation_creation_without_live_authorized_authority` and asserts
  the version one message `INVOCATION_SCOPE_OR_AUTHORIZATION_MISMATCH` — the combined
  admission now exists, so the blanket-creation reason no longer applies, and the
  authorization reason is the one that is actually enforced;
- `sqlite_trigger_rejects_direct_status_rewrite_and_dispatch` now additionally asserts the
  dispatch refusal reason, accepting either the new consumed-approval refusal or the
  live-authority refusal, so it states the actual boundary instead of a superseded one.

`crates/storage-sqlite/src/capability_dispatch.rs` no longer patches the schema in its test
fixture. The fixture now asserts that the **shipped** schema carries
`capability_invocation_dispatch_requires_consumed_approval` and that the blanket creation
block is absent, so the production schema is the thing under test.

`.venv/bin/python scripts/validate_architecture.py` passes with the new schema file and the
rewritten OpenAPI projection.
