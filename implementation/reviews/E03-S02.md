## Contract and behavior

The accepted API contract in [API](../../docs/API.md) requires an owner-scoped
`Idempotency-Key`; a create atomically commits the Conversation, event, aggregate-state
reference, and receipt. A 4xx rejection commits none of those records. The desktop now
persists an unresolved `(Workspace, RequestId, normalized title)` in a bounded Tauri
app-data journal before POST. Unix permissions are validated by the journal; Windows uses
inherited app-data ACLs that have not yet been qualified. It restores and retries the exact identity, and
acknowledges only after the UI validates the response. A confirmed 4xx or a local
operator-client initialization failure before POST clears that exact journal row. A
transport error, 5xx, malformed success, or acknowledgement failure keeps it retryable.
Workspace and mounted-instance fences prevent late responses from changing another
Workspace's view.

## Windows journal replacement CODE slice — 2026-10-16

The journal now routes Windows replacement through the existing safe wrapper in
`windows-local-security`. It flushes the newly written same-directory temporary file before
calling `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`; it does not
allow cross-volume copy/delete fallback. A failed move returns the generic journal commit
error, and the Tauri bridge does not initialize the Operator client or issue POST until
`journal.record` succeeds. Unix continues to use rename followed by parent-directory sync.

The Windows helper has tests for creating/replacing exact bytes and preserving the prior
destination on a failed replacement. They compile for the Windows GNU target but were not
executed on this Linux host. `MOVEFILE_WRITE_THROUGH` is the documented operation requested
here; the cited API documentation does not establish that this same-volume rename survives
a sudden power loss. The journal's Windows directory and temporary-file access controls are
inherited from the Tauri app-data directory; this ACL boundary has not been verified on
Windows, so no Windows owner-only/private permission claim is made.

Environment: Linux WSL2 x86_64; Rust/Cargo `1.98.1`.

```sh
cargo test --locked -p windows-local-security
cargo check --locked --target x86_64-pc-windows-gnu -p windows-local-security --tests
cargo clippy --locked --target x86_64-pc-windows-gnu -p windows-local-security --all-targets -- -D warnings
cargo test --manifest-path apps/litecowork-ui/src-tauri/Cargo.toml --lib conversation_create_journal -- --nocapture --test-threads=1
```

Observed results: helper Linux tests **5/5**; Windows target helper tests cross-compiled; strict
Windows target helper Clippy passed; Linux Tauri journal tests **11/11**. The full Tauri
Windows target check first found the repository's missing `icons/icon.ico`; a retry used a
temporary ICO derived from the tracked PNG and then stopped because
`x86_64-w64-mingw32-windres` is unavailable. The temporary ICO was removed. This check does
not compile the full Tauri Windows caller. No Win32 operation was executed on Windows.
Actual Windows replacement/failure, journal reopen across a real application restart,
inherited ACL, packaged SYSTEM, power-loss, and owner USER acceptance remain pending.
Microsoft reference: [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).
