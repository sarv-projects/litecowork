## Contract and behavior

The accepted API contract in [API](../../docs/API.md) requires an owner-scoped
`Idempotency-Key`; a create atomically commits the Conversation, event, aggregate-state
reference, and receipt. A 4xx rejection commits none of those records. The desktop now
persists an unresolved `(Workspace, RequestId, normalized title)` in a bounded Tauri
app-data journal before POST. Unix permissions are validated by the journal; Windows uses
inherited app-data ACLs that have not yet been qualified. It restores and retries the exact identity, and
acknowledges only after the UI validates the response. A confirmed 4xx or a local
operator-client initialization failure before POST clears that exact journal row. A
transport error, 5xx, malformed success, or acknowledgement failure keeps it retryable.
Workspace and mounted-instance fences prevent late responses from changing another
Workspace's view.

## Durable turn-before-dispatch CODE slice — 2026-10-20

Ordinary Conversation submit now makes the authenticated USER message and its
`ConversationTurn` durable before any admission attempt, while native agent dispatch stays
closed. This is a partial CODE slice only; E03-S02 remains `PLANNED`.

Behavior served by `POST /v1/conversations/{id}/turns`:

- The route validates the bounded body, resolves the owner-scoped Conversation, and reads
  its already-pinned `active_agent_binding_id`. A Conversation without an enabled,
  lead-eligible pinned binding returns `422 AGENT_UNAVAILABLE` and commits nothing, matching
  [API](../../docs/API.md#conversations). A body `agent_binding_id` is compared for identity
  only; it never writes the Conversation selection.
- Entity IDs are derived from the authenticated principal and `Idempotency-Key`
  (`idempotent_id`), so an exact retry rebuilds the same canonical request payload instead
  of conflicting on freshly generated IDs.
- The USER `ConversationMessage`, OPEN `ConversationTurn`, Conversation version bump,
  `conversation.message.added.v1`, `conversation.turn.created.v2`, and the idempotency
  receipt commit in the existing `CreateConversationTurnCommit` SQLite transaction. No SQL
  was duplicated.
- The handler then asks the authoritative storage transition gate to start admission
  (`TurnCommand::Start`). The gate still refuses with
  `CONVERSATION_SESSION_ADMISSION_UNAVAILABLE`. Only that exact typed reason triggers a
  second SQLite transaction that settles the same turn `OPEN -> FAILED` with
  `conversation.turn.settled.v1` and the same reason code in `reason_code`; no OPEN turn is
  stranded on the normal path. If that settlement transaction itself fails, the route
  returns `500` (retryable) rather than a false unavailable claim; an exact retry resolves
  the receipt and re-attempts the settlement. The response is `503 DEPENDENCY_UNAVAILABLE`
  with `Cache-Control: no-store` and states that the message was saved but not sent to an
  agent.
- Exact replay resolves the stored receipt before aggregate writes and returns the same
  unavailable outcome without adding a message, turn, event, or receipt. A reused key with
  changed content returns `409 CONFLICT`. Replay never returns the stored OPEN snapshot as
  if it were current: the admission CAS detects the later turn version.
- `conversations.active_agent_binding_id` is never set from caller input, and
  `CONVERSATION_SESSION_ADMISSION_UNAVAILABLE` remains the storage gate's decision. The
  shared reason and event-revision strings are now constants in `storage-core`.

Storage transaction change: `create_conversation_turn` previously wrote the turn aggregate
blob before the receipt lookup. The blob write now happens inside the serialized
transaction after the replay check, so an exact replay performs no BlobStore write and
cannot leave an unreferenced snapshot with a fresh candidate timestamp.

## Conversation AgentBinding selection resolution — 2026-10-20

The ordinary Conversation submit route no longer depends on an unserved pin. It now
resolves the admitted AgentBinding selection that the accepted contract already defines,
and the durable turn plus failure-settlement path is reachable in production.

### Contract

- [API](../../docs/API.md#conversations): "`POST /v1/conversations/{id}/turns` first
  resolves and checks the Conversation override or Workspace default AgentBinding/endpoint.
  If none is eligible, it returns `AGENT_UNAVAILABLE` and persists no message or turn."
- [API](../../docs/API.md#workspaces): "The user enables a discovered AgentBinding, then sets
  an enabled, lead-eligible binding as the Workspace default. A Conversation may select an
  enabled, lead-eligible binding override; when absent, new Conversation turns use the
  Workspace default." and "The first configured selection is authoritative."
- [FLOWS](../../docs/FLOWS.md): "an explicit Conversation override or Workspace default is
  selected... First configured binding must be eligible, enabled and compatible; never skip
  an invalid selection to a different provider. Without an eligible binding, retain draft
  and request setup before persisting a turn."
- [DATA-MODEL](../../docs/DATA-MODEL.md): "Workspace has at most one default enabled
  AgentBinding; a Conversation may override it. Changing the default affects newly admitted
  Conversation turns and Tasks only... every ConversationTurn records its chosen
  AgentBinding... Missing or disabled selection fails admission with `AGENT_UNAVAILABLE`; the
  user draft remains available and no partially admitted turn or Task is created."
- [SERVICES](../../docs/SERVICES.md): "`submit_turn` first resolves and rechecks an enabled
  compatible AgentBinding/endpoint. If none is eligible, it returns `AGENT_UNAVAILABLE`
  before persisting a message or turn."

### Changed paths

- `crates/storage-sqlite/src/conversations.rs` — `create_conversation_turn` resolves the
  selection inside the authoritative transaction: the Conversation's own
  `active_agent_binding_id` override first, then `workspaces.default_agent_binding_id`. The
  resolved binding must be `enabled=1 AND lead_eligible=1` in the same Workspace, and the
  `conversation.turn.created.v2` payload must carry that exact binding. A missing or
  ineligible selection returns `AGENT_UNAVAILABLE` and rolls the whole transaction back, so
  no message, turn, event, receipt, or Conversation version bump survives. The Conversation
  aggregate snapshot now records the Conversation's own override instead of the resolved
  binding, so a later Workspace default change still reaches newly admitted turns instead
  of being frozen by a snapshot.
- `apps/litecoworkd/src/conversation_operator.rs` — the route resolves the same selection
  before it writes anything and refuses a missing selection with `422 AGENT_UNAVAILABLE`.
  The caller's `agent_binding_id` is still compared for identity only; it never rewrites the
  Conversation and never overrides the resolved selection.
- `crates/storage-sqlite/src/conversation_turn_tests.rs` and
  `apps/litecoworkd/src/conversation_operator_tests.rs` — new fixtures and cases.

## Native session readiness guard and idempotency masking - 2026-10-25

**Status:** Safety-boundary remediation only. E03-S02 remains PLANNED; this does not
implement or qualify native dispatch, streaming, permission mediation, reconnect, cancel,
retry, or packaged/system/USER acceptance.

### Finding

The former submit route had a branch that resolved an ONLINE Runtime with a READY
incarnation and EXECUTOR Workspace entitlement, wrote an AgentSession as STARTING,
changed the Conversation turn from OPEN to RUNNING, and returned HTTP 202 without
calling a native adapter or observing SESSION_READY. ConversationApiState has no
session supervisor, and the staged Codex/OpenCode transports are not wired into ordinary
Conversation submission.

The branch was masked by an idempotency-key collision: turn creation wrote
request_dedup(principal_id, public Idempotency-Key) for
conversation.turn.create.v1, and admission reused the same key for a different
conversation.turn.admit.v1 digest. SQLite returned a digest conflict before session
insertion. A temporary red-test step used a distinct internal admission key and reproduced
the false 202 on the ready-host fixture. The production admission branch and its unused
receipt/session response helpers were removed rather than making that unsafe branch
reachable. A future implementation must use a stable internal receipt namespace and wait
for real adapter readiness before activation.

### Changed paths

- apps/litecoworkd/src/conversation_operator.rs - removes the inventory-only host
  admission and 202 RUNNING response; keeps durable message creation and failure
  settlement while no supervisor is connected.
- apps/litecoworkd/src/conversation_operator_tests.rs - adds an ONLINE/READY Runtime,
  active EXECUTOR enrollment, live endpoint binding, and a test assertion that storage
  resolves this host while the HTTP route still fails closed.
- implementation/epics/E03.md, implementation/backlog.json,
  implementation/CURRENT-RUN.md, and docs/NATIVE-COMPOSER-LLD.md - record the verified
  safety boundary and remaining E03-S02 work.

insert a STARTING session and move a turn to RUNNING based on database inventory when

probe; native prompt schema, per-session permission behavior, permission requests/replies,
