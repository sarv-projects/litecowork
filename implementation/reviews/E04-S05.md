# E04-S05 — Artifact/Evidence/verifier completion review packet

Status: **PARTIAL — CODE PRESENT and focused CODE tests pass; SYSTEM and USER
acceptance remain pending.** This packet records the verifier Evidence settlement
slice implemented in SQLite. It does not claim the full E04-S05 scope is complete.

## Implemented behavior

- An authenticated verifier settlement that passes a VerificationRun must include at
  least one Evidence record, and the requested evidence refs must exactly equal those
  Evidence IDs. Failed and inconclusive runs require a typed failure code and cannot
  attach Evidence.
- Each Evidence record is validated against the pinned VerificationRun: exact Task,
  verifier service identity, subject/input reference, `VERIFIED` level, and run
  identity. A caller cannot attach the record to a different run.
- A passing VerificationRun, its `VERIFIED` Evidence, the Evidence-created events,
  the run-completed event, and the idempotency receipt commit in one SQLite
  transaction. The existing SQLite v22 guards independently reject a pass without
  same-run Evidence.
- Runtime Evidence admission remains limited to `REPORTED`; Runtime callers cannot
  set a verifier run identity or self-attach to a passed run.
- Non-cancelled VerificationRun start and settlement now require each pinned subject
  Resource revision to remain the exact unique current head in the same Workspace.
  If a source moves after a run starts, the verifier cannot settle it as PASSED and
  emit VERIFIED Evidence for that stale subject. Cancelled runs may still close against
  the immutable revision they originally pinned. The Effect VERIFIED gate independently
  repeats current-subject freshness checks before accepting run-bound Evidence.
- VerificationRun dependency edges now cover both input refs and declared subject refs,
  deduplicating a Resource revision that appears in both lists. Resource changes can
  therefore project stale/conflicted freshness for all declared verifier dependencies.
- The production `ArtifactVersionWriteStore` managed-text append path is exercised through
  the real SQLite writer and BlobStore. It advances the backing Resource head before the
  Artifact content version, returns Resource then Artifact events, and resolves an exact
  retry to the original immutable versions/events and one durable receipt. A forced event
  ID conflict during the ordered event writes proves the transaction rolls back both
  aggregate heads, the ResourceRevision, ArtifactVersion, both new event IDs, and the
  idempotency receipt. A provenance input that claims an observed digest for a pinned
  ResourceRevision with no stored digest is rejected as an integrity error. This does not
  qualify the packaged UI route or broader provenance and provider-backed Artifact cases.

The transaction accepts the verifier result from the authenticated internal storage
port. It does not execute the verifier, qualify its executable/oracle, or establish
an external verifier trust chain. Evidence payload snapshots use the existing
encrypted blob path in production; the direct SQL test fixture checks transaction
and trigger behavior only.

The domain-effects crate now also exposes `assess_completion_with_evidence`, which
requires an exact PASSED run for each current criterion and validates that every run
reference resolves to committed-shaped, same-Task, `VERIFIED` Evidence bound to that
same run and one of its pinned subjects. The legacy assessment without Evidence rows
remains fail-closed. This is an evaluator primitive only: no TaskService completion
transition consumes it yet, so it does not make a Task completable or prove that an
arbitrary caller supplied an authoritative Evidence projection.

## 2026-10-20 — verification-run read projection and evaluator rejection matrix

### Implemented behavior

- `GET /v1/tasks/{taskId}/verification-runs` is now served by a dedicated read-only
  Operator module. It matches the existing OpenAPI operation
  `listTaskVerificationRuns`; no route, parameter, or schema was invented.
- The route resolves `X-Workspace-ID`, requires the authenticated local principal to own
  that Workspace, and delegates the Task/Workspace/owner check to the storage read. A Task
  in another owned Workspace and an absent Task both return the same `404 NOT_FOUND` body
  (`"Task is unavailable"`); a Workspace owned by another principal returns `403`.
- Successful pages carry `Cache-Control: no-store`.
- Pagination uses the contract's `cursor`/`limit` query parameters. The cursor is opaque
  base64url JSON binding the Workspace, Task, page size, and the last item's
  `started_at`/`verification_run_id`. The storage query is a keyset read ordered by
  `started_at DESC, verification_run_id DESC`, so a page boundary does not shift when new
  runs are appended. `limit` is enforced at 1–200; changing the limit, Task, or cursor
  payload is rejected with `400 INVALID_ARGUMENT`.
- The projection is built field-by-field from exactly the OpenAPI `VerificationRun`
  fields. The internal aggregate `version`, the typed `failure_code`, and any future
  private domain field are never serialized. No producer credentials, provider handles,
  or filesystem paths exist in the record shape.
- The handler performs no writes, emits no events, and creates no idempotency receipt.
  It does not start, execute, settle, or repair a run.

The `VerificationRunStore` list port gained the two keyset arguments; the previous method
had no callers and could not honor the contract cursor. The SQLite implementation keeps
owner/Workspace/Task authorization inside the read transaction and still returns
`NotFound` for an out-of-scope Task.

### Completion-evaluator matrix

The new rejection/accept matrix lives in `crates/storage-sqlite/src/verification_runs.rs`
because that test module already owned the `VerificationRunRecord`, `EvidenceRecord`, and
run-payload fixtures. It proves `domain_effects::assess_completion_with_evidence`:

- accepts exactly one PASSED run matching the criterion revision/digest plus one
  `VERIFIED`, same-Task, same-run Evidence record naming a pinned subject;
- rejects a criterion with no PASSED run (still RUNNING);
- rejects a run pinned to a stale criterion digest;
- rejects `REPORTED` and `OBSERVED` Evidence;
- rejects Evidence bound to another run;
- rejects Evidence whose subject is not one of the run's pinned subjects; and
- rejects a run when extra Evidence is bound to the run but not listed in
  `evidence_refs` (binding must be exact).

This remains a pure evaluator test. No Task transition consumes the result, and no
completion decision is persisted or exposed.
