# E07-S00 partial CODE/SYSTEM review packet — Task-scoped local Environment isolation

**Status:** Partial CODE and lower-level Linux SYSTEM evidence only. E07-S00 remains
`IN_PROGRESS`; no production EnvironmentProvider is integrated and native Task dispatch
must remain disabled.

## Outcome and changed modules

The `local-environment-staging` crate validates exact Workspace/Resource/revision/digest
pins, size/count/path bounds, traversal and case-fold collisions, and creates a Unix
preview root with read-only inputs and separate writable outputs. A Task input adapter
resolves exact historical Resource revisions through `ResourceStore` and returns
`PreparedOnly`. It does not create an Environment record, reauthorize the owner through an
Operator flow, bind a provider to a Runtime incarnation, enforce process/filesystem/network
restrictions, or admit an Attempt/session/lease.

Separate `linux-process-scope` code uses Bubblewrap namespaces and systemd/cgroup process
scope primitives. It requires positive quiescence before writer release. This lower-level
primitive is not yet the complete E07-S00 provider.

**Windows process-tree quiescence primitive (2026-10-18):** `crates/windows-local-security/src/lib.rs` now exposes `ContainedChild::wait_for_job_quiescence(timeout)`. It polls the exact owned Job Object's `JOBOBJECT_BASIC_ACCOUNTING_INFORMATION.ActiveProcesses` under a checked monotonic deadline; query failure and timeout return errors. It does not infer quiescence from direct-child exit. Windows host tests use real nested processes to prove that a descendant keeps the Job non-quiescent after its parent exits, that terminating the Job and observing active-process count zero succeeds, and that a live tree times out. A query-failure seam verifies fail-closed propagation. This is only a process-tree primitive: it is not wired to Runtime's private process journal, does not provide the required IsolationAttestation, and does not enable Task dispatch or qualify Windows filesystem/network/resource enforcement.

**Contained-child settlement integration (2026-10-18):** The same Windows helper now applies Job-zero semantics to its existing production `ContainedChild::try_wait` and `wait` methods. `try_wait` preserves the direct `ExitStatus` internally but returns `None` while any descendant remains; Job-query errors return errors. Blocking `wait` uses a one-second bound, terminates the private Job on timeout/query failure, reaps the direct child, and only returns a normal status after a positive zero-process observation. If cleanup cannot establish zero, it returns an error. Native Windows host tests prove direct-parent exit with a live descendant stays unsettled, timeout cleanup kills and observes the descendant, normal no-descendant completion succeeds, and query errors fail closed. Full `windows-local-security` host suite passed 29/29 with 0 doc tests on Windows 10.0.26200.0, PowerShell 5.1.26100.9711, Rust/Cargo 1.98.1, `x86_64-pc-windows-msvc`; helper and source-copy SHA-256 match `37cfb31869747e0911c0cc716ca9cff85ba5d82e2c53a12a0353b48e37b30eca`. **Windows handle-relative staging (2026-10-18):** The Windows security helper now
provides verified-directory-relative `create_new_directory` and `create_new_file`
operations. Each component is created/opened relative to an owned directory handle with
`NtCreateFile`, `OBJ_DONT_REPARSE`, `FILE_OPEN_REPARSE_POINT`, and create-new semantics.
Protected SYSTEM/OWNER DACLs are passed in `OBJECT_ATTRIBUTES` during object creation;
the staging path does not create a file and then reopen its pathname to apply ACLs. File
bytes are written and flushed through the retained file handle before setting the
read-only attribute. Windows `local-environment-staging` now opens the supplied staging
parent without reparse traversal, creates the staging root plus `inputs`/`outputs` relative
to verified handles, and writes the exact pinned paths under the retained input-root
handle. This closes pathname ancestor replacement/reparse traversal during the staging
writes. The returned object remains `PreparedOnly`; this is not a same-user sandbox,
output-quota enforcement, provider attestation, dispatch admission, or general Windows
Environment qualification. A host helper test independently reads a newly created
directory's DACL and checks that it is protected and contains exactly two ACEs; it does
not decode the SID and access mask in each ACE or inspect a staged file's DACL.
