## Contract and behavior

Authorities: [ROUTINES](../../docs/ROUTINES.md) (RoutineHealth projection),
[AUTOMATION](../../docs/AUTOMATION.md), [API](../../docs/API.md), [EVENTS](../../docs/EVENTS.md),
[STATE-MACHINES](../../docs/STATE-MACHINES.md), [EXPERIENCE](../../docs/EXPERIENCE.md),
[V1-WORKFLOW-EVENT-LLD](../../docs/V1-WORKFLOW-EVENT-LLD.md), and [E09](../epics/E09.md).

- A projection is a read-only view over persisted facts. It never repairs, never
  re-enables, never advances a cursor, and never creates a Task or an occurrence.
- `DRIFTED` requires explicit incompatibility evidence. A failed Task alone is `WARNING`.
  The absence of an observation is `UNKNOWN`, never `HEALTHY`.
- The success rate uses the ten most recent terminal Tasks of the current Routine
  revision. `COMPLETED` counts as success, `FAILED`/`INCOMPLETE` as unsuccessful, and
  `CANCELLED`/nonterminal runs are excluded. Fewer than three eligible runs are reported
  as "not enough runs yet" instead of a percentage.
- A completed schedule is never presented as evidence that its Tasks succeeded: the
  occurrence state and the Task outcome stay separate facts in the Runs view.

### The Automation test run

The exact-revision test run is implemented end to end without creating an occurrence.

```sql
-- schema v27 / docs/schemas/sqlite-v27.sql
CREATE TABLE automation_test_runs (
  test_run_id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL,
  command_key TEXT NOT NULL,
  automation_id TEXT NOT NULL,
  automation_revision INTEGER NOT NULL,
  routine_id TEXT NOT NULL,
  routine_revision INTEGER NOT NULL,
  task_id TEXT,
  requested_by_json TEXT NOT NULL,
  created_at TEXT NOT NULL,
  version INTEGER NOT NULL
);
ALTER TABLE tasks ADD COLUMN automation_test_run_id TEXT;
```

- **Admission.** `POST /v1/automations/{automationId}/test-runs` requires the selected
  Workspace, `Idempotency-Key`, and the current `If-Match` version. It pins the exact
  current AutomationRevision/RoutineRevision, accepts `PAUSED` or `ENABLED`, refuses
  `DISABLED`, and creates one ordinary READY Task with a null `automation_id` and
  `automation_occurrence_id` plus `automation_test_run_id`. It requires no trigger identity
  or trigger-host binding, writes no AutomationOccurrence, and never advances an
  AutomationCursor.
- **Lead path.** When the AutomationRevision pins a Coworker, the Task records that exact
  origin and uses its lead/failover defaults while the Coworker remains `ACTIVE`; otherwise
  it uses ordinary Routine/Workspace lead precedence.
- **Idempotency/order.** The exact immutable revision is loaded first, then the receipt is
  checked, and only then are mutable status/head/version checks applied. The first response
  is `201`, an exact replay is `200`, and a changed payload under the same key is `409`.
  Exact replay remains readable after the Automation advances revision, is disabled, or
  the Workspace is archived; a new run against the old revision is `409`.
- **Storage guards.** The stored `command_key` is checked against the canonical domain
  `TestRunIdentity` fingerprint for the exact principal, request, Automation, and revision.
  SQLite triggers require an unlinked reservation with matching Workspace/Routine pins,
  reject a Task that combines test and occurrence provenance, make the provenance immutable,
  and allow the reservation to link once (version 1→2). A forced `request_dedup` failure
  leaves zero Task/test-run/occurrence/cursor/receipt rows and the same request succeeds
  after the fault is removed. The Task aggregate-state blob is written before the SQLite
  transaction, so a failed commit can leave an unreferenced content-addressed blob; no
  Task, test-run row, occurrence, cursor, event, or receipt is visible.
- **Route evidence.** The real-router test advances the Automation to revision 2 after the
  first commit, proves the original revision-1 receipt still replays `200`, rejects a new
  revision-1 run against the advanced head, then proves the same replay after disable and
  after Workspace archive while new test runs are refused.
- **Desktop.** The Automation detail shares bounded Routine input fields between Manual Run
  and Create test Task. A test result is labeled as a real READY Task with no occurrence or
  cursor; the process-local pending registry preserves the exact test request for an
  ambiguous-outcome retry. A setup-progress checklist derives Review/Test/Enable states
  from persisted status, pinned Routine state, and observed host readiness, and reports
  blockers instead of claiming success. No dry-run or simulated-preview claim is made.
