## Contract and behavior

Authorities: [ROUTINES](../../docs/ROUTINES.md) (RoutineHealth projection),
[AUTOMATION](../../docs/AUTOMATION.md), [API](../../docs/API.md), [EVENTS](../../docs/EVENTS.md),
[STATE-MACHINES](../../docs/STATE-MACHINES.md), [EXPERIENCE](../../docs/EXPERIENCE.md),
[V1-WORKFLOW-EVENT-LLD](../../docs/V1-WORKFLOW-EVENT-LLD.md), and [E09](../epics/E09.md).

- A projection is a read-only view over persisted facts. It never repairs, never
  re-enables, never advances a cursor, and never creates a Task or an occurrence.
- `DRIFTED` requires explicit incompatibility evidence. A failed Task alone is `WARNING`.
  The absence of an observation is `UNKNOWN`, never `HEALTHY`.
- The success rate uses the ten most recent terminal Tasks of the current Routine
  revision. `COMPLETED` counts as success, `FAILED`/`INCOMPLETE` as unsuccessful, and
  `CANCELLED`/nonterminal runs are excluded. Fewer than three eligible runs are reported
  as "not enough runs yet" instead of a percentage.
- A completed schedule is never presented as evidence that its Tasks succeeded: the
  occurrence state and the Task outcome stay separate facts in the Runs view.

## Remaining gates and reviewer replay

### OpenAPI follow-up owned by the lead

`GET /automations/{automationId}/health` is served by the daemon but the shared
`docs/schemas/operator-api.openapi.yaml` does not yet declare it, and there is no
`AutomationHealth` component schema. The served body is:

```yaml
# Required lead-owned OpenAPI addition (not applied by this epic).
AutomationHealth:
  type: object
  additionalProperties: false
  required: [automation_id, current_revision, status, host_ready, blockers,
             next_occurrence_at, last_occurrence_at, nonterminal_occurrences,
             occurrence_counts, routine_health, drift_state, drift_evidence_refs]
  properties:
    automation_id: {type: string}
    current_revision: {type: integer, minimum: 1}
    status: {type: string, enum: [ENABLED, PAUSED, DISABLED]}
    host_ready: {type: boolean}
    blockers: {type: array, items: {type: string}}
    next_occurrence_at: {type: [string, 'null'], format: date-time}
    last_occurrence_at: {type: [string, 'null'], format: date-time}
    nonterminal_occurrences: {type: integer, minimum: 0}
    occurrence_counts: {$ref: '#/components/schemas/AutomationOccurrenceCounts'}
    routine_health: {$ref: '#/components/schemas/RoutineHealth'}
    drift_state: {type: string, enum: [HEALTHY, WARNING, DRIFTED, UNKNOWN]}
    drift_evidence_refs: {type: array, items: {type: string}}
```

The Routine projection already matches the contracted `RoutineHealth` component, including
its `additionalProperties: false` rule: the served body carries no `status` field, its
`observed_costs` entries use the `UsageQuantity` shape, and its
`required_dependency_health` entries use the contracted `DependencyHealth` shape. The
occurrence history matches the contracted `AutomationOccurrencePage` and
`AutomationOccurrence` components, including the opaque Workspace/Automation-bound cursor.

### The Automation test run

The **Automation test run** is not implemented. `tasks` currently requires
`automation_id` and `automation_occurrence_id` to be set together and foreign-keys them to
a persisted `automation_occurrences` row, so an Automation test Task cannot be pinned to an
AutomationRevision without creating an occurrence. The needed migration is:

```sql
-- Required lead-owned migration for E09-S03 (not applied by this epic).
ALTER TABLE tasks ADD COLUMN automation_test_run_id TEXT;
-- plus a nullable automation_test_runs table:
--   workspace_id, test_run_id, automation_id, automation_revision, task_id,
--   requested_by, created_at, version
-- and a tasks trigger that rejects a Task that carries automation_id without
-- automation_occurrence_id when automation_test_run_id is set, and rejects a
-- test Task that points at a non-test run.
```
