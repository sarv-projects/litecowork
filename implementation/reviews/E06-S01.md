## Implemented source path

The authenticated local Operator serves:

```text
POST /v1/resources/{resource_id}/archive/preview
```

The handler is `preview_resource_archive` in
[`resource_archive_operator.rs`](../../apps/litecoworkd/src/resource_archive_operator.rs),
mounted through `operator.rs`. It reads the selected Workspace header, requires the
authenticated principal to own that Workspace, and accepts a closed request containing
only `resource_revision_id` and `content_digest`. It resolves that exact immutable
ResourceRevision through `ResourceStore::read_resource_content_bounded`, capped at 16 MiB,
and cross-checks Workspace, Resource, revision, digest, and length before passing bytes to
the worker. The response contains safe virtual paths and ZIP entry metadata only. Successes,
handler errors, and Axum extractor errors receive `Cache-Control: no-store`. This read-only
operation records no event, receipt, Invocation, Effect, Artifact, or child Resource.

The bounded Runtime bridge is
[`resource_archive_worker.rs`](../../apps/litecoworkd/src/resource_archive_worker.rs).
It is compiled only on Linux with the explicit, non-default Cargo feature
`source-zip-worker`; without that feature (including release sidecars), it returns
`Unavailable` before checking any source-tree path. When enabled, it launches only
`/usr/bin/python3 -I` with the fixed source-tree CLI path, cleared
environment, no host path/URL input, 24 MiB request and 8 MiB response caps, a 15-second
outer deadline, and process-group cleanup. The CLI in
[`runtime_cli.py`](../../capabilities/zip_intake/runtime_cli.py) accepts a closed JSON
protocol and rejects duplicate fields. It invokes `ZipWorker`; untrusted member parsing is
inside Bubblewrap. No member payload is returned by this preview CLI.
The supervisor treats that worker as untrusted output: it revalidates canonical safe paths,
requires paths for every non-rejected entry, and rejects duplicate/case-folded or
file-ancestor collisions unless the worker quarantined all affected entries as
`REJECTED / PATH_CONFLICT`.

The canonical contract references are:

- `docs/API.md`, section “The Linux development Runtime also exposes a separate read-only ZIP metadata preview”.
- `docs/schemas/operator-api.openapi.yaml`, operation `previewResourceArchive` at `/resources/{resourceId}/archive/preview`.
- OpenAPI schemas `ArchivePreviewRequest`, `ArchivePreviewResponse`, `ArchivePreviewLimits`, and `ArchivePreviewEntry`.
- Generated desktop types in `apps/litecowork-ui/src/api/operator-api.ts`: operation `previewResourceArchive` and the four `ArchivePreview*` schemas.
- Capability readiness remains `GET /v1/capabilities/zip-intake` with `UNAVAILABLE / ISOLATED_WORKER_NOT_QUALIFIED`.

The UI source-reference panel is wired to actual local lexical/on-demand search results in
`apps/litecowork-ui/src/App.tsx`. It renders only result rows with source spans, passes the
exact revision/digest/span set to the existing preview flow, and marks search spans only
after the preview digest and UTF-8 byte offsets validate. It does not claim semantic RAG or
that a Task consumed the displayed source.

## Limits and pending acceptance

- Only a Linux build explicitly compiled with the non-default `source-zip-worker` feature
  resolves `capabilities/zip_intake/runtime_cli.py` relative to the Cargo source tree. The
  Tauri sidecar build uses a release build without features; package preview stays unavailable
  even if the source checkout remains on disk. The desktop bundle also does not include the
  Python capability. Readiness stays `UNAVAILABLE / ISOLATED_WORKER_NOT_QUALIFIED`.
- The daemon route previews metadata only. The Python capability has a separately tested
  bounded in-memory extraction method, but Runtime extraction is not exposed or wired.
- No Core transaction creates child Resources, immutable child blobs, `DERIVED_FROM`
  provenance, index entries, or atomic failure/recovery receipts. There is no deletion or
  purge lifecycle for extracted members.
- The UI/runtime route has no explicit user cancellation API. The Python supervisor supports
  an internal cancellation event; the route does not provide or forward one.
- Only this Linux WSL2 development host was exercised. Packaged Linux, native Windows,
  macOS, other Linux distributions, PDF/Office parsing, OCR, and real provider qualification
  remain untested or unavailable.
- No owner USER acceptance, mixed-folder import/extraction report, crash/restart state

## Provider-side extraction plan and staging materialization — 2026-10-20

`capabilities/zip_intake/extraction.py` now adds a metadata-only `ExtractionPlan` and a
streaming, anchored staging-root materializer. The plan carries stable entry identity
(archive index plus raw-name SHA-256), declared bytes, measured compressed bytes, a bounded
media-type hint, typed refusal codes, archive-order entries, and the required processing
order sorted by UTF-8 path bytes. `materialize()` rebuilds and compares the plan against the
exact archive before writing, refuses stale/forged plans, streams 64 KiB chunks under
per-entry/ratio/total budgets, rejects traversal, absolute, link, device, duplicate and
case-colliding members, and never follows a destination symlink or writes outside the root.
It creates no Resources, provenance, Effects, receipts, events, or index rows.

## Core-side extraction publication gap — 2026-10-20 (E06 owner)

The provider deliberately creates no child Resources, no provenance, and no extraction
Effects. This note records exactly which Core side already exists, so that the next
slice does not re-implement it, and which part of the Core side has no contract yet.

**Already implemented in Core and reusable without new schema:**

- `storage_core::ResourceStore::create_derived_resource` publishes a child Resource
  and its pinned `DERIVED_FROM` `ResourceEdge` in one storage transaction, together with
  both domain events and the idempotency receipt. The v25 migration makes
  `resource_edges` append-only. This is the publication path an extraction result would
  use; it is not wired to ZIP extraction by any route.
- The ContextDocument purge flow owns the SQL-reference removal that makes an encrypted
  ResourceIndex snapshot collectible, and its manifest already has a `DERIVED_INDEX`
  replica kind for the local text index.

**Not implemented and not contract-specified:**

1. **A Core extraction service.** Nothing maps a provider `ExtractionPlan` to a
   `DerivedResourceCreateCommit`: there is no service that decides the child Resource
   identity, kind, media type, and `DERIVED_FROM` parent pin from provider output, and
   no route that invokes the provider and then publishes the result. The daemon only
   serves the metadata-only `POST /v1/resources/{resource_id}/archive/preview`.
2. **An extraction Effect.** `docs/EVENTS.md` and `docs/DATA-MODEL.md` define no
   extraction effect type. Recording that "an archive was expanded into N member
   Resources" as a durable Effect needs a new event/effect contract and an event
   registry entry. Adding one is a contract change for the lead, not a code change in
   this epic.
3. **A deletion lifecycle for extracted members.** The parent ContextDocument purge
   removes the parent's own managed content, its ResourceIndex rows, and its upload
   chunk objects. It does not revoke or purge the child Resources that an extraction
   would create. A parent deletion must therefore also enumerate and fence the child
   Resources, which needs the same new contract as (2).
4. **Provenance content.** The child Resource `provenance` shape that records the
   archive member path, the member digest, and the extraction plan identity is not
   defined by `docs/DATA-MODEL.md` today. `docs/DATA-MODEL.md` owns the canonical
   `Resource.provenance` fields and must be extended before the first child Resource is
   published.

**Recommended next Core slice (no migration required):** a daemon route that accepts the
provider's `ExtractionPlan` result, verifies each member against the staged bytes, and
publishes one child Resource per member through the existing `create_derived_resource`
transaction, with the archive Resource as the `DERIVED_FROM` parent. That slice needs
the provenance shape from (4) but not a migration. Items (2) and (3) need the contract
changes first.
