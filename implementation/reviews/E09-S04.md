# E09-S04 — Notifications and settings review packet

**Evidence status:** The notification **decision layer** is implemented and covered by
domain CODE tests. The two contracted read routes (`GET /v1/notifications` and
`GET /v1/notification-preferences`) and the versioned preference write
(`PUT /v1/notification-preferences/{event_class}`) are now served from the canonical
`notification_deliveries` and `notification_preferences` tables. Reads are owner-scoped with
a tied-timestamp-safe keyset cursor; the write is `If-Match` versioned, idempotent, records
`notification.preference.changed.v1`, and refuses an ARCHIVED Workspace. No migration was
added: both tables already exist in `docs/schemas/sqlite-v1.sql`. The desktop delivery
history and policy surface is implemented over a typed Tauri bridge. The delivery pipeline,
the `notification.delivery.changed.v1` event, and the OS provider are not implemented, so a
production delivery list is truthfully empty until a producer writes it. Backlog status for
E09-S04 remains `PLANNED`.

## Contract and behavior

Authorities: [AUTOMATION](../../docs/AUTOMATION.md) (execution policy and notification
policy), [RESPONSIBILITIES](../../docs/RESPONSIBILITIES.md), [CHANNELS](../../docs/CHANNELS.md),
[API](../../docs/API.md), [STATE-MACHINES](../../docs/STATE-MACHINES.md), and
[E09](../epics/E09.md).

- A notification is a separate fact from the Task outcome it reports. Delivery success is
  never Task completion.
- One notification is produced per settled occurrence, never per worker token or Step.
- The governing Automation notification policy (`ALWAYS`, `ON_SUCCESS`, `ON_FAILURE`,
  `ON_CONCITION`, `SILENT`) and the Workspace class preference both have to address the
  outcome. `SILENT` never produces a delivery.
- A duplicate delivery of the same logical outcome is suppressed by the Workspace-scoped
  dedupe key. A Workspace with no local channel binding never claims a delivery.
- Quiet hours suppress a delivery inside the configured local window.
- A suppressed outcome records a typed reason (`SILENT_POLICY`, `POLICY_MISMATCH`,
  `CLASS_DISABLED`, `DUPLICATE`, `QUIET_HOURS`, `NO_CHANNEL`) instead of silently
  disappearing.

- **Read routes served.** `GET /v1/notifications` (status filter, keyset cursor, limit
  1–200) and `GET /v1/notification-preferences` read the canonical tables through
  `crates/storage-sqlite/src/notification.rs` and
  `apps/litecoworkd/src/notification_operator.rs`. Both are owner-scoped and use the
  Core-data authorization level, so an ARCHIVED Workspace stays readable.
- **Preference write served.** `PUT /v1/notification-preferences/{event_class}` requires
  `Idempotency-Key` and `If-Match` (`0` for the first write). The policy row, its request
  receipt, and a `notification.preference.changed.v1` event commit in one `IMMEDIATE`
  transaction; the event payload carries exactly the five fields declared by the schema
  (`workspace_id`, `event_class`, `policy`, `preferred_channels`, `aggregate_version`).
  The route refuses an ARCHIVED Workspace with `409 WORKSPACE_ARCHIVED` because a policy
  change is a mutation; the refusal happens inside the transaction, so no row, event, or
  receipt is recorded.
- **Replay and conflict semantics (storage CODE).** The same key with the same canonical
  request returns the committed record without a second event; the same key with a
  different policy is `StoreError::IdempotencyConflict`; a stale `If-Match` is
  `StoreError::Conflict { expected, actual }` and leaves the prior row untouched.
- **Pagination is tied-timestamp safe.** The cursor carries `(created_at, delivery_id)`
  because `created_at` alone is not unique; a page boundary on a shared second neither
  repeats nor skips a delivery. The route fetches one extra row so `next_cursor` reflects
  a real next row instead of an empty follow-up page.
- **Failure/auth evidence (storage CODE).** A foreign principal receives `NOT_FOUND`
  rather than a missing/foreign distinction; a half cursor, a limit of 0, and a status
  token outside the contracted enum are rejected; unreadable stored preference JSON is
  `Integrity`, never a silently dropped policy; invalid policy tokens, unknown or duplicate
  weekdays, out-of-range local times, and a non-ASCII five-byte time value are rejected
  before any write.
- **Fixtures/digests:** delivery and preference rows are inserted by the storage test
  fixture, and the write tests read back the committed row, event, and receipt. No provider
  payload or owner fixture result is recorded.
- **Failure/race/auth:** the domain cases cover the silent policy, the success/failure

- **Provider/OS:** no OS notification provider is exercised. No delivery is claimed.
- **Screenshots/accessibility:** no screenshot or screen-reader run is recorded. The

## Desktop surface (2026-10-21)

- **Tauri bridge.** `apps/litecowork-ui/src-tauri/src/notification_bridge.rs` exposes only
  `list`, `preferences`, and `set-preference` over the authenticated local Operator IPC.
  The command accepts no arbitrary URL, method, or header. An event class is one allowlisted
  path segment (`[A-Za-z0-9_-]{1,128}`), status and policy are the contracted enums, the
  cursor is bounded to 2,048 bytes, `limit` to 1–200, channels to 64 entries of at most 256
  control-free bytes, quiet hours to an 8 KiB JSON object, and the request identity to the
  shared `Idempotency-Key` grammar. The response is capped at 1 MiB. Unit tests cover path
  injection, status/policy tokens, and channel bounds.
- **Transport and decoders.** `src/notifications/notification-api.ts` binds every response
  to the selected Workspace, strictly decodes delivery status, attempt counts, nullable
  runtime/host fields, error codes, quiet hours (IANA timezone, weekday enum, `HH:MM`
  local times), and a keyset cursor. `desktop-notification-api.ts` maps the three finite
  paths onto the bridge, rejects a changed Workspace header, validates `If-Match`
  (including version `0`) and the idempotency key before invoking, and decodes through the
  shared `operatorBridgeResponse`.
- **Page.** `NotificationsPage.tsx` reads one bounded delivery page with a status filter and
  a "load older" keyset continuation, renders an honest empty state ("No notification
  deliveries yet"), and edits the five contracted event classes. Each Save sends the
  stored version as `If-Match`, preserves saved quiet hours, and refreshes the row from the
  committed response. A conflict or stale version stops the save and offers an explicit
  policy reload; an ARCHIVED Workspace refusal is shown as read-only history. Unconfigured
  classes stay unlabelled as "using the Runtime default" rather than inventing a default.
- **Truthful limits.** Quiet hours are displayed and preserved, not edited on this surface.
  Deep links, retry of a failed channel setup, and the OS permission state have no UI
  because the delivery pipeline does not exist yet. No alert is claimed as delivered.

## Remaining gates and reviewer replay

The durable tables already exist in the applied schema; no migration is needed.
`docs/schemas/sqlite-v1.sql` defines them, and both survive every later migration:

- `notification_preferences(workspace_id, event_class, policy, preferred_channels_json,
  quiet_hours_json, version)` — matches the OpenAPI `NotificationPreference` shape.
- `notification_deliveries(delivery_id, workspace_id, dedupe_key, source_event_id,
  channel_binding_id, attempt_runtime_id, attempt_host_epoch, status, attempt_count,
  next_attempt_at, last_error_code, created_at, settled_at)` with
  `UNIQUE(workspace_id, dedupe_key)` and a `CHECK` on the status enum.

An earlier revision of this packet proposed new `notification_deliveries` and
`workspace_notification_preferences` tables. **That proposal must not be applied**: the
names and columns conflict with the canonical schema, and `notification_deliveries` already
exists. The delivery decision is persisted in `notification_deliveries.status`
(`PENDING | SENDING | SENT | FAILED | AMBIGUOUS | SUPPRESSED`) plus a typed
`last_error_code`, not in a separate `decision`/`suppress_reason`/`delivery_state` triple.

Served CODE is the storage read/write port
(`crates/storage-sqlite/src/notification.rs`), the
`GET /v1/notifications` / `GET /v1/notification-preferences` /
`PUT /v1/notification-preferences/{event_class}` Operator routes, the
`notification.preference.changed.v1` event written by the preference transaction, and the
desktop bridge/transport/page. Pending CODE is the delivery adapter that maps the domain
decision onto `notification_deliveries` with idempotent dedupe on `(workspace_id,
dedupe_key)` and the `notification.delivery.changed.v1` transition events. The producer also
has no caller yet: `domain_responsibility::settle_from_task_outcome` is exercised only by
domain tests, so no served path settles an occurrence when its Task reaches a terminal
state. The next bounded slice is Task outcome → occurrence settlement → delivery record;
until then the desktop delivery list is intentionally empty and no delivery is claimed.
Pending SYSTEM is the real local notification provider on the supported OS. Pending USER is
the owner completing a Task with the app closed and reopening the correct Artifact from
the notification. The deep link target must be the persisted Task/Artifact identity, never
an agent sentence.
