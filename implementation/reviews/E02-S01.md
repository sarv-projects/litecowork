## Contract and behavior

The slice addresses the resize/200% zoom negative case in [E02](../epics/E02.md) and
the responsive requirements in [DESIGN-SYSTEM](../../docs/DESIGN-SYSTEM.md) and
[EXPERIENCE](../../docs/EXPERIENCE.md): labeled drawer below 900px, single-column compact
behavior on narrow screens, and no two-dimensional scrolling. `body` and the Tauri window
no longer enforce a 760px minimum. Below 900px the sidebar becomes a modal navigation
drawer. Its trigger exposes `aria-expanded`/`aria-controls`; opening moves focus into the
drawer, makes main content inert, and traps Tab/Shift+Tab. Escape, close button, backdrop,
navigation selection, and resizing above 900px close it; dismissal restores focus to the
trigger on narrow windows. Closing at desktop width moves focus to the active navigation
item after the mobile close control becomes hidden. Below 620px the top bar and content
spacing compact.

No Task, Trust, Effect, Evidence, storage, API, or event behavior changed. The native
minimum window width is 480px, so smaller layouts are tested in browser viewport emulation;
the packaged WebView and physical zoom remain unqualified.

## Home first-run Workspace setup and create-race CODE/UI slice — 2026-10-14

Home now checks the authenticated Workspace list before showing a creation form. While no
Workspace is selected, the normal Task composer, Coworker setup, and recent-work panel are
withheld. The setup view distinguishes list loading/failure from Runtime checking,
reconnecting, offline, degraded, and unavailable states. Workspace creation calls the same
existing Tauri `create_workspace` command as Settings, which uses the authenticated local
Operator route. A confirmed receipt adds the Workspace to the list. A user selection made
while the request is pending is preserved when the create response arrives.

Settings also blocks Workspace creation until an authenticated Workspace-list request has
succeeded. The name field and submit action stay disabled while the list is loading or
failed; the existing Refresh action recovers the list, and creation becomes available after
the successful response. A production-App regression test covers loading, failure, retry,
and the zero-create-command condition. An adversarial review found this Settings-only bypass
after the initial Home implementation; the fix gates the shared Settings create form on the
same list state used by Home.

The create handler now has a synchronous in-flight guard, retains the same Idempotency-Key
after ambiguous failure, rejects a different name while that receipt is unresolved, and
locks the original name in both Home and Settings until exact retry succeeds. After an
application restart, the authenticated Workspace-list read gates the form: a committed
Workspace is rediscovered before another create can be offered; if the list is unavailable,
creation stays blocked. No Task, Coworker, or agent is represented as started or ready by
this setup screen.

The rendered check mounts the production `WorkspaceFirstRun` component with an isolated
callback fixture. It verifies list loading/error/retry, Runtime offline/start/refresh,
existing-Workspace restoration, accessible labeled input, blank and busy submission,
ambiguous retry with locked name, and one submit callback. Three additional rendered cases
mount the production App over mocked Tauri IPC: Settings create stays blocked while the
Workspace list is loading or failed and is enabled after an empty-list retry; a committed
create survives a stale in-flight list refresh; and a failed Runtime refresh disables create
after READY. These are App/UI CODE evidence, not real daemon/SQLite proof. The existing
daemon route and process restart/replay evidence remains recorded under E01-S04; no daemon or
Tauri source changed in this slice.
