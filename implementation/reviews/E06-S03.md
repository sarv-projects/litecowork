## What was implemented

### A Core-owned index state projection

`crates/storage-sqlite/src/rag_retrieval.rs` adds a read-only projection of the index
facts Core already owns, and `crates/domain-rag/src/index_state.rs` turns those facts
into the owner-visible state.

| Index facts | State | Meaning |
|---|---|---|
| projection matches the current revision and digest | `READY` | the current revision is searchable |
| projection exists for an older revision, or the head moved | `STALE` | the changed file is not searchable; the stale projection is never served |
| no projection at all | `ABSENT` | uploaded is not searchable |
| the qualified provider cannot index the Resource | `NOT_INDEXABLE` | typed reason |

The storage read (`SqliteWorkspaceStore::resource_index_state`) exposes only revision
identity, the digest already visible on the Resource, the parser identity, the index
timestamp, and the number of superseded projection rows. It returns no extracted text,
no term tokens, no blob digests, and no provider locator.

The state is served by `GET /v1/resources/{resource_id}/index-state` for the
authenticated Workspace owner.

### Serve-time invalidation (already Core-owned, now covered by E06 evidence)

The existing local index already refuses to serve a stale, revoked, or deleted
Resource, and the retrieval provider now re-checks the same facts at the last
boundary:

- The index candidate query requires `r.current_revision_id = rev.resource_revision_id`,
  so a projection built for a superseded revision is never returned.
- The candidate query and the final `candidate_is_current` recheck require the
  ContextDocument status to be `ACTIVE`, so a revoked or deleted Resource is never
  returned.
- The retrieval provider additionally re-reads the Resource detail and compares the
  returned revision with the current head before it accepts a segment, so a head that
  moved between the index scan and the answer is dropped.

### Recovery after a crashed index

The existing v19 ResourceIndex blob registry and its bounded collector already recover
a snapshot that was published before the projection commit failed, and the v17/v18
collectors recover content and upload-chunk objects. This slice does not change that
mechanism; it adds the observable state that shows a crashed or unrebuilt projection
as `STALE` or `ABSENT` instead of an empty result.

## Remaining gaps

- A superseded projection row is still registered and still keeps its encrypted
  snapshot until the Resource is deleted. The state projection reports the leftover
  count, but no writer removes it. **This needs a write path in
  `crates/storage-sqlite/src/lib.rs` (a new writer command), which is lead-owned
  shared code, and possibly a DDL change.** No DDL is required for the read path.
- There is no automatic re-index on a revision change. The owner rebuilds the exact
  current revision through the existing `POST /v1/resources/{resource_id}/text-index/rebuild`
  route. An automatic, background re-index is not implemented.
- There is no provider-owned replica registration and no purge receipt for an external
  index. The qualified provider is the local encrypted index, which is already covered
  by the Core ContextDocument purge manifest (`DERIVED_INDEX` targets).
- There is no watcher, no delta indexing, and no overflow reconciliation.
- No SYSTEM crash/restart run and no owner USER case (edit then revoke/delete a source
  and prove absence in a fresh query).

No story status promotion is supported by this slice. E06-S03 remains `IN_PROGRESS`.
