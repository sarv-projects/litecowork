## SQLite `SQLITE_FULL` through the bounded writer — 2026-10-12

`sqlite_full_through_writer_actor_preserves_state_and_allows_retry` uses a disposable
on-disk SQLite database and the real bounded writer actor. It sets `max_page_count` on the
actor-owned connection and verifies the effective cap, then submits an oversized revision
through `StateStore::commit_workspace`. SQLite returns `StoreError::Io("database disk is
full")`. Reads and event replay through the same actor still show the original projection,
one event, and origin sequence 1. The test raises the cap through the actor and retries the
same Workspace revision and event; the commit succeeds at origin sequence 2, the stream is
`[1, 2]`, and replay equals the committed projection. A read-only adversarial review
confirmed these claims and found no blocking issues.

The aggregate-state blob is written before the SQLite transaction. As specified in
`docs/STORAGE.md`, an unreferenced immutable blob may therefore remain after rollback and
is eligible for garbage collection. This test does not exhaust physical database/WAL/blob
storage and does not run the WorkspaceService policy-update command for the failing write.
It proves SQLite's `SQLITE_FULL` mapping, transaction rollback, actor availability, and
retry sequence continuity, not packaged/system provider behavior or owner acceptance.

## WorkspaceService idempotent `SQLITE_FULL` path — 2026-10-12

`sqlite_full_workspace_policy_command_rolls_back_idempotency_receipt_and_retries` uses a
temporary on-disk database and the production bounded SQLite writer. It caps the writer at
the current page count, then issues valid, idempotent replication-policy changes through
`WorkspaceService` until a normal event/receipt transaction returns
`StoreError::Io("database disk is full")`. Existing free database pages are consumed by
the successful commands first; the loop is bounded at 10,000 commands and SQLite rejected
the next write before that limit. After failure, the persisted Workspace equals the last
committed revision, event history remains contiguous at its previous origin sequence,
projection replay is unchanged, and the failed `(principal_id, request_id)` has no receipt.
The test restores capacity through the writer, retries the exact failed command and payload,
and checks it commits at the next version/sequence. Repeating that same request returns the
stored response; the receipt response digest validates and the event stream has no duplicate.

## Outcome

The first Workspace persistence vertical slice now has concrete Rust ports and adapters:

- `WorkspaceService` creates a `LOCAL_ONLY` Workspace and changes its replication policy.
- `StateStore` commits the projection with its event; `EventStore` reads the immutable
  Workspace event stream; the SQLite adapter owns their shared transaction boundary.
- A bounded synchronous SQLite actor applies the canonical v1 SQL contract, enables
  foreign keys/WAL/FULL synchronization, uses immediate write transactions, and records a
  migration source checksum plus resulting schema fingerprint.
- A per-Workspace/origin sequence advances atomically with the projection and event.
- `FileBlobStore` writes immutable content-addressed ciphertext using an injected,
  versioned `WorkspaceBlobKeyProvider`. Missing keys fail closed. The production
  `OsWorkspaceBlobKeyProvider` stores keys in the OS credential store. Linux explicitly
  constructs the persistent Secret Service credential, and a contract test checks its
  concrete type without connecting to the service. Key initialization and rotation use a
  OS file lock shared across processes and data directories. Unix lock-directory ownership
  and mode are checked; Windows uses `LOCALAPPDATA` and rejects reparse points, but ACL
  qualification remains open. An isolated child-process test checks lock exclusion. Injected backend tests cover staged
  rotation recovery. Actual OS credential-service behavior remains unqualified.
- Restart/replay checks the event revision chain, JCS payload digest, referenced encrypted
  aggregate-state blob, and equality with the persisted Workspace projection.
- Added an isolated SP02 SQLx/rusqlite comparison using separate Cargo processes. Both
  sides call the same WorkspaceService and production encrypted FileBlobStore, perform
  concurrent Workspace updates, close/reopen the database and decrypt/replay the complete
  event state. The rusqlite side uses the product adapter; SQLx remains an experimental
  WorkspaceStore adapter without all product migration/security checks. Three 200-update
  runs per driver used the same system SQLite 3.45.1. The overlapping results do not select
  a driver; SP02 remains open.
- Added a product-rusqlite mixed-load qualification mode with 40 independent Workspace
  writers, four concurrent readers and a 32-slot write queue. Readers validate monotonic
  versions and policy/version coherence; restart/replay checks all 40 final projections.
  Three sequential samples passed those integrity checks but showed substantial latency
  variation, so they are not a stable capacity baseline or proof of sustained queue
  saturation. Details and raw measurements are in `implementation/spikes/SP02.md`.
- Added process-local SQLite writer pressure observations: outstanding command count and
  high-water mark, plus total/maximum bounded-channel send wait. A held external writer
  lock test proves blocked callers are measured and settle without partial state; these
  observations are operational telemetry only and are not persisted or replicated.

This storage slice is composed into `litecoworkd` through `LocalWorkspaceStorage::open`.
The daemon's Operator API/IPC and desktop shell are separate implementation slices; this
packet does not claim Task execution, external agent/provider, cloud Runtime, or OS
credential-service qualification.

## Failure and race evidence

- Concurrent updates with the same expected Workspace version: exactly one succeeds and
  one conflicts; only the winning event is committed.
- Injected failures after aggregate, sequence, and event writes and before commit: all
  three durable tables remain unchanged.
- SQLite-generated `SQLITE_FULL` from a capped on-disk database is exercised through
  `commit_workspace_transaction`; the Workspace update, domain event and origin sequence
  remain unchanged and the adapter maps the failure to the safe storage I/O error. After
  restoring the page allowance, retrying the same revision succeeds at the next contiguous
  origin sequence. This is deterministic SQLite page-limit evidence, not a physical
  filesystem-full test.
- External SQLite writer lock: the configured timeout returns `Busy`, with no partial
  Workspace/event update.
- Interrupted baseline migration: DDL and marker roll back; retry applies the schema.
- RuntimeWorkspaceBinding upgrade: active and revoked legacy Runtime rows map to the
  expected `MESH_PAIRING` authorization bindings at v3; a failed v4 rebuild leaves those
  rows intact, and retry reaches the current schema without changing them.
- Removed schema trigger or unsupported future `user_version`: open fails closed.
- Changed recorded migration source checksum: reopening fails with `CorruptSchema` and
  leaves `user_version` unchanged.
- Blob put failure: no aggregate/event write begins.
- A failed active-pointer write leaves the old version usable. Rotation retry validates
  and activates the staged next key without replacing it; a reported pointer-write error
  after commit is reconciled by reading back the pointer and matching the stored key.
  Malformed staged material/pointers, orphaned first keys (recovery-required refusal), missing active keys, version
  exhaustion, staged-write failures, failed reconciliation reads, and changed key bytes
  fail closed. These checks use an injected credential backend. The Linux provider factory uses `SsCredential` rather than
  the keyutils-persistent wrapper/cache, but this does not qualify a live Secret Service,
  macOS Keychain, or Windows Credential Manager integration.
- Missing key provider: no ciphertext or plaintext object is written.
- Missing key after ciphertext was written: BlobStore `get` fails closed and returns no
  plaintext.
- Symlinked BlobStore root, Workspace, and purpose directory ancestors: `put`, `get`, and
  `remove` reject redirected paths, and outside sentinels remain unchanged.
- Wrong Workspace/purpose, corrupt ciphertext, and broad Unix purpose-directory
  permissions: read/write is refused. SQLite state paths reject symlinks and broad Unix
  directory permissions, and the main database file is restricted to `0600`.
- JCS fixture: object-key ordering and numeric formatting match the asserted RFC 8785
  canonical bytes; unsafe typed integers are rejected before digest persistence.
- Valid-ciphertext transplantation between two existing Workspace object paths and between
  two purpose paths is rejected by AEAD authentication, even though the fixed test provider
  intentionally returns the same key for every scope. This directly proves that AAD binds
  Workspace and purpose; the older wrong-scope `NotFound` tests exercise path separation.

Physical database/filesystem disk exhaustion is **not tested**. `SQLITE_FULL` via SQLite's
page limit exercises the database error mapping and transaction rollback, but does not
substitute for OS disk exhaustion, WAL/SHM sidecar exhaustion, or blob-volume exhaustion.

## Descriptor-relative Unix BlobStore hardening — 2026-10-14

The previous path-based Workspace/purpose/object checks had a deterministic TOCTOU gap:
an ancestor could be renamed and replaced with a symlink after validation but before the
object path operation. A test-first regression forced this interleaving and failed because
`get` read a valid encrypted sentinel through the replacement. Unix `FileBlobStore` now
walks the configured root and private Workspace/purpose scope with held directory handles
and no-follow opens. Object reads, temporary creation, no-clobber publication, removal,
and directory syncing are relative to the opened purpose handle. Scope creation syncs each
containing directory after a successful `mkdirat`. Reads and removals open leaf objects
nonblocking before checking for regular files, so a FIFO cannot stall the daemon. `put`
authenticates the published object before returning success.

Deterministic tests force Workspace-directory replacement after the purpose handle is
opened. `get` returns `NotFound` from the original tree rather than reading the outside
sentinel; `put` writes only into the moved original directory; `remove` leaves the outside
same-name object intact. A FIFO fixture confirms `get` and `remove` reject a non-regular
object without blocking. The descriptor boundary does not protect a compromised same-UID
process from changing entries inside its private directory; in particular portable Unix
APIs do not provide unlink-by-open-file-descriptor. Windows remains on the path-based
