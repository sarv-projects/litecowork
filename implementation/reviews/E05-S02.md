## Implemented source

`domain-task` now contains strict serde types for the schema's `TaskPacket` and
`ResultEnvelope`, with closed nested fields, typed result/evidence enums, typed budget and
blocker references, and bounded validation functions. The packet validator checks required
IDs/revisions, reference Workspace scope, field/array limits, duplicate child grant IDs,
budget shape, RFC3339 deadline, and canonical serialized size. Optional output destination
revision IDs are validated against the canonical Resource-ref ID contract. The result validator checks
status, size/count limits, confidence bounds, unique evidence/usage IDs, exact child
Attempt and pinned Task-revision identity, Workspace-scoped output/artifact references,
blocker references, and timestamps.

These envelopes carry references only. A caller still has to authorize referenced content,
resolve `BoundedDecision.source_event_id` against committed Task/Conversation events, and
verify outputs. The validators are not yet wired into a TaskPacket producer, accepted-Step
admission transaction, native session transport, or ResultEnvelope consumer.

`domain-task::decide_child_attempt_admission` now provides a pure versioned decision over
trusted admission projections. It rejects stale Task/Plan/TaskSpec pins, non-READY or
already-bound Steps, a parent that is not the current RUNNING Attempt with its exact
ACTIVE AgentSession and lease, malformed/cyclic ancestry, depth beyond the platform or
parent-profile ceiling, changed/disabled/archived profile revisions, Coworker-excluded
profiles, and exhausted effective Task/Coworker/profile concurrency. The effective Task
concurrency ceiling is the minimum of platform, Task and pinned Coworker limits; the
profile-specific active count is checked separately. This decision does not persist or
reserve capacity and does not replace Trust, Environment, adapter, grant, Effect, budget
or lease checks. The storage transaction does not yet consume these projections, so this
is a domain guard seam, not live child admission.

The exported `task_packet_preparation` module validates a `TaskPacket` against exact durable
Task/Step/Attempt/TaskSpec/Plan/profile pins and caller-supplied allowsets for exact input
Resource revisions, Artifact versions, committed decision event IDs, child-scoped grants,
authorized Resource references and approved output destinations. It emits canonical JSON
and a digest only when the envelope fits the caller's Task/profile context byte budget;
it rejects over-budget packets without truncating or rewriting them. The preparation
module does not resolve referenced content, mint grants, or decide whether the caller's
allowsets are authoritative. It is exported for a future producer but is not invoked by
one. A delegated parent must carry its immutable profile pin before creating another
descendant; root Attempts may remain unpinned, with the platform depth ceiling still
applied.

## Focused child-admission hardening (2026-10-17)

The durable preview now preserves the distinction between policy eligibility and executable
admission: when the policy projection would allow a child but any adapter, Runtime,
Environment, Trust, credential, containment, Effect, or budget proof is not `Confirmed`,
the preview returns `AuthorityPrerequisitesUnproven`. This is still a read-only preview;
the atomic writer remains unavailable and does not admit or dispatch a child.

SQLite also validates the parent Attempt / profile ID / pinned profile revision tuple as
all-present or all-absent before it takes the root-versus-child path. This rejects stray
profile pins on a root Attempt as well as partial child identity. The durable snapshot no
longer derives `Debug`, avoiding accidental debug output of nested Attempt failure and
checkpoint metadata.

## ResultEnvelope publication/read vertical path (2026-10-17)

`DelegationResultService` now connects the strict domain ResultEnvelope validator to the
durable `DelegationResultStore` port. Publication binds the report to the authenticated
Runtime, incarnation, AgentSession, Workspace, Task, and TaskSpec revision supplied by the
private Runtime boundary; the SQLite writer independently verifies the exact terminal
child Attempt and matching session before persistence. The service canonicalizes and
digests the bounded envelope, and emits only the child/task IDs, result status, revision,
digest, and aggregate version in `delegation.result.published.v1`; summary and raw output
remain in the immutable envelope state blob. The typed internal `result(...)` read uses
the owner/Workspace-scoped storage query and rejects a mismatched TaskSpec revision.

The SQLite adapter commits the result row and `DELEGATION_RESULT` aggregate event in one
transaction, stores publisher session/Runtime/incarnation pins, returns the original event
for exact same-publisher replay, and rejects changed content or publisher identity. Both
replay and owner read verify that the aggregate-state blob exists and its canonical bytes,
media type, size, and digest match the immutable row. The v24 migration supplies composite
Attempt, Task/Workspace, and AgentSession foreign keys plus immutable update/delete guards.

## Parent-scoped result consumer extension (2026-10-17)

The internal read context now carries authenticated Workspace owner, Workspace, Task,
parent Attempt, child Attempt, and the pinned TaskSpec revision. The SQLite adapter verifies
the owner and exact Task/result revision, then proves the child Attempt points to that

## DelegationChannel durable result adapter (2026-10-18)

Added `DelegationChannelResultReader<S>` for the existing `result(child_attempt_id)`
operation. The Runtime constructs a `DelegationChannelParentScope` from the authenticated
parent AgentSession; the reader binds owner principal, Workspace, Task, parent Attempt and
pinned TaskSpec revision once, then accepts only the child Attempt ID per result lookup.

canonical digest verification, and the existing parent-scoped storage query. SQLite still
rechecks actual Workspace ownership, parent-child Attempt provenance and session/revision

## Task-wide versus profile concurrency correction (2026-10-19)

Review found that the pure admission policy incorrectly folded the selected profile's
`max_concurrency` into the Task-wide active-child ceiling. The contract makes Task and
Coworker limits aggregate across profiles, while a profile limit applies only to active
Attempts using that profile. The evaluator now computes the aggregate ceiling from the
platform, Task and pinned Coworker limits, then independently compares the selected
profile's active count to its own limit. This prevents a profile configured for one child
from throttling unrelated profiles while preserving both caps.
