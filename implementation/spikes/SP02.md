# SP02 — SQLite adapter qualification

Status: **PARTIAL; rusqlite remains provisional and is not production-qualified.**

Checked 2026-10-06 on Ubuntu 24.04.4 LTS under WSL2, x86_64, Linux
6.18.40.1-microsoft-standard-WSL2, Rust/Cargo 1.98.1. Production `storage-sqlite`
continues to enable its `sqlite-bundled` feature by default. The controlled comparison
builds both standalone drivers against the host SQLite shared library, version **3.45.1**;
runtime `sqlite_version()` and `ldd` confirmed that both test executables load
`libsqlite3.so.0`.

## What was compared

The isolated executables live in
[`sp02-driver-compare`](sp02-driver-compare/README.md) because SQLx 0.9.0 and rusqlite
0.40.2 resolve incompatible `libsqlite3-sys` versions and cannot link into one process.
They use separate Cargo lockfiles and targets.

Both sides exercise the same `domain_workspace::WorkspaceService` and the production
`FileBlobStore` implementation (`crates/storage-sqlite/src/blob.rs`):

1. Create eight Workspaces before measurement.
2. Run eight concurrent producer threads, each updating one Workspace with alternating
   replication policy. Every update performs the same domain validation/read, canonical
   aggregate serialization, encrypted content-addressed blob write, durable blob readback
   and verification, then the atomic projection/origin-sequence/event commit.
3. Use WAL, `synchronous=FULL`, a 5-second busy timeout and a 32-slot bounded writer queue.
4. Close the adapter, reopen the same database and blob directory, verify the active
   projection, decrypt every aggregate-state blob, replay each event stream and compare the
   replayed aggregate to the persisted projection.

The rusqlite side uses the actual product `SqliteWorkspaceStore` with its default bundled
feature disabled **only for this qualification executable**. It retains rusqlite's
`cache` and wasm-compatible default features. The bundled-dependent `modern_sqlite` feature
is not enabled against the older system library, avoiding newer compile-time bindings than
SQLite 3.45.1 supplies; the storage adapter does not call those modern-only APIs. The SQLx
side is an experimental adapter implementing the WorkspaceStore ports around a SQLx
connection on a dedicated writer thread; it reuses the same domain service and production
FileBlobStore source. The SQLx prototype applies the canonical v1 DDL, but it does not
implement the product adapter's migration receipts/schema-drift checks, production
path-permission checks, complete error mapping, or root-scope reads. This is a comparable
commit/reopen workload, not proof that SQLx is a drop-in production adapter.

## Results

Three sequential optimized runs per driver, 200 updates per run. Runs alternated between
drivers on the same machine. End-to-end latency includes domain service calls, aggregate
canonicalization, encrypted blob write/read verification and database commit. It excludes
Workspace setup and reopen/replay validation. The benchmark intentionally reports no
synthetic queue-wait metric; the product adapter does not expose one.

| Driver | SQLite | Throughput updates/s | End-to-end p50 (ms) | End-to-end p95 (ms) |
|---|---:|---:|---:|---:|
| rusqlite 0.40.2 | 3.45.1 | 312.1, 333.4, 327.4 | 24.352, 22.834, 22.716 | 39.010, 35.274, 36.754 |
| SQLx 0.9.0 prototype | 3.45.1 | 309.2, 322.9, 323.8 | 24.121, 23.487, 23.780 | 34.681, 34.187, 31.565 |

Median throughput was 327.4 updates/s for rusqlite and 322.9 updates/s for the SQLx
prototype. The results are close and the ranges overlap; this is **not enough evidence to
select a driver on performance**. All six benchmark runs reported eight replayed
Workspaces and `replay_matches=true`.

The workload is intentionally small and single-host. It does not qualify mixed reader /
writer load, memory, shutdown/cancellation under load, realistic large event payloads,
backpressure under sustained overload, disk-full behavior, or production key management.
The SQLx adapter is also less complete than the product adapter, so timing differences may
reflect adapter implementation quality as well as the driver.

## Reproduction

Run test suites:

```sh
cargo test --no-default-features --features sqlite-rusqlite-defaults -p storage-sqlite
cargo test --locked --manifest-path implementation/spikes/sp02-driver-compare/Cargo.toml
cargo test --locked --manifest-path implementation/spikes/sp02-driver-compare/rusqlite/Cargo.toml
```

Build release executables once, then run each command three times in alternating order to
reduce ordering bias:

```sh
cargo build --release --locked --manifest-path implementation/spikes/sp02-driver-compare/Cargo.toml
cargo build --release --locked --manifest-path implementation/spikes/sp02-driver-compare/rusqlite/Cargo.toml
implementation/spikes/sp02-driver-compare/target/release/sp02-driver-compare 200
implementation/spikes/sp02-driver-compare/rusqlite/target/release/sp02-rusqlite-qualification 200
```

The rusqlite executable selects system SQLite through `storage-sqlite`'s
`--no-default-features` dependency while explicitly retaining the rusqlite cache and
wasm-compatible default capabilities. The SQLx manifest enables `sqlite-unbundled` without
SQLx's `sqlite` convenience feature (which also enables bundled SQLite). Confirm both
runtime versions match and both binaries link `libsqlite3.so.0` before collecting samples.

The product adapter's focused recovery test remains:

```sh
cargo test --locked -p storage-sqlite workspace_create_update_restart_and_projection_replay_match -- --nocapture
```

## Still open

- Mixed read/write contention, sustained backpressure, memory use, shutdown/cancellation,
  large payloads and actual disk-full fault injection.
- SQLx product-grade migrations, schema validation, path hardening, full error mapping,
  root-scope support, and parity fault-injection tests.
- Independent repeat on the owner's supported desktop OS and a cloud host.
- Production `WorkspaceBlobKeyProvider` qualification for each desktop OS/cloud deployment,
  including key rotation, unavailable/revoked keys, recovery/deletion and backup/restore.
- Independent cryptographic review. Fixed test keys are benchmark-only and not suitable for
  production.
- E01-S01 owner acceptance and hosted GitHub Actions. E01-S02 remains in progress and
  owner acceptance is pending.

Do not change the product driver decision from these samples alone. If later measurements
or Runtime integration justify another adapter, implement the full contract and compare it
under the same system SQLite version and real workload before switching.
