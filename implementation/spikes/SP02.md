# SP02 — SQLite adapter qualification

Status: **PARTIAL; rusqlite is provisional, not production-qualified.**

Checked 2026-10-06 on Linux. The current slice uses Rust 1.98.1, Cargo 1.98.1,
`rusqlite` 0.40.2 with its bundled SQLite 3.53.2, and a bounded synchronous writer
actor. `StateStore` owns the atomic aggregate/event commit; `EventStore` reads the
immutable Workspace stream; both are composed by the storage adapter. No SQL transaction
spans filesystem or key-provider work.

## Evidence completed

- The actual `docs/schemas/sqlite-v1.sql` is applied inside a migration transaction.
- Migration metadata records the source checksum, resulting schema fingerprint and
  version; startup rejects schema drift and a newer unsupported `user_version`.
- A failed migration rolls back its DDL and can be retried.
- The SQLite adapter tests verify expected-version races, transactional rollback after
  aggregate/sequence/event writes, a bounded busy timeout, restart/replay, event sequence,
  and blob failure before aggregate commit.
- The file BlobStore encrypts content using an injected versioned key provider, verifies
  plaintext digest/size on read, scopes object paths by Workspace and purpose, rejects
  wrong-scope/missing blobs and corrupted ciphertext, and fails closed on broad Unix
  purpose-directory permissions. Its tests use a fixed test-only key.
- JCS object ordering and number formatting are checked with an RFC 8785-style fixture.

### Isolated SQLx prototype (exploratory; not a driver selection)

The experiment now includes separate SQLx and rusqlite executables under
[`sp02-driver-compare`](sp02-driver-compare/README.md). Separate Cargo processes are
required: SQLx 0.8.6 requires `libsqlite3-sys` 0.30.1 while rusqlite 0.40.2 requires
0.38.2, and SQLx 0.9.0 allows versions below 0.38.0 while rusqlite still requires 0.38.2.
Cargo rejects these in one target because both packages link the same native `sqlite3`
library. The harnesses use separate lockfiles and binaries; they are not product adapters.

Each harness applies the same v1 DDL and transaction shape: one bounded writer, WAL,
`synchronous=FULL`, eight concurrent producers, a 32-entry queue, Workspace projection
version update, Workspace/origin sequence increment, one event insert, commit, close,
reopen, and persisted version/event-count check. This final check is named
`restart_state_matches`; it is not event replay. The SQLx harness also injects a failure
after projection and sequence writes and verifies all three durable values roll back.

Three 1,000-write optimized runs per executable were performed sequentially on Ubuntu
24.04.4 LTS under WSL2, x86_64, Linux 6.18.40.1-microsoft-standard-WSL2, Rust/Cargo
1.98.1:

| Driver | SQLite | Throughput per second (runs) | Commit p95 (runs) | Queue wait p95 (runs) |
|---|---:|---:|---:|---:|
| SQLx 0.9.0 | 3.51.3 | 243.5, 273.4, 281.7 | 6.581, 6.159, 5.880 ms | 40.917, 37.645, 34.846 ms |
| rusqlite 0.40.2 | 3.53.2 | 363.9, 298.3, 385.1 | 4.833, 6.505, 4.724 ms | 31.431, 47.365, 29.734 ms |

These figures are directional only. The SQLite patch versions differ because the link
constraints prevent a shared library version in the current dependency pair. The harness
also excludes encrypted aggregate-state blob writes/verification, mixed read traffic,
process cancellation/shutdown timing, realistic event payload serialization, memory
sampling, and OS-level disk-full behavior. It therefore does not establish that rusqlite
is faster for LiteCowork's full storage workload and does not close SP02.

Reproducible focused command:

```sh
cargo test --locked -p storage-sqlite workspace_create_update_restart_and_projection_replay_match -- --nocapture
```

Run the isolated reduced driver experiment and its checks using the commands in the
[spike README](sp02-driver-compare/README.md). Those outputs qualify only the prototype
transaction path and must not be substituted for product adapter acceptance.

Observed summary:

```text
storage replay: sqlite=3.53.2, workspace=workspace-persist, version=2, policy=METADATA_ONLY, events=2, replay_matches=true
```

## Not completed

- No comparable full-adapter SQLx implementation exists; the isolated prototypes do not
  contain the encrypted BlobStore path or production StateStore implementation. The
  choice between rusqlite and SQLx remains provisional.
- The isolated workload measures bounded-queue wait and commit latency, but does not yet
  qualify mixed reader/writer contention, memory, cancellation/shutdown, or adapter-level
  backpressure under realistic event/blob sizes.
- No real database or filesystem disk-full fault injection was run. The test suite checks
  injected transaction rollback and a BlobStore that fails before SQL admission.
- No production OS keystore/cloud key-service provider, key rotation/recovery workflow,
  or independent cryptographic security review exists. A test key is not acceptable for
  production.
- No `litecoworkd` process, Operator transport, desktop UI, or real external provider is
  wired to Workspace storage in this story slice.
- E01-S01 owner acceptance and GitHub Actions remain pending; E01-S02 is not owner
  accepted.

## Decision and next experiment

Keep rusqlite 0.40.2 as the implementation candidate because a bounded synchronous writer
matches SQLite's single-writer transaction model and already passes the contract-schema
and recovery tests. Do not describe it as the final stack choice. The isolated SQLx sample
demonstrates that the same core transaction shape is implementable, but its measurements
are confounded by differing bundled SQLite versions and omit product blob work. Next,
qualify both adapters with controlled SQLite versions and the complete Workspace commit
path, then measure mixed reader/writer load, memory, cancellation/shutdown, backpressure,
and busy/error behavior. Revisit only if measured product workload or Runtime integration
needs async I/O.

Before shipping encrypted blobs, qualify a production `WorkspaceBlobKeyProvider` on each
supported desktop OS and cloud deployment, then test unavailable/rotated/revoked keys and
backup/restore behavior. Keep that qualification as a production release gate; do not add
plaintext fallback.
