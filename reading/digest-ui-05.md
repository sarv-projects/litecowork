## Cross-cutting observations

1. **Two transport layers, both narrow.** (a) `invoke<TauriCommand>` for resources/approvals/notifications/artifacts/automation/suggestions/discover; (b) an injected `(path, init) => Promise<Response>` `Transport` for the API-client modules, whose desktop adapters (`desktop-notification-api.ts`) parse path+headers+body and call one fixed command with named args, then `operatorBridgeResponse` rebuilds a `Response` from base64 (2 MiB cap). Evidence of the design intent in CODE: comments say the WebView "cannot supply a method, URL, header, install action, or provider". This matches ARCHITECTURE.md §2 ("credentials never enter public projections") and §6 (brokered HTTP).
2. **Uniform server-side distrust.** Every domain decode re-checks the Workspace id on every item (`coworker-api`, `routine-api`, `notification-api`, `goals`, `artifact`, `suggestions_bridge`, `discover_bridge`), validates `sha256:` digests with the identical 71-char rule (Rust `valid_digest` ↔ TS `DIGEST`), and uses `cache: "no-store"` client-side plus `cache-control: no-store` enforcement in `approval_bridge`.
3. **Generation-counter fencing is the dominant concurrency idiom.** ~10 independent fences: `resourceReadRequest`, `resourceSelectionGeneration`, `headPreviewRequest`, `comparisonRequest`, `locationsRequest`, `deletionStatusReadSequence`, `GoalPage.generation`, `ApprovalDetail.generation`, `CoworkerRosterRequestEpoch`, `WorkspaceListRequestFence`, `TaskAttentionPaginationGate`, `resource-search-request`. The CDP tests exist specifically to prove late responses cannot cross a Workspace/generation boundary.
4. **Idempotency identity is first-class UI state.** `PendingApprovalDecision` in `sessionStorage` (`litecowork:approval-decision:v1:`), `pendingGoalMutations` in-module (cap 32, pub/sub, explicit "discard retry identity"), `revisionUploadRecoveries` in-module, `workspaceRootScanRequest` map, `getOrCreateInstructionSave`. All reuse the original id on retry and refuse to silently replace a different pending change.
5. **Honesty rules are enforced in code, not prose.** "Unknown is not success" shows up as: `planning-readiness` refusing any execution-attempt flag; `GoalsPage` "No percentage or completion is inferred"; Needs You "Showing the last saved open items" + "offline never infers an empty inbox" (asserted in CDP); `projectPresentationEntries` keeping a visible `REJECTED` placeholder (UIV1-054); `rich-presentation` refusing to render tables/slices that do not exist verbatim in the semantic message.
6. **Divergences from repo invariants / doc-vs-code gaps.**
   - `SettingsView.tsx`: 5 of 9 categories are cosmetically non-functional; a comment claims localStorage persistence that does not exist; "Clear All Data" reports "permanently removed" while performing no effect; static success badges (`Windows Job Object Active`, `Windows Credential Store`, `Service Integrated`, `Enforced (TLS Verified)`) read as observed state. Under the repo's evidence vocabulary these are UI claims with **no CODE path behind them** — the clearest place where the UI outruns the implementation.
   - `automation_bridge.rs` doc comment says definition writes "remain paused" while `create/revise/pause/resume/disable` are implemented (stale comment).
   - `ArtifactLibrary.loadMore` clears the list on pagination error, inconsistent with the retain-snapshot policy asserted elsewhere.
   - `workspace-root-scan.ts` duplicated `entriesExamined >= 0` guard.
   - `settings-view.css` bypasses the design-token system used by every other stylesheet; `ZCode`/`Cockpit` provenance comments survive in `SettingsView.tsx` and `settings-view.css`.
   - Test-harness config ≠ production config: CDP/Vite tests use `configFile: false` with inline `@vitejs/plugin-react`, so `vite.config.ts` is never exercised.
   - Three CDP tests, three missing-Chrome policies: `needs-you-page-interaction` **throws** (`Set LITECOWORK_CHROME…`) → hard failure; `task-attention-page-pagination` skips; `resource-editor-race` skips only when `LITECOWORK_CHROME` is unset and the error contains `ENOENT`.
