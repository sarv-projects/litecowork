## 4. Optimization notes

- The TypeScript validator computes one SHA-256 per TEXT_SLICE; for 200 slices this is the main cost. If AC-016 fails, hash the encoded document once and verify slice ranges against that buffer instead of re-encoding.
- Move validation to publish time in Rust so the desktop's work is a confirmation pass on already-valid documents; rejected documents never cost render time.
- Keep chart geometry and the calculator reducer as pure TypeScript modules so they run under `node --test` without a DOM.
- Do not split rendering into a Web Worker unless the 100 ms long-task budget fails on the release-row machine.

ACP does not guarantee a universal presentation payload, dashboard schema, or subagent list. The current LiteCowork ACP path still has no structured UI ingress and no production RichPresentation publisher. A2UI is therefore an optional adapter candidate only: it must be version-pinned, provider-carried, bounded to LiteCowork's canonical component profile, normalized and provenance-correlated, and tested for unsupported/replayed input before any use. AG-UI is an agent/frontend event exchange design, not an ACP replacement; MCP Apps provide tool-owned embedded UI and are not the default answer renderer. No protocol name by itself proves support in OpenCode or another native harness.

Official A2UI material was rechecked on 2026-11-17. Its protocol v1.0 describes streamed declarative surfaces and optional bidirectional function calls ([protocol](https://github.com/a2ui-project/a2ui/blob/main/specification/v1_0/docs/a2ui_protocol.md), [version index](https://github.com/a2ui-project/a2ui/blob/main/docs/public/index.md)). Official sources still disagree about shipping status: the index calls v1.0 current, while the [README](https://github.com/a2ui-project/a2ui/blob/main/README.md) calls v0.9.1 the production release and the [renderer guide](https://github.com/a2ui-project/a2ui/blob/main/docs/public/guides/renderer-development.md) labels v1.0 candidate. This is a reason to pin an exact release/tag and conformance corpus before any adapter adoption, not a reason to add the A2UI runtime now.

Agent-produced progress and subagent claims must retain producer identity and their owner-provided evidence. Native harness subagents remain Feature 001 session/projection facts; admitted Task workers remain Feature 015 Attempt/AgentNode facts. A generated presentation cannot create worker state, Task progress, approvals, permissions, Effect receipts or Artifacts. The contextual right pane and live computer preview remain Feature 008 concerns with separate local observation consent; a rendered card cannot start screen capture, a browser, a terminal, or a computer action.

### 9.4 HLD/LLD, contracts and test gaps exposed by the review

The existing Feature 016 SPEC, DATA-MODEL, WIRING and contracts already define the service boundaries, message/presentation identities, closed document model, immutable publish/read lifecycle, semantic fallback, trust boundary, error handling and release gates. The blueprint does not justify duplicating those into a new global UI service or schema. The work that survives review is to sharpen implementation evidence under the existing owners:

- **UI/UX:** provide clear semantic-first loading and per-block fallback; preserve the original response; keep generated content display-only; use host controls for user actions; keep expandable Canvas identity and local state only if T21 is later accepted. Current rich UI is not published in production.
- **LLD/parser:** implement AC-019's explicit Markdown subset and per-block failure. Keep parser complexity bounded by the existing document/content budgets; never return generated HTML; make code highlighting lazy and React-node based; ensure unsupported syntax falls back safely without hiding valid neighboring blocks.
- **Contracts:** do not invent a universal event, `SurfaceSpec`, generic component action, agent graph or MCP request. Any new protocol input must map to canonical intent/RichPresentation and preserve correlation, digest, size, replay and error semantics. A-85 blocks model-visible MCP proposal input.
- **Tests:** AC-019 needs representative real-agent corpus cases for GFM tables, horizontal rules, nested lists, language-tagged code, unsupported block-local syntax, unsafe URLs, HTML/script-looking text, and TEXT_SLICE parity. Add accessibility and loading/recovery evidence under authorized T18; no test here establishes packaged provider support.
- **Delivery:** no package/dependency is adopted from the blueprint. Any future Markdown/math/highlighter dependency needs exact version/license/pin, bundle/performance measurements, safe React-node output and accessibility review. Existing contracts and source paths are the baseline to change, not the proposed Next.js/server/database stack.

**Decision at that checkpoint:** retain the blueprint as product and implementation research; keep current architecture and canonical schemas; correct T18's stale source paths; do not implement Feature 016 renderer or provider ingress while T01/T25 and their dependencies remain blocked. That review added no API, event, schema, dependency, model call, permission, persistence behavior, owner acceptance or qualification. The later revision 0.3 proposal below records the owner's follow-up to broaden design scope, still without implementation authority.
