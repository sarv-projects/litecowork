## User outcome

LiteCowork starts with the user's selected native agent and presents its answer as readable conversation, useful structured content, or a safe interactive view when the committed answer supports one and the target profile enables it. An eligible view can expand into the contextual Workbench Canvas without changing its message identity or current in-session values. The owner directed Saved Views to remain in V1 and Feature 007 B-21 to be amended. Under A-84, a separate explicit Library save may opt in to compatible numeric input values inside the immutable ArtifactVersion; the component remains transient and non-submitting under B-40. Unsupported agents and malformed proposals still produce a complete readable semantic answer. No generated executable code runs in the chat WebView; executable Artifact Runtime remains separately gated and PREVIEW_ONLY in V1.

## Current truth

The TypeScript contract validator (`apps/litecowork-ui/src/presentation/rich-presentation.ts`) accepts the same renderer-v1/v2 document profiles as the pure Rust `domain-presentation` validator under the shared 512 KiB cap. Both iterate one golden corpus. The response parser and React renderer expose v2 METRIC, CHART and SAFE_CALCULATOR. SAFE_CALCULATOR is CODE/UI from T07: the component uses bounded numeric input, the pure CalcAst evaluator, transient state, formula text, reset and a visible semantic fallback; it makes no host/provider calls or durable writes. CHART is host-generated static SVG with an accessible exact-data table. METRIC displays one exact bound numeric cell, derives its measure label from source headers/rows, and requires declared unit/scale/time-interval/aggregation context grounded in the exact semantic answer; it performs no unit conversion, scaling or aggregation. This guards against presentation-added meaning but does not independently fact-check semantic claims or complete the derived analytics in T20/T24. These components are CODE/UI only: the table-only post-commit binder exists, but it does not produce metric/chart/calculator intent, so those components are not yet reachable from provider answers. T09 now adds a Settings > General local display preference that defaults on for legacy snapshots and, when off, selects semantic-only rendering, suppresses new optional projection reads and discards late in-flight results. It is separate from the turn-captured provider presentation preference. The named keyboard control, local reload behavior and explicit session-only notice after a failed storage write have rendered CODE/UI evidence; packaged E2E-11 remains open. There is no image component, media ingestion or qualified Interactive Artifact Runtime. The T18 semantic Markdown renderer supports its bounded display-only subset and does not publish RichPresentation; focused unit and rendered-browser checks pass, while the real native-agent answer corpus remains outstanding. The read route and semantic fallback view exist.

Under this package's IN_REVIEW status, proposed task P-03 is folded in as 016-T18: per-block Markdown degradation with GFM tables, horizontal rules and nested lists; code blocks with a language label, copy button and lazy highlighting; TEXT_SLICE rendered through the same renderer; and a golden corpus of real agent answers that renders with no whole-message raw fallback and no HTML strings. The renderer and authored adversarial fixtures are implemented; actual native-agent answer capture and corpus review remain open. ## Revision 0.4 design review

The proposal treats semantic answers, registered interactive views, expanded Canvas and Saved Views as one conversation-first experience with staged delivery. The same canonical RichPresentation document remains the only UI tree; provider adapters may supply optional structured intent, while deterministic host formatting and the complete semantic answer serve routes without that capability. The user delegated implementation of the complete current proposal, recorded in A-84. This does not satisfy T01 formal acceptance or T25 cross-owner review and does not establish provider evidence or release qualification. T02 contract promotion and each task's own dependencies govern implementation. See SPEC §20, PLAN, TASKS and the ACP presentation pipeline LLD.
