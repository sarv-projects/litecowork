## 5. Desktop Conversation UI audit (historical; superseded by section 0)

The desktop source was traced from the active-turn projection through the composer, stop action and generated API contract. The current UI does not complete the target stop/retry contract:

1. `ConversationTurnPresentation` in `apps/litecowork-ui/src/api/operator-api.ts` exposes only `turn_id`, `status`, `retry_ordinal` and `presentation_preference`. It does not expose the aggregate `version` required by `If-Match` on retry/cancel. The UI therefore cannot construct a valid optimistic-concurrency precondition from its active-turn snapshot.
2. `ConversationsPage.tsx` computes `isTurnRunning` from transient STREAMING/RECONNECTING frames or snapshot status RUNNING. However, `cancelTurn` searches only `transientTurns` and returns immediately when none exists; it does not fall back to `currentSnapshot.active_turn`. The current Operator does not emit the documented `turn.delta` / `turn.settled` native token stream, so the normal OpenCode execution path can show the Stop button from the durable RUNNING snapshot while providing no transient turn for the handler to cancel.
3. When a transient turn does exist, the UI sends `expectedVersion: 1` unconditionally. The storage activation transaction advances a newly admitted turn from version 1 (OPEN) to version 2 (RUNNING), so the normal running turn is already stale against this precondition. A valid cancel must use the current authoritative turn version and then wait for supervisor-observed native stop/quiescence; the current backend instead immediately settles CANCELLED.
4. The generated OpenAPI TypeScript surface includes `retryConversationTurn`, but repository-wide source search found no desktop source or test call site for it. The Conversation page has no failed-turn retry action or UI flow, despite the API route being registered.
5. The composer treats only RUNNING or a transient stream as active. OPEN is labelled “Preparing” but is not included in `isTurnRunning`, so the Send control remains available during durable OPEN admission. WAITING_USER, WAITING_DEPENDENCY and CANCEL_REQUESTED are also not included in the send guard. This contradicts the strict single-flight B-01 interaction contract and becomes observable because storage currently admits multiple nonterminal turns.
6. The optimistic USER message is appended before the POST and removed/restored only on request failure; the UI does not visibly reconcile the accepted `ConversationTurnReceipt` into a local active-turn projection. It relies on subsequent projection delivery. Since the native transient stream is not emitted, progress/stop behavior must be qualified against the durable projection path, not inferred from the optimistic bubble.

These are source-level UI findings, not a browser USER test. They require UI/API contract changes and rendered regression tests after the backend lifecycle is corrected. Do not paper over them by inventing a version or treating a transient stream sequence as the aggregate version.

## 6. Important contract mismatches/gaps (historical; superseded by section 0)

1. The actual Operator path bypasses the target AgentTurnCoordinator and starts AgentSessionSupervisor directly with detached `tokio::spawn`; no durable dispatch intent/outbox/claim is committed with USER+OPEN.
2. Exact idempotent replay returns the 202 receipt without proving a dispatch worker exists. No Runtime-startup sweep for orphaned OPEN turns or STARTING Conversation sessions was found.
3. `create_conversation_turn` inserts a new OPEN turn but has no same-Conversation nonterminal-turn guard; no matching active-turn unique constraint was found. The accepted B-01 strict single-flight rule is therefore not enforced in the storage admission boundary.
4. Retry is inconsistent: Operator's `TurnCommand::Retry` sets the turn RUNNING and assigns a new session ID before dispatch, while `start_conversation_agent_session` requires the turn to remain OPEN with no session pointer. The supervisor start call can therefore reject the retry before provider dispatch.
5. Running cancellation is inconsistent with the state-machine owner contract: the Operator transitions RUNNING -> CANCEL_REQUESTED and immediately settles CANCELLED in the same request path; no native interrupt/quiescence observation is made before terminal settlement.
6. Several errors before the supervisor's `execute_agent_turn` error-handling block (host resolution, profile lookup, host-instance setup, STARTING reservation) can return to the detached caller, where the Operator only logs them. Such failures can leave the durable turn OPEN; the error path inside the supervisor is not a substitute for startup recovery.
7. The OpenCode code path is real but only CODE-level. It is not the declared generic framed Adapter 1.0 route, and the source has no Claude Code/Codex/Gemini/Cline Conversation dispatch qualification.
8. The final-result SQLite transaction exists, but its current typed request lacks explicit retry ordinal/provider-response identity; author JSON is passed through from the caller. Existing test coverage is focused rather than complete transaction fault injection.
9. OpenCode/Codex transport input is 256 KiB while product ConversationContextPackage allows 4 MiB. Need an explicit provider/context reduction contract.
10. Native output is not authority/effect proof. Durable projection should remain the user-visible source of truth.
11. The active-turn projection omits the aggregate version needed by the If-Match contract; the UI cannot safely cancel/retry from the projection it currently receives.
12. The Stop control is not connected to the durable active-turn identity: it searches only transient stream turns, while the current Operator does not emit the transient native token frames that would populate that collection.
13. The Stop request hardcodes expected version 1, but activation advances the turn to version 2 before RUNNING; even a populated transient turn would submit a stale precondition.
14. The retry route is present in generated API types but has no desktop call site or failed-turn retry UI. Composer activity guards also omit OPEN, WAITING_USER, WAITING_DEPENDENCY and CANCEL_REQUESTED.
15. UI source assertions and reducer tests do not substitute for rendered browser tests of stop/retry, stale version, repeated send, and accepted-turn reconciliation.

### 8.1 Finding for 001-T12 and T27 (rechecked 2026-11-11): pinned OpenCode v2.0.32 contracts

The prior text overstated the absence of a native answer contract. Read-only inspection of the official `anomalyco/opencode` tag `v2.0.32` source confirms a session Form contract: `packages/schema/src/form.ts` defines `form.created`, `form.replied`, and `form.cancelled`, a pending/answered/cancelled state, and an answer keyed by field. `packages/protocol/src/groups/session.ts` defines session form routes, and `packages/server/src/handlers/session.ts` implements ownership checking for get/reply/cancel. The same pinned source defines native permission request/reply contracts: `packages/protocol/src/groups/session.ts` defines session permission routes and `packages/server/src/handlers/permission.ts` checks both session and request identity before forwarding the decision to the native Permission service. These are source-contract findings only; no OpenCode session was run and no HTTP request/reply was exercised here.

This evidence does not establish that the current LiteCowork `/api/event` reader receives the right `form.created` payload for provider-generated input in the per-turn server, nor that every form represents an interruption that should become a LiteCowork UserRequest. The reducer currently recognizes neither Form events nor their terminal events. At the earlier audit, the permission fixture lacked `action` and `resources`; it is now corrected to the pinned event shape and covered by bounded normalizer tests, but remains synthetic rather than a captured provider event. T12 remains BLOCKED pending an exact pinned-server event capture, a decision mapping only genuine provider input requests to B-06 (with its Runtime-local key and acceptance/rejection/ambiguity handling), and integration evidence. A native permission is still distinct from a UserRequest and must never become a LiteCowork grant or Effect.

For T27, “no supported OpenCode permission reply API” is disproved at the pinned source-contract level. Additional review of the v2.0.32 tag confirms these details:

- `permission.asked` is an ephemeral event whose request has `id`, `sessionID`, `action`, `resources`, and optional `save`, `metadata`, `source`; the core request can also carry an optional `message`. The T27 normalizer now validates bounded `id`, correlated `sessionID`, `action`, `resources`, and optional `message`, while discarding other fields; its synthetic fixture is shape coverage, not a live capture.
- `POST /api/session/{sessionID}/permission/{requestID}/reply` accepts `decision` (`once | always | reject`) and optional `message`, and returns no content. The handler checks that the pending request exists and that its `sessionID` equals the path session before forwarding the decision.
- Exact route definitions are in [`packages/protocol/src/groups/permission.ts`](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/protocol/src/groups/permission.ts) (not `groups/session.ts`): `GET /api/session/:sessionID/permission`, `GET /api/session/:sessionID/permission/:requestID`, and `POST /api/session/:sessionID/permission/:requestID/reply`. The pinned [permission handler](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/server/src/handlers/permission.ts) lists by session; get/reply both call `requireOwnedRequest`, which compares the pending request's `sessionID` with the path. The current LiteCowork transport has bounded list/get/reply methods, and the active turn worker now invokes reply/list through the bounded mailbox; coverage now includes synthetic state/reconciliation, negative route tests, an authenticated POST-to-worker receipt/replay test and a mailbox-close-after-dispatch race test, both with seeded prompts and a fake provider; neither is a successful real-provider decision.
- `once` resolves only the selected request. `reject` rejects the selected request and every other request currently pending in that same session. `always` can save the request's `save` scope and automatically resolve other pending requests that become allowed by the saved rule. It is therefore not a harmless per-request button; omit it from the basic V1 prompt unless a separately reviewed, explicit persistent-rule flow is added.
- The pinned core contains no elapsed-time timeout/default for a pending permission. A permission remains pending until replied to or the Permission service closes; service close emits rejection for each pending request. Therefore T27's former acceptance wording, “times out to the harness default,” is unsupported. An app-side timer must not silently invent that behavior. The target must keep the request actionable while the native session is live, or expose an explicit Stop/close path whose provider result is handled as session termination.
- The next implementation must correlate the exact Workspace, Conversation turn, native session and request in daemon-owned ephemeral state; it must not turn the request into a LiteCowork UserRequest/grant/Effect or persist raw resource paths, metadata, native handles or message text in ordinary activity records. UI detail should be a separately bounded/redacted projection. A lost reply acknowledgement cannot be labeled answered or denied merely because the HTTP call timed out; reconcile against the exact pending request while the same native session is live, otherwise retain an unknown/ended state and do not replay an uncertain decision.

The normalizer now validates the bounded v2.0.32 permission payload, and the active per-turn adapter has a bounded mailbox-backed reply path. Remaining gaps are a redacted live event capture, successful route-to-provider evidence, rendered allow-once and session-wide rejection controls, service-close/decision-state projection, and packaged denial, ambiguity, restart and reconnect recovery evidence. ACP `request_permission` is a separate harness path and is not a prerequisite for OpenCode's HTTP permission route. These are pinned source-contract facts, not live-provider or LiteCowork integration evidence. Sources: [v2.0.32 Permission schema](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.32/packages/schema/src/permission.ts), [permission routes](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.32/packages/protocol/src/groups/permission.ts), [permission handler](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.32/packages/server/src/handlers/permission.ts), and [permission service](https://raw.githubusercontent.com/anomalyco/opencode/v2.0.32/packages/core/src/permission.ts).

The implementation and UI design are recorded in [contracts/native-permission-design.md](contracts/native-permission-design.md). It deliberately keeps live prompts in Runtime-local memory, exposes only an opaque incarnation-scoped UI token, and labels OpenCode's reject action as session-wide for currently pending requests. This design does not revise the accepted Conversation aggregate or persist native permission state. The target API and transient-frame contracts were promoted through global owner docs, canonical schemas, UI ledgers and generated API types on 2026-11-15; the normalizer, Runtime-local registry and authenticated GET/POST handlers have CODE/SERVED partial evidence; the user journey and successful provider decision remain unimplemented/unqualified.

The pinned T3 runtime separates durable app thread/run/attempt identity from provider session/thread/turn/item identity. Its event sink commits normalized events, projections, command receipt and pending effects in one database transaction, then publishes and wakes workers after commit ([`EventSink.ts`](https://github.com/pingdotgg/t3code/blob/222288b00f9ed392e1e7352ad929c9ae9ac10cef/apps/server/src/orchestration-v2/EventSink.ts#L314-L341), [transaction and publication](https://github.com/pingdotgg/t3code/blob/222288b00f9ed392e1e7352ad929c9ae9ac10cef/apps/server/src/orchestration-v2/EventSink.ts#L763-L870)). Its outbox distinguishes process-bound effects from effects it considers safe to replay; recovery cancels process-bound work after server loss and only retries the explicitly replay-safe class ([`EffectOutbox.ts`](https://github.com/pingdotgg/t3code/blob/222288b00f9ed392e1e7352ad929c9ae9ac10cef/apps/server/src/orchestration-v2/EffectOutbox.ts#L35-L175), [recovery](https://github.com/pingdotgg/t3code/blob/222288b00f9ed392e1e7352ad929c9ae9ac10cef/apps/server/src/orchestration-v2/EffectOutbox.ts#L523-L550)). A repeated command ID resolves to its stored receipt rather than planning or performing the effect again ([`Orchestrator.ts`](https://github.com/pingdotgg/t3code/blob/222288b00f9ed392e1e7352ad929c9ae9ac10cef/apps/server/src/orchestration-v2/Orchestrator.ts#L15408-L15421)).

LiteCowork should treat these as cross-checks for its existing durable Conversation admission, idempotency, dispatch-intent and startup-recovery contracts. They do not authorize replacing canonical Conversation states or importing T3's run/effect protocol. T3's Stop is a durable command that cancels eligible work, holds queued work, and prevents late provider events from restarting stopped work ([`Orchestrator.ts`](https://github.com/pingdotgg/t3code/blob/222288b00f9ed392e1e7352ad929c9ae9ac10cef/apps/server/src/orchestration-v2/Orchestrator.ts#L13708-L13824)); LiteCowork Stop semantics remain those in the accepted Conversation contract and require its own provider quiescence evidence.

T3's environment is the server machine and its Project path is not a filesystem sandbox; its own security guide warns that an operating agent can have the server account's filesystem access ([`environment-auth.md`](https://github.com/pingdotgg/t3code/blob/222288b00f9ed392e1e7352ad929c9ae9ac10cef/docs/internals/environment-auth.md#L7-L23)). Do not transfer that trust model into LiteCowork: the local Workspace remains LiteCowork's security/resource boundary, and Core Trust authority covers only actions LiteCowork actually mediates. T3's server-side event pruning and remote-capable topology also do not change LiteCowork's local retention or V1 boundary. This is source comparison, not evidence of LiteCowork integration or qualification; the broader first-party T3 review remains in progress.

### Shared OpenCode host and per-session Workspace location (2026-11-14)

The host-reuse design was cross-checked against the pinned official OpenCode v2.0.32 source, rather than assuming the server's startup cwd can stand in for every session. `packages/core/src/session.ts` defines `CreateInput` with a required `location: Location.Ref` when creating a session without a parent; `Session.create` resolves the project from `location.directory` and publishes that location on the created session. Before the T04 change, LiteCowork sourced that field from the server's fixed `working_directory`. The adapter now accepts the revalidated Workspace path and `OpenCodeServer::create_session` validates and serializes it explicitly; its Windows fake-transport test sends two distinct roots through one server handle. A reusable host still needs two distinct values: a Runtime-owned neutral process startup directory and the revalidated Workspace root supplied for each admitted native session. The current per-turn launch continues to use the Workspace root as process cwd.

Remaining verification must run the exact request against pinned v2.0.32 with two different Workspace roots on one host, sequentially and with overlapping sessions if the provider supports concurrent requests. Session IDs, context and stream events must remain correlated to the turn's exact native session. If this pinned route cannot preserve session-specific locations, reuse across roots fails closed; do not silently fall back to server cwd. Current evidence is pinned source plus LiteCowork request-construction CODE; it is not a live provider test, integration result or qualification. Pinned source: [OpenCode v2.0.32 Session.create](https://github.com/anomalyco/opencode/blob/v2.0.32/packages/core/src/session.ts#L1303-L1321) and [create implementation](https://github.com/anomalyco/opencode/blob/v2.0.32/packages/core/src/session.ts#L1628-L1668).

#### Foreground server shutdown boundary (2026-11-14; pinned source recheck)

The official `v2.0.32` tag resolves to commit [`843a6c514e606b436a7fe713422ace0a93ad3d61`](https://github.com/anomalyco/opencode/commit/843a6c514e606b436a7fe713422ace0a93ad3d61). LiteCowork launches `opencode serve --hostname 127.0.0.1 --port ...` without `--service`; the pinned [serve command](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/cli/src/commands/handlers/serve.ts#L6-L16) maps that to `mode: "default"`. In [ServerProcess.run](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/cli/src/server-process.ts#L201-L208), only `mode === "service"` awaits the managed server's shutdown effect; default foreground mode awaits `Effect.never`. The pinned [protocol API group list](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/protocol/src/api.ts#L84-L108) does not include a global-dispose group. The CLI's [service stop command](https://github.com/anomalyco/opencode/blob/843a6c514e606b436a7fe713422ace0a93ad3d61/packages/cli/src/commands/handlers/service/stop.ts#L8-L14) asks the managed service registry to stop its service; it is not a per-process graceful-stop command for LiteCowork's foreground child.

Decision: do not call `opencode service stop` to reap a LiteCowork-owned child, because it targets the separate user-managed service; do not infer a `/global/dispose` API from other OpenCode versions or third-party route lists. Safe idle stop for the private foreground process still needs an exact OS-owned graceful-stop mechanism and process-tree proof before the 5-second grace/force-stop lifecycle can be implemented or claimed. This source finding does not prove signal behavior, does not change current process behavior, and is not provider integration or qualification.
