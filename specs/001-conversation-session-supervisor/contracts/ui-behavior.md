# UI behavior — Conversation Send and turn progress (Feature 001)

**Status:** ACCEPTED/LOCKED - owner-accepted 2026-11-09; authorizes implementation; not a claim of implementation or qualification. Binds UI to owner contracts; not pixels.  
**Normative UI indexes:** [V1-UI-SCREEN-CONTRACT.md](../../../docs/V1-UI-SCREEN-CONTRACT.md), [V1-UI-ACTION-STATE-LEDGER.md](../../../docs/V1-UI-ACTION-STATE-LEDGER.md) (UIV1-016–022, 049–057), [DESKTOP-SHELL-LLD.md](../../../docs/DESKTOP-SHELL-LLD.md), [NATIVE-COMPOSER-LLD.md](../../../docs/NATIVE-COMPOSER-LLD.md).

UI **renders** conversation projections and stream frames; **sends** typed Operator commands. It does not parse English error strings.

## 1. User flow and transitions

| Step | Screen / surface | Transition |
|---|---|---|
| F1 | Conversation route, composer visible | User has eligible binding or sees repair state |
| F2 | User edits draft | Local reducer only; no domain mutation |
| F3 | Send | Admission command → turn OPEN/RUNNING/WAITING_* per state machine |
| F4 | Streaming | Stream frames + projection reconcile; scroll policy per shell LLD |
| F5 | Stop | Cancel command; terminal turn settlement |
| F6 | Failure / ambiguous | Typed error + repair; draft preserved where specified |
| F7 | Reload / restart app | Read models + RESYNC_REQUIRED if stream gap |

No navigation to Task or Coworker is required for F1–F7.

### Message lineage projection (A-114 / T31)

The committed message view may render downstream actions only from the explicit same-snapshot `turn_status` carried by its message wrapper. The parser maps a missing legacy field to unknown/null. It must not derive completion from stream settlement, latest `activity_turn`, an active/retryable turn, message order, or local cache. Feature 005's Task promotion control is visible only for a committed AGENT reply with exact `turn_status=COMPLETED` and a loaded preceding USER message from the same `turn_id`; the promotion route revalidates all source facts transactionally. No Conversation or turn state changes when opening or saving the Task draft.

|---|---|---|

### New Chat first Send

With a Workspace selected and no Conversation selected, the composer behaves as a normal chat composer. Send/Enter submits one `CreateConversationFirstTurnRequested` command containing the current draft, selected text ResourceRefs, exact visible AgentBinding ID (including the Workspace-default choice) and presentation preference. The UI does not first create an empty Conversation and does not require a second Send. During submission it disables duplicate Send, preserves the draft/chips until a validated composite receipt arrives, and shows a clear pending/retry state on transport ambiguity. Tauri journals the exact request privately before dispatch. On success, it validates Workspace, Conversation, turn and USER-message identities, acknowledges the journal row, selects the new Conversation, clears the draft/chips, and reloads the durable presentation snapshot. A duplicate/restart retry reuses the journaled request ID/payload/binding; a committed user message is rendered from the projection, not a synthetic optimistic row.

The path uses `POST /v1/conversations/first-turn`. Denial or pre-commit failure leaves no Conversation and retains the draft and attachments; an authoritative typed 4xx clears the replay row so the user can correct the draft and submit under a new identity. A post-commit/lost-ack path keeps the same request for receipt replay; it must not change the key, payload or binding. A timeout, transport failure, 5xx or malformed success retains the journal. If a daemon response is invalid or outside the selected Workspace, the UI does not discard the user's input. Resource picker access is available for the unselected New Chat draft and remains scoped to the selected Workspace.

### A-119 / 001-T32 Runtime readiness

The Conversation composer enables a **new** Send and the FAILED-turn **Retry** control only when the local Operator is ready and the lifecycle view matches the exact `runtime_id`/`runtime_incarnation_id`, Runtime availability is `ONLINE`, and incarnation recovery is `READY`. Missing, loading, mismatched, degraded or unknown lifecycle state closes these controls and explains that Runtime status must be refreshed. The authenticated Operator passes its own identities to the owning SQLite transaction. Exact replay is resolved first; existing read-only ownership/admission/version/resource/binding checks follow; storage then rechecks current ONLINE/READY, `ready_at` presence and `stopped_at` absence before the first durable/blob effect. A racing or malformed lifecycle returns `503 RUNTIME_UNAVAILABLE` with no partial admission. This is CODE/SERVED operational readiness, not provider, package or qualification evidence.

The exact pending saved-send recovery action remains available under its existing Operator connectivity rule: it first tries to recover an already committed receipt using the original body/key. If no receipt exists, SQLite applies the fresh-work fence and refuses without writing. Stop, cancellation/settlement and read-only history are not disabled by this fresh-dispatch gate. Runtime operational readiness does not establish provider authentication or the G-09 qualified route; no qualification is claimed.
