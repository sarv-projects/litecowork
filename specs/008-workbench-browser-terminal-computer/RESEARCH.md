## Workbench React UI findings

- `WorkbenchPanel` is mounted by `App.tsx` as a right-pane component and is keyed by `selectedWorkspaceId`. It is resizable/collapsible and the Workbench view is conditionally mounted; closing it unmounts the component, and changing Workspace remounts it.
- The Files view is a filtered list of Workspace Resource projections. Clicking a row loads an exact ResourceRevision text preview through App callbacks. It does not read a live native filesystem tree or mount an Environment filesystem. File names and uploaded Resources are not proof of current disk contents.
- Browser uses `browserUrl`/`browserInputUrl` in React state and an HTML iframe with a sandbox attribute. Its default URL is `http://127.0.0.1:4242/v1/health`. This is a generic embedded WebView preview, not a Chrome session or managed browser. It has no provider tab/session identity, Chrome executable/version, managed profile, consent, CDP/Playwright transport, action lease, screenshot/DOM observation or history persistence. When switching to another tab, the conditional removes the iframe; returning creates a new iframe. Closing the pane or changing Workspace resets the component state.
- Terminal uses component-local `terminalScrollback`, `terminalInput`, `commandHistory` and `historyIndex`. `handleRunTerminalCommand` launches no child process and performs no IPC. `help`, `status`, `dir/ls`, `whoami` and `version` append hard-coded sample lines; `dir/ls` enumerates Resource records, not an OS directory; arbitrary commands append a fabricated “completed with exit code 0” message. The header and initial scrollback claim `pwsh 7 · Windows ConPTY`, `KILL_ON_CLOSE` and Job Object resource enforcement without a PTY process. The local history survives tab switches only because WorkbenchPanel remains mounted; it is not a resident shell. Closing the pane/Workspace switch loses it.
- Diffs has no selected source file (`selectedDiffFile` is always null). If a Resource preview exists, the code labels lines as additions/deletions on a fixed modulo pattern, not by computing a comparison. Without preview it renders a static example patch, and the summary is hard-coded `+4 additions / -1 deletions`. This is not a VCS diff, Resource revision diff or proof of changed files.
- `WorkbenchTab` declares `activity`, but no Activity navigation control, `setActiveTab("activity")` call or Activity render branch was found. The terminal branch is separate, Browser branch is separate, and final `else` renders Diffs. Activity is not a usable Workbench tab in this component.
- Computer controls do not appear as a live Workbench surface. The UI has no screen capture/input control provider path, and the backend probe cannot return READY on the current qualified platform set.

## Product viability assessment

- The shell/side-pane layout is a useful container, but the current Browser, Terminal and Diff views should not be presented as working automation/execution tools. The synthetic terminal success is a release-blocking truthfulness defect: it tells a user that arbitrary shell commands completed successfully when no process ran. The sample containment and memory-quota output is likewise unsupported.
- The current iframe can be retained as an explicitly named “embedded preview” mode, but it must not satisfy the Browser provider/control contract or be described as a managed Chrome session. The real provider must own profile, session, tabs, observations, consent and action execution. The display surface is a separate adapter.
- The Terminal pane needs a real daemon-owned PTY/ConPTY session service attached to the exact admitted Environment. UI mount/unmount and tab selection must not own the child process; close, detach, stop, Runtime restart and Workspace change need distinct lifecycle semantics. A Job Object badge without a process attached to it is not containment evidence.
- Diff and Activity must consume actual domain events, persisted Attempt/Effect/Artifact records, immutable Resource revisions or VCS changes. If the Activity view is moved to Work/Task detail by the screen contract, the Workbench should not retain a fake `activity` enum.
- Computer use is separately deferred/blocked until the OS permission provider and actual capture/input injection backend are qualified. Consent/policy data models alone cannot enable it.

## Alternatives and decisions

- Call the current iframe a full Chrome/browser automation surface: rejected. It is a generic embedded preview only.
- Treat local React scrollback as resident PTY: rejected. No process/session is created.
- Claim Job Object/KILL_ON_CLOSE based on the UI badge: rejected unless an actual terminal process is attached and exact containment is attested.
- Preserve fake terminal success for design polish: rejected. Unsupported or unavailable must be visible, and arbitrary commands must never return fabricated exit code 0.
- Build a separate browser/terminal security engine in the UI: rejected. Provider processes and actions belong behind daemon/Environment/Trust owners.

## Implementation language and reuse notes (2026-11-09)

- Diffs: `apps/litecowork-ui/src/artifacts/text-version-diff-model.ts` `lineDiff` is a bounded O(n x m) LCS table (`Uint16Array` rows) run on the UI thread. It is adequate for small Artifact previews. For Workbench exact-revision and VCS diffs, compute in the Rust daemon with a Myers/histogram algorithm (for example the `similar` crate, license to be checked at T15) under the same line/byte bounds, and send rows to the UI. This keeps untrusted revision bytes off the WebView thread and makes counts authoritative.
- PTY: Linux `openpty` is available through `rustix` (already a `litecoworkd` dependency with `fs`/`process` features; the `pty` feature must be added). Windows ConPTY uses `windows-sys` `CreatePseudoConsole` in `crates/windows-local-security`, which already has `spawn_kill_on_drop_job`, `kill_tree` and `wait_for_job_quiescence`. Prefer these over adding `portable-pty`, so containment receipts stay in one crate.
- Browser: REF-BROWSER-HARNESS is Python with pinned CDP dependencies. Do not ship a Python runtime inside the daemon for V1; implement the allowlisted CDP session in Rust (`tokio` WebSocket client) and reuse only the harness mechanics as reference. The existing Rust policy modules `browser_consent.rs` and `browser_control_service.rs` become the admission layer.
- Terminal rendering stays in TypeScript (a terminal emulator component in the WebView); scrollback ring buffer, backpressure and receipts live in Rust.
- `WorkbenchPanel.tsx` (608 lines) mixes five views; split per view and lazy-load Browser and Terminal panes so the unavailable path costs no bundle weight.

## Upstream reference: OpenHands command receipts and terminal observations — PROPOSAL (2026-11-06)

**Status: PROPOSAL for owner review. No upstream code was copied, vendored or added as a dependency, and no LiteCowork change below is decided.** Pins: shell `OpenHands/OpenHands` `22e3057c89b2e5245a5a36fd9c48e52c8a984ba4` and engine `OpenHands/software-agent-sdk` `f19fb2cf6a7f38266c6be954e91a9ef2a360bf9f`, both MIT, both read on 2026-11-06. - Ordered command receipt persisted before publication — `BashOutput{command_id, order (monotonic), exit_code=None⇒still running, stdout, stderr}` plus a separate `BashError`; chunks are written to the event store before they are published, so a subscriber that dies cannot lose a receipt (engine `openhands-agent-server/openhands/agent_server/models.py` L669–L692; `.../bash_service.py` L346–L388). Directly useful for B-23: it is the message shape a daemon-owned PTY/ConPTY provider would emit and the cursor a renderer would resume from.
- Timeout is a terminal receipt rather than a silent kill — process-group SIGTERM, then SIGKILL escalation, then `exit_code = -1` with a stated reason; a stop that races the spawn is recorded and applied when the process exists (engine `.../bash_service.py` L340–L344, L417–L436). Relevant to the containment-honesty rule in this file's viability section: a kill is attributable, not invisible.
- Model-visible text states the exit status and the truncation bound — `exit_code=-1` means soft-timeout and incomplete, the observation carries a `timeout` flag, and the rendered text appends `[Command finished with exit code N]` after bounded truncation (engine `openhands-tools/openhands/tools/terminal/definition.py` L146–L199). Candidate replacement for the fabricated "completed with exit code 0" line.
- Consumer-side receipt integrity — a duplicate receipt raises, an absent exit code becomes `-1` with an explicit timed-out reason, and a transport error is never reported as success (engine `openhands-sdk/openhands/sdk/workspace/remote/remote_workspace_mixin.py` L218–L284). Candidate test cases for any daemon→UI receipt channel.
- Session status machine carried across polls — `COMPLETED / NO_CHANGE_TIMEOUT / HARD_TIMEOUT` with `prev_status` (engine `openhands-tools/openhands/tools/terminal/terminal/terminal_session.py` L39–L46): a reference vocabulary for the distinct close/detach/stop/Runtime-restart semantics B-23 requires.

### Proposed Browser settings interaction (TARGET for T22 review)

The V1 Settings inventory names a **Browser & Computer** category, but the category is not mounted today. If owner review accepts it, keep separate Browser and Computer sections so the user can tell which provider and permission surface each setting controls. Progressively disclose Browser settings only when a Browser provider exists: show Runtime/provider/profile readiness and Workspace scope first; then the Browser-owner-returned effective site-policy outcome and every relevant source/reason; then profile data/download actions; then privacy and sanitized diagnostics. Do not show a global “Browser enabled” switch as if it were consent. A Workspace preference labeled **Allow Browser tools in new agent sessions** is omitted for any provider that lacks verified Feature 001/002 support for LiteCowork-mediated tool provisioning. Where supported, it applies only to sessions started after the change; it does not create a session, share local preview, grant input, or govern direct native-harness tools outside a qualified LiteCowork broker. The Settings projection describes site policy only; action dispatch still rechecks Runtime/Environment, applicable Task/Attempt, grants, control lease and Effect policy. Separately show per-session consent, local preview, any agent observation grant, per-origin permissions and the current input lease. Each has its own owner and revocation behavior.

Existing-Chrome connection is a separate per-session action from the Workbench Browser surface, never a Settings toggle. Before attachment, disclose that the connection may expose open tabs, session storage and authenticated sites; require explicit user permission and Chrome confirmation; verify version and integrity; and show cancelled/denied, incompatible, integrity-failed, connected, detached and revoked states. Failed checks leave Chrome unattached. For supported bookmark/preferences import, use a staged dialog: choose an explicitly supported non-secret source; show the Workspace profile destination, item counts, duplicates and skipped items; allow dry-run; then require a clear commit action. Never offer checkboxes for credentials, cookies, browsing history or extensions, and never ask to elevate privileges to extract them. For profile cleanup, preview the exact categories and provider-deletable scope, require confirmation, bind the mutation to the observed profile version, commit a durable pending intent and stable idempotency identity before the external provider call, then commit the outcome receipt only after provider reconciliation. For any unsupported control (history manager, extension manager, WebMCP, full CDP, external-app URL routing), omit the control until its separate contract and provider path exist rather than displaying a nonfunctional toggle.

This proposal does not define new IPC commands, schemas, or persistent settings. Those require T22 owner decisions and the authorized T23 promotion task; mutations must then be traced through the exact Settings control, typed command, authenticated Operator route, authorization, profile/version fence, receipt, projection and restart recovery. The current screen remains unavailable and has no Browser controls.
