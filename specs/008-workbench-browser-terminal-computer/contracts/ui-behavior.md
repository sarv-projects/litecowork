## Target surface

- Workbench is a resizable right-side view over authorized Workspace/Resource/Environment objects. It does not own privileged shell/browser processes. Closing the pane detaches the view unless the user explicitly requests a separate session Stop/Close operation.
- Product-level target: the Workbench belongs to the same conversation-led workspace as Projects and unified Recents. It is a contextual object surface, not a separate Browser, Code, Files or Cowork mode. Less-frequent domain pages are reached through More or from the current object/context. This navigation proposal is IN_REVIEW; the accepted four-destination baseline remains current until owner approval.
- The 2026-11-14 general-shell proposal uses object tabs plus a keyboard-searchable **+ / New tab** chooser. The chooser lists only views/actions backed by current owner contracts and reports the precise missing prerequisite for unavailable options. Object tabs carry owner identity and optional immutable revision; a tab switch is a local view transition. `OpenWorkbenchObject` resolves/reauthorizes the current object through its owning read path; it does not imply an OpenAPI command, create a provider, start capture or spawn a process. Restored references are reauthorized and show missing/revoked/stale recovery instead of stale content.
- A URL entry may be offered only as a Browser-owned action when a qualified Browser provider and its navigation policy are available. It is not a generic filesystem path opener or authority to follow an agent-supplied destination; without that owner path the chooser reports Browser unavailable and offers no active URL action.
- The tab strip is contextual rather than an always-visible tool inventory. It supports bounded overflow, close, keyboard selection and expansion. Opening/dismissing the chooser and switching tabs preserve conversation scroll, composer draft and focus unless the user explicitly navigates into an editing control. Dirty authored content uses its Artifact owner's save/discard/conflict guard.
- A future external **Open with** action is not served or included in V1 here. If separately accepted, it must be an explicit handoff for an exact file/version and clearly state that external edits, permissions and effects are outside LiteCowork mediation unless a later qualified reconciliation path exists.
- An optional agent-status object is limited to public status events that the selected native provider actually emits and the adapter correlates to this Workspace/Conversation/turn. It must not expose native private transcript/reasoning or assume ACP defines a universal subagent event/feed. With no supported projection, the chooser omits the view or explains why it is unavailable.
- Files show admitted Resources or exact Environment filesystem views; labels and location identity distinguish Workspace Resource projections from live local files. A Resource preview is never labeled as a live filesystem editor.
- Browser shows provider availability, mode, engine/version, profile identity, session/tab state, current URL, permission and control owner/epoch. Managed browser and Connect Existing Chrome are distinct modes. A generic iframe preview, if retained, is labeled as embedded preview and has no agent-action or Chrome assurance badge.
- Take control/Return to agent are available only for a live provider-backed lease. UI displays the exact owner/epoch and pending-action state; Takeover fences new admission immediately and cancels queued old-epoch input; USER input is enabled only after the provider confirms the new epoch; Return requires confirmation and fresh observation. Closing the side pane is separate from closing the browser or stopping a Task.
- Terminal tabs show exact shell profile/version, executable identity, current directory, Environment/process identity, containment evidence, session owner, and connection/lost state. Input/stdout/stderr and resize use a real PTY/ConPTY bridge. A tab switch, pane resize or detach/reattach does not own or restart the process.
- Explicit Stop is a separate command with process-tree/quiescence receipt. UI close is a view detach; daemon stop/restart renders ACTIVE→LOST/RECONNECTING only from authoritative service state. There is no silent shell restart.
- Diffs show actual content/revision or VCS comparison, exact source IDs/digests and true added/removed counts. Activity shows committed event/Attempt/Effect/process observations only, or is deferred to Work/Task detail by the screen contract.
- Computer use is only shown when a real provider and OS permission exists. Otherwise the UI states unavailable/unsupported with a reason; it never animates a phantom cursor or claims screen capture/input injection.

## Browser Settings screen (008-T22 proposal; TARGET / IN_REVIEW)

The target [V1 Settings inventory](../../../docs/V1-UI-SCREEN-CONTRACT.md#14-settings) names one **Browser & Computer** category; it is not currently mounted. If owner review accepts that target IA, keep Browser preferences inside it, with a visibly separate **Browser** section and **Computer** section; do not add a permanent Browser navigation destination or combine browser and whole-desktop authority. The accepted global navigation baseline remains in force until owner review records a change. This proposal refines the Browser portion of [CHROME-BROWSER-LLD Settings surface](../../../docs/CHROME-BROWSER-LLD.md#settings-surface) and does not allocate an API, event, schema or migration.

The screen presents grouped information in this order:

1. **Provider and Workspace profile** — show actual Runtime/provider readiness, supported mode, browser engine/version, Workspace-scoped profile identity, profile lock/health and retention state. Treat the provider's profile reference as opaque; do not assume UUID shape or infer ephemeral storage from a label such as “incognito.” Show ephemeral only when the qualified provider contract attests its lifecycle. Provider availability is not a user grant. Do not show a global “Browser enabled” switch. A future **Allow Browser tools in new agent sessions** preference is shown only for a provider whose Feature 001/002 owner path verifies LiteCowork-mediated Browser tool provisioning; ACP by itself does not provide that evidence. Omit it for providers without that capability. Where available, it applies only to sessions started after the change. It never consents to a live session, exposes local preview to an agent, or grants input. Existing sessions and grants stay visibly listed until separately revoked or stopped. No control claims to govern direct native-harness tools outside a qualified LiteCowork broker.
2. **Site access** — show the effective decision and its contributing sources/reasons as returned by the Browser access owner. Relevant facts may include Runtime/provider readiness, Workspace restrictions, profile and exact-origin rules, Browser-level permissions, and observable native/OS permissions; the UI does not impose an owner-unapproved universal precedence order. Navigation, observation, input, downloads, clipboard, camera and microphone remain distinct capabilities. A camera/microphone site rule controls whether the site may request access; it does not grant OS permission. Show OS permission state only when the qualified provider can observe it; otherwise say it is unavailable and provide no misleading Settings control. A site grant never creates the live session, model-disclosure permit or input lease.
3. **Profile data and downloads** — show only operations backed by the managed profile and Artifact owners: retention, eligible download destination/review and profile-scoped cleanup. Cleanup previews the exact categories and scope the qualified provider can delete (including when a provider can only delete an entire profile directory), requires explicit confirmation, commits against the observed profile revision and returns the owning receipt; ambiguous results require reconciliation before retry. Never label whole-profile deletion as clearing selected categories. Do not add a visited-page history manager until its private-data retention, query redaction, deletion and export contract is approved.
4. **Import** — allow a staged flow only for supported, user-selected non-secret bookmarks/preferences exports. Show source type, Workspace destination, item counts, duplicates and skipped entries before dry-run and explicit apply. Never import passwords, cookies, authenticated session state, browsing history or extensions; do not request administrator elevation to extract profile data.
5. **Privacy and diagnostics** — keep local Browser preview, agent observation/disclosure, Computer screen sharing, and Browser input ownership distinct. Any diagnostics are sanitized and opt-in. Browser extensions, WebMCP discovery, generic/full CDP access and external-app URL routing are omitted until separate owner contracts and qualified providers exist; tool discovery belongs to Connections & Tools, not a Browser permission shortcut.

The cross-layer path for every future read is Settings view → authenticated Tauri bridge → Operator authorization → owning profile/access/capability projection → Operator response → Settings projection. For every future mutation it is Settings control → typed UI intent → authenticated Tauri bridge → Operator principal/Workspace authorization → owner transaction with version/idempotency and durable intent/receipt → external provider effect after commit where required → owner reconciliation → Operator projection → Settings UI → restart/reconnect recovery. Operation IDs and event names remain unassigned here; promote them only with the owning service contract and canonical machine schemas. In the current build the Settings route and these operations are not served, so no interactive Browser Settings control is rendered. Computer settings remain a separate, unavailable surface until their own provider and consent path qualify.

## Current implementation crosswalk (re-checked 2026-11-12)

- `WorkbenchPanel` is a React right pane with launcher, Files, Terminal, Browser, Review (`diffs`) and Activity paths. Activity has its own launcher/tab and status-only empty state; it does not fall through to Review.
- Files is a list/filter of the Workspace Resource catalog; preview is fetched for an exact ResourceRevision. It is not a native filesystem tree or Environment browser.
- Browser is a URL input and iframe preview labelled "Embedded page preview". `browserUrl` starts empty (register A-51); there is no default endpoint and no containment claim. It is not a Chrome process/provider, managed profile, persistent session, browser agent or CDP/Playwright controller.
- Terminal (`TerminalPane`) renders "Terminal execution is unavailable" with the missing prerequisites. It has no input, executes nothing and shows no exit code, ConPTY, Job Object or KILL_ON_CLOSE label (register A-51; `tests/workbench-truthfulness.test.mjs`).
- Review (`ReviewPane`) renders "Nothing to review yet" and states that changes are never inferred from document text. No diff producer exists.
- Computer-use source has policy/consent helpers only; the Workbench shows a status-only UNAVAILABLE message with no action control.

This crosswalk describes the current fixed-tab source and remains distinct from the object-tab proposal above. The right pane currently has local `launcher | files | terminal | browser | diffs | activity` selection state, not persistent multi-object tabs, an object chooser, a generic file editor, a public Subagents view or the requested live Computer preview. These are TARGET proposals and do not change the current CODE/SERVED boundary.

## Revision 1.1 live-preview selection behavior (TARGET / IN_REVIEW)

After the owner has explicitly selected a source and granted local observation, when its existing Computer session reaches LIVE, the visible Workbench selects the Computer tab and shows the newest eligible frame. Selecting a tab never starts capture or changes agent-disclosure/input permits. The selection must not move keyboard focus, alter the Conversation scroll position, or discard the composer draft. If the owner deliberately closes/collapses the Computer view during that session, do not reopen it repeatedly; keep the persistent control strip and a **Show computer** entry available. With local preview disabled or revoked, show permission/source status and no frame. This is a view projection, not a new domain state or authorization command.

Acceptance is proposed as AC-027 in SPEC: verify automatic tab selection only for an already-authorized LIVE local view, no capture or focus side effect, suppression after deliberate dismissal, stale-frame labeling, and status-only rendering after local-preview denial/revocation.

## Required rendered regression cases after implementation

- Browser provider unavailable/needs setup/offline/ready; no iframe fallback masquerades as a qualified browser session.
- Managed profile isolation and connect-existing Chrome consent/version mismatch/revoke; default Chrome profile always refused.
- Browser stale session/tab/control epoch, input in-flight takeover, provider crash, fresh-observation Return and uncertain navigation form submit.
- Terminal profile discovery must not run startup scripts; selected shell exact executable/argv/cwd/env; unsupported shell remains unavailable.
- Terminal multi-tab attach/detach, resize, backpressure/high-volume output, explicit stop, process-tree containment, owner switch, pane close vs Stop, workspace change and daemon restart.
- Actual diff with equal revisions, rename, binary/unpreviewable content, no changes, missing source and uncommitted source; never report fabricated counts.
- Computer-use permission denied/revoked, sensitive-region exclusion, provider unavailable, per-action scope and stale permission.

## Historical revision 1.0 browser-only refinement (superseded requested scope)

The repository owner requested a visible, low-overhead view and an immediate manual takeover path on 2026-11-11. Resolve this within accepted B-22/B-32 boundaries:

- When the real managed-browser provider is available, show only that browser tab's viewport in Workbench using ephemeral frames, a bounded latest-frame queue, and stale-frame labeling. Do not persist frames into Conversation or Activity by default. Label it **Browser view**; it is not a share of the laptop desktop. Whole-desktop capture/input remains unavailable under B-32.
- While a live browser lease is AGENT-owned, show a persistent, non-modal banner with session/tab identity and **Take over**. The command fences new agent inputs, resolves or cancels queued old-epoch inputs, reaches a bounded safe point for dispatched input, then atomically advances the lease epoch to USER. Report USER control only after the provider confirms the epoch and rejects old-epoch input. Reconcile a dispatched action that may already have taken effect; unresolved outcomes remain pending/unknown. Move focus to the browser after confirmed transfer.
- Browser **Take over** transfers browser input authority only. It does not stop Conversation generation, cancel a Task, or close the browser. Conversation **Take control** is a separate action owned by Feature 012: cancel the active Conversation turn through Feature 001 Stop, wait for observed quiescence, settle `CANCELLED` and record `OWNER_TOOK_CONTROL`; only then does the owner continue by hand. Sending a message is a separate subsequent turn, never an implicit takeover side effect.
- Without a served provider-backed lease, show status only. Returning control is separate and explicit: confirm, advance the epoch, obtain a fresh observation, and resume only from that observation. Never replay stale queued inputs or auto-submit a user-edited form.

Every command below crosses typed UI -> authenticated Tauri bridge -> Operator using transport Principal, Workspace scope, expected revision and stable idempotency; service names are proposed ports pending T23 promotion. None is an allocated operationId or current call site. Receipt/event references are proposed semantics requiring canonical schema promotion.

| Computer **Share with agent**, **Hide from agent** -> SetAgentObservationPermit | Trust exact AgentSession/destination/scope/expiry; transaction records permit and outbox; revoke flushes queued disclosures | Independent local-view and agent-view indicators; USER input can retain local observation; no chat persistence; AC-021, T24 |

Take over and Stop run remain reachable while Computer is hidden or another tab is selected. Keep the persistent, non-modal app-chrome strip outside captured pixels, generated artifacts and agent-controlled pages. Because the target app normally covers LiteCowork, Computer input also requires at least one qualified out-of-app emergency trigger (global shortcut or native tray item); without one, the provider is observation-only. The trigger closes the broker fence first and may show the app/result afterward. Stop run closes Computer input, then requests the actual Conversation/Task stop through their owners; each domain reconciles separately. Computer tab includes source, frame age, local/agent sharing state, input owner and Stop sharing. No capture begins on launch, Quick Entry, + menu opening or automatic context switch. Saved layout restores view references only after authorization.

Use a persistent, non-modal takeover banner instead of a transient modal popup: it stays visible across Workbench tabs, does not time out, and does not block the target view. Show **Take over** only while a live LiteCowork-mediated Computer input lease is AGENT-owned. A normal text-only Conversation/Task run uses its own run status and owner-routed Stop when that path is qualified; it does not show Computer Take over. **Take over** fences further mediated Computer input while reasoning and unrelated authorized work may continue; **Stop run** also requests cancellation through the applicable Conversation/Task owner. Neither button sends a message. A native notification may announce that control began, but cannot replace the persistent banner and qualified out-of-app trigger. Direct native-agent tools outside LiteCowork's broker are not intercepted by this control.

While a Conversation turn is RUNNING, sending a normal message does not transfer computer control or stop the run. An in-turn continuation/answer is available only for an exact provider-correlated request whose typed reply path has been qualified under Feature 001; otherwise the user stops the run, waits for settlement, and sends a new turn. Do not add a prompt queue or generic steering action by implication.

Compact geometry follows Desktop shell: roughly 24% clamped to 300-400 CSS px with 520px chat minimum; below 900px use a full-surface route. **+** opens a keyboard-navigable menu showing actual readiness/reasons, not a row of dead buttons. Object tabs retain separate Computer, Browser, Terminal and Canvas identities. Closing the last view returns Start; closing a live view explains detach vs stop. Unsaved Canvas drafts receive Save/Discard/Stay. Canvas is editor/artifact content, never arbitrary JS in the chat WebView.

Rendered tests cover persistent takeover with tab hidden, keyboard/focus/zoom, no capture on selection, expired permit and workspace switch, stale frames, provider loss, dirty Canvas close, blocked terminal and independent capture/input availability. Packaged UI/provider tests are mandatory before qualification; this map itself is TARGET.
