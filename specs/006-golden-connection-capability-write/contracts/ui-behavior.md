## Target flow and state distinctions

1. Discover catalog availability, host compatibility, package installation and authentication state are distinct observations. Selecting a package never creates a Connection or grants capability authority.
2. The owner explicitly selects **Connect GitHub**. LiteCowork names the GitHub App and explains the repository `Issues: write` permission needed for the complete issue-comment read/write capability, including that this provider permission is broader than the single LiteCowork operation. The UI opens only `https://github.com/login/device` in the system browser and displays the provider-issued one-time user code, expiry, waiting state and Cancel. It warns the owner to enter only a code generated by this current LiteCowork flow. The code is never put in Conversation, agent context, logs or event payloads. A canceled, denied or expired attempt has no connected state; restart requires a fresh owner action.
3. Connection/authentication, GitHub App installation/repository access, capability assignment, LiteCowork grant and Invocation state are separate. The UI confirms the GitHub account/connection and accessible repositories through authenticated provider data, never an unverified display hint. An unavailable App installation or target repository is shown as **Needs GitHub access** with a safe user-directed setup path; it is not presented as a LiteCowork grant.
4. Connection health/status is displayed separately from capability assignment and grants. Local disconnect immediately fences future use and removes local credentials; GitHub authorization revoke is shown as a separate owner action. Historical Invocations/Effects remain readable within retention rules.
5. The owner assigns a compatible capability and grants the exact repository/operation/expiry scope. The selected native agent sees only an opaque capability reference, never device code or token bytes.
6. A read operation displays its source/receipt. A consequential write displays the exact target/action digest, operation class, exact LiteCowork grant, provider permission breadth, approval expiry and reconciliation semantics before approval.
7. Needs You approval confirms the exact action digest. Approve is a decision state, not a dispatch. The user-visible outcome changes only after the mediated Invocation/Effect is reconciled and any required independent verification is committed.
8. Revoke immediately fences later invocation attempts; offline/expired/unknown/ambiguous states remain truthful and block new actions.

## Current implementation crosswalk (not the target)

- DiscoverPage currently provides Explore, Installed/native, Managed and Connections tabs. Explore lists Workspace-local skills and says public package discovery is unavailable. Installed/native shows only bounded Runtime-reported capability hosts, not a complete native inventory.
- Managed explicitly says LiteSPM install/adopt/repair/update/unmanage flows are not qualified. Connections explicitly says account Connections cannot be read. No account sign-in or Connection details surface is rendered.
- Discover row action buttons are disabled: `connectActionOutcome()` returns `allowed=false` even for otherwise available rows. Workspace-local skill Open/Run is unavailable, and package Connect/Use is unavailable pending LiteSPM contract qualification.
- The backend connect-or-install route returns 503; its test route returns UNKNOWN without contacting a provider. UI does not simulate a successful connection or grant.
- Needs You ApprovalDetail is real: it loads an owner-scoped Approval, shows exact action/target/risk/expiry, requires exact digest on APPROVE, preserves the same idempotent decision request after uncertain response and refreshes state. Its copy correctly says approval does not execute the action or create a reusable grant.
- No connected account list/detail, device-authorization begin/poll/cancel UI, permission review, connection revoke, provider read/write picker, CapabilityGrant authoring for a connector, or actual Invocation dispatch/reconciliation UI exists.

## Revision 1.1 user-delegated V1 additions (TARGET; owner ratification pending)

- Discover Connections tab: list plus "Connect GitHub", disabled with a stated reason when the keystore is unavailable, the user cancels, provider configuration is missing, or device authorization cannot start.
- Connection detail: authorization status, repository access, the GitHub App's Issues permission in plain words, the exact LiteCowork grant, recent Invocations, Disconnect with confirmation, and remote-revoke state (`CONFIRMED` or `OWNER_ACTION_REQUIRED`) with the GitHub Authorized GitHub Apps settings destination.
- Device authorization panel: visible App name, fixed GitHub verification URI, user code with copy control, expiry countdown, provider waiting/polling status and immediate cancel. Never display the opaque device code. Copying the user code is an explicit user action and must not send it into chat or to the connected agent.
- Empty/loading/failure states distinguish checking authorization, waiting for user, permission denied, code expired, user canceled, App not installed for target resources, insufficient repository access, keystore unavailable, refresh expired, and reconnect required. Retry starts a fresh device flow after a terminal attempt; it does not silently reuse an expired code.
- Explain before authorization that the GitHub App may act only where both the user and App have access; installation repository selection is controlled at GitHub. LiteCowork's exact grant remains a separate narrower control.
- Golden read and golden write are separate actions; the write shows the exact target and body and routes to Needs You for approval.
- Managed and Installed tabs stay owned by package 013.

## Required rendered regression cases after implementation

- Cancel, `access_denied`, expiry, restart and late poll leave no new usable Connection; stale/duplicate polls fail by AuthAttempt identity/version; no loopback callback or PKCE state is used.
- The device code never leaves daemon memory; user code appears only in the current authorized settings surface; neither code enters React Conversation state, event payloads, logs or agent context. User can cancel immediately, and cancel fences late token responses.
- Device polls respect the provider interval and `slow_down`; no background poll continues after cancel, expiry, terminal state or shutdown.
- Insufficient GitHub App permission, missing App resource access, missing user access and a cross-repository LiteCowork grant each deny dispatch with a stable reason.
- Local disconnect is visibly distinct from revoking GitHub App authorization in account Settings; the UI never claims remote revoke without evidence.
- Connection token custody commit failure purges newly written secrets and does not show CONNECTED; refresh stampede serializes; invalid_grant becomes REAUTH_REQUIRED; revocation fences refresh and invocation.
- Catalog listing, package install, Connection status, capability assignment, grant and Invocation are shown as separate states.
- Provider not qualified, missing scopes, expired Connection, revoked grant, stale approval, unavailable Runtime and denied Trust each disable the relevant action with a stable reason.
- APPROVE with stale digest/version is rejected; an exact decision replay is idempotent; approval alone does not show the external action as completed.
- Timeout after dispatch becomes AMBIGUOUS; no retry occurs until provider/client idempotency and exact-target reconciliation prove the basis.
- Revoking the Connection blocks later read/write calls while preserving historical Approval, Invocation, Effect and Evidence history.

## Validation

Source-level tests or a mounted Approval route do not prove a live connector. Qualification requires the chosen provider's real auth, read, consequential write, exact approval, reconciliation, revoke and restart USER path on the declared OS.
